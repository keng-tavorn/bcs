# ADR-016: เทียบ Zip เป็นลำดับการพัฒนา แยกจากสิ่งที่ใช้ได้จริง

- สถานะ: ตัดสินแล้ว
- วันที่: 2026-10-01
- ที่มา: ตารางเรื่องที่ต้องตัดสินใจในเอกสารต้นทาง (spec §18.1 · ภาคผนวก C: เอกสารต้นทางหัวข้อ 14 "เรื่องที่ต้องตัดสินใจ") · เอกสารต้นทางหัวข้อ 7 เทียบกับ Zip อยู่ที่ §0.5 และ ADR นี้ (ภาคผนวก C)

## บริบท

- ต้นแบบหลักของ BCS คือ Zip แต่ไม่ขายว่า "เหมือน Zip" (§1.2)
- ความเสี่ยง "พูดเกินจริงว่ามีเหมือน Zip" (§18.4)

## การตัดสินใจ

> นำเสนอความสามารถเทียบ Zip เป็นลำดับการพัฒนา แยกจากสิ่งที่ใช้ได้จริง และผูกสัญญากับขอบเขตที่ตกลง

- ทุกอย่างใน spec หมายถึง "อยู่ในแผน" ไม่ใช่ "ใช้ได้แล้ว" (§0.5)
- สถานะจริงอยู่ที่ `docs/feature-status.yaml` ซึ่งเป็นแหล่งเดียวที่ใช้ตอบลูกค้า · เอกสารขายอ้างได้เฉพาะสถานะ `verified` และ `live` (§15.6)
- ในระบบ โมดูลเปิดตามสัญญาพร้อม `contractRef` (§4.11 · BR-AUTH-08 · ADR-034) · ถ้อยคำและขั้นตอนในสัญญาขาย spec ไม่ได้ระบุ

## ผลที่ตามมา

- อัปเดต `docs/feature-status.yaml` ทุกครั้งที่ติ๊กข้อใน checklist (§17.5) และ `pnpm verify` ตรวจว่าไฟล์อ้าง FR ที่มีจริงและสถานะถูกต้อง (§15.5 ข้อ 10)
- ก่อน go-live ไฟล์นี้ต้องเป็นปัจจุบัน (§16.9)
- ไม่แข่งจำนวน integration กับ Zip (NG-8)
- หน้าจอยืมหลักการใช้งาน ไม่ลอกหน้าตา และห้ามลอกโลโก้ สี ชื่อ ภาพหน้าจอ หรือข้อความของ Zip (§9.9)
