# ADR-020: Event และ ledger แบบ append-only

- สถานะ: เสนอ
- วันที่: 2026-10-01
- ที่มา: เสนอโดย spec · ใช้ได้ทันทีเว้นแต่มีผู้คัดค้านใน PR (§18.1)

## บริบท

- `Event` เป็น audit trail ที่แก้ย้อนหลังไม่ได้และเป็นแหล่งคำนวณ KPI (§4.5 · P-8) · ทุกการเปลี่ยนสถานะต้องบอกได้ว่าใครทำอะไร ผ่านช่องทางไหน ภายใต้ DOA ฉบับใด (EG-6)
- งบใช้ ledger เป็นแหล่งความจริง (ADR-021)

## การตัดสินใจ

> Event และ ledger แบบ append-only บังคับด้วย trigger และแยก DB role

- `Event` `BudgetLedgerEntry` และ `EventSeal` ห้าม UPDATE และ DELETE (INV-EVT-01): trigger `bcs_forbid_mutation` บนทั้ง 3 ตาราง · REVOKE UPDATE DELETE TRUNCATE จาก `bcs_app` และให้แค่ SELECT INSERT (§6.3 ข้อ 1–2)
- role `bcs_migrator` ใช้กับ migration ผ่าน `DIRECT_URL` · role `bcs_app` ใช้ตอน runtime ผ่าน `DATABASE_URL` (§5.2 · ภาคผนวก B · FR-PLT-006 AC3)
- TRUNCATE อนุญาตเฉพาะ role migrator ใน local และ test (§6.3)

## ผลที่ตามมา

- `pnpm verify` ตรวจจากฐานข้อมูลจริงว่ามี trigger ครบ 3 ตัว และ `bcs_app` UPDATE `"Event"` ไม่ได้ (§6.3 · §15.5 ข้อ 5)
- trigger และ REVOKE ของ `BudgetLedgerEntry` ใส่ตอนสร้างตารางใน S3 และของ `EventSeal` ใน S5 (§6.2 คอลัมน์ขั้น) · ใน S1 ด่าน db ตรวจเฉพาะ `Event` (S1-03) · ข้อใน checklist §16 ที่ใส่ trigger และ REVOKE ของสองตารางนี้ spec ไม่ได้ระบุ (S3-01 ระบุแค่ CHECK §6.3 ข้อ 3 · S5-14 ระบุแค่ job seal audit)
- แก้ไขด้วยรายการย้อนกลับเท่านั้น (INV-BUD-06) · ห้าม UPDATE หรือ DELETE Event และ ledger (§17.3)
- seal hash chain ทุกวัน 00:15 เวลาไทยและตรวจรายสัปดาห์ ถ้าไม่ตรงถือเป็นเหตุการณ์ความปลอดภัย (INV-EVT-03 · §4.5)
- SQL เพิ่มเติมทำด้วย `prisma migrate dev --create-only` และห้ามแก้ migration ที่ apply แล้ว (§6.3)
