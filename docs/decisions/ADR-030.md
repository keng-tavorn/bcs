# ADR-030: Transactional outbox ส่งต่อ Inngest

- สถานะ: เสนอ
- วันที่: 2026-10-01
- ที่มา: เสนอโดย spec · ใช้ได้ทันทีเว้นแต่มีผู้คัดค้านใน PR (§18.1)

## บริบท

- งานเบื้องหลังถือฐานข้อมูลเป็นแหล่งความจริง ทุก function อ่านสถานะล่าสุดก่อนทำ (§4.6 หลักการ 1) · การแจ้งเตือนเขียนในธุรกรรมเดียวกับ command จึงไม่หลุดจากสถานะจริง (§4.7)
- Inngest อาจไม่พร้อมตอน commit (FR-PLT-012 AC3)

## การตัดสินใจ

> Transactional outbox ส่งต่อ Inngest

- service เขียน `Outbox` ในธุรกรรมเดียวกับ aggregate ledger และ Event (§4.3 ข้อ 4) · `notify()` เขียน `Notification` และ outbox ในธุรกรรมเดียวกับ command เสมอ (§4.7)
- หลัง commit ส่ง outbox ไป Inngest ทันทีแบบ best-effort โดยใช้ `Outbox.id` เป็น event id เพื่อกันส่งซ้ำ (§4.3 ข้อ 5)
- รายการที่ส่งไม่สำเร็จ job `outbox-sweeper` ส่งซ้ำทุก 1 นาที สำหรับรายการที่ค้างเกิน 30 วินาที (§4.3 · §4.6)

## ผลที่ตามมา

- Inngest ไม่พร้อมตอน commit → outbox ยังอยู่ และถูกส่งภายใน 2 นาทีหลัง Inngest กลับมา (FR-PLT-012 AC3)
- function ของ Inngest ต้อง idempotent และอ่านสถานะล่าสุดก่อนทำ (§4.6 · ADR-006)
- ติดตาม metric outbox ค้าง (NFR-OBS-02) · ตาราง `Outbox` มี eventName payload createdAt sentAt attempts lastError (§6.2) · ทำในข้อ S1-05
