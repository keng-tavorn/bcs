# ADR-039: แยก tenant ในฐานข้อมูลเพิ่มเติม

- สถานะ: เสนอ
- วันที่: 2026-10-02
- ที่มา: ผลการตรวจแบบโต้แย้งของฐาน S1 (2026-10-02) พบว่า `db.forTenant()` กรองเฉพาะ query ชั้นบนสุด จึงยังอ่านหรือเขียนข้าม tenant ได้

## บริบท

- INV-TEN-01 กำหนดว่า query ผ่าน client ของ tenant A ไม่มีวันคืนแถวของ tenant B (§4.8 · ADR-029)
- การตรวจพบสามช่องทาง (มีสคริปต์ทดลองยืนยันทุกข้อใน `scratch/review-tenant/` ซึ่งไม่ commit · หลักฐานถาวรคือ `tests/generated/tenant-isolation.test.ts`): (1) `include` `select` และตัวกรองตาม relation วิ่งผ่านตารางที่ใช้ร่วมกันทุก tenant เช่น `User` `Session` `TwoFactor` `PlatformAdmin` ไปถึงแถวของ tenant อื่น รวมถึง hash รหัสผ่านและ secret ของ TOTP (2) nested write เช่น `connect` ย้ายแถวข้าม tenant หรือเปลี่ยนผู้มีอำนาจลงนามของอีกองค์กรได้ (3) foreign key ชี้ไปแถวของ tenant อื่นได้ เพราะ Postgres ตรวจแค่ว่าแถวมีอยู่ · และ `Event.seq` กับ `createdAt` ถูกกำหนดค่าจากโค้ดได้

## การตัดสินใจ

> แยก tenant ในฐานข้อมูลเพิ่ม: foreign key ระหว่างตาราง tenant รวม `organizationId` · `db.forTenant()` ห้ามเข้าตาราง identity และ platform และห้าม nested write · `Event.seq` เป็น identity

- foreign key ทุกตัวระหว่างตาราง tenant เป็นแบบคู่ `(organizationId, id)` ทำให้ Postgres ปฏิเสธการชี้ข้ามองค์กร · ผู้มีอำนาจลงนามของ `Organization` ตรวจด้วย trigger เพราะ key คู่ที่ใช้ `Organization.id` ทำให้ Prisma ไม่สร้าง id ให้
- `db.forTenant()` เข้าได้เฉพาะตาราง tenant และแถว `Organization` ของตัวเอง · ตาราง identity และ platform รวมทุกเส้นทาง `include` `select` ตัวกรอง และการเรียงตาม relation ที่ไปถึงตารางเหล่านั้น ถูกปฏิเสธ · nested write ถูกปฏิเสธทั้งหมด ใช้ foreign key แบบ scalar แทน
- แผนที่ relation สร้างจาก schema ด้วย `scripts/gen-db-relations.ts` (รันใน `pnpm db:migrate`) และเทสต์ที่สร้างอัตโนมัติล้มเมื่อแผนที่ไม่ตรง schema
- service ที่ต้องเพิกถอน session หรือ 2FA ใช้คำสั่งใน `src/server/db/sql/identity.ts` ซึ่ง join ผ่าน Member ขององค์กรนั้นในธุรกรรมเดียวกัน · การค้นข้าม tenant ที่เริ่มจาก token ลับ (ลิงก์เชิญ) อยู่ใน `src/server/db/lookups.ts`
- `Event.seq` เป็น `GENERATED ALWAYS AS IDENTITY` (§4.5) และ trigger กำหนด `createdAt` เป็นเวลาของฐานข้อมูลเสมอ

## ผลที่ตามมา

- เทสต์ที่สร้างจาก DMMF ตรวจทุกตาราง ทุก relation ที่ไปถึงตาราง identity หรือ platform (ทั้งทางตรงและผ่านตาราง tenant อีกชั้น) ทุก nested write และทุก foreign key ระหว่างตาราง tenant ว่าชี้ข้ามองค์กรไม่ได้
- ผู้ดูแลองค์กรรีเซ็ต 2FA ของสมาชิกที่ใช้บัญชีเข้าระบบเดียวกันกับองค์กรอื่นไม่ได้ (`FORBIDDEN` reason `SHARED_IDENTITY`) เพราะจะเปลี่ยนการเข้าระบบขององค์กรอื่นด้วย · spec ไม่ได้ระบุ: FR-AUTH-002 AC3 ยกเว้นเฉพาะผู้ดำรงตำแหน่งที่ DOA อ้างหรือมีงานอนุมัติค้าง ข้อนี้จึงเป็นข้อจำกัดสิทธิ์ของ ORG_ADMIN ที่เพิ่มจาก spec · ผลข้างเคียง: ผู้ที่เป็นสมาชิกสององค์กรขึ้นไปแล้วทำแอปยืนยันตัวตนหาย เหลือแค่รหัสสำรอง หรือให้องค์กรหนึ่งปิดใช้งานสมาชิกก่อน · ใช้ค่าที่ปลอดภัยกว่านี้ไว้ก่อนและรอผู้ใช้ยืนยันใน NEW-10 (§17.4) · demo มีองค์กรเดียวจึงไม่กระทบ
- migration ใหม่ทุกตัวที่เพิ่มตาราง tenant ต้องใช้ foreign key แบบคู่ · ด่าน integration ของ `pnpm verify` ตรวจด้วยเทสต์ใน `tests/generated/tenant-isolation.test.ts`
- Postgres RLS ยังทำภายหลังตาม ADR-029
