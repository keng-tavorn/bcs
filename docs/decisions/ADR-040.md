# ADR-040: การใช้ Better Auth

- สถานะ: เสนอ
- วันที่: 2026-10-02 · แก้ 2026-10-03 (ล็อกขั้นที่สอง · ตรวจและนับในขั้นเดียว · rate limit ต่อ IP · cookie Secure · LINE verify · ตรวจ env)
- ที่มา: ตัดสินระหว่าง S1-07 ตามความสามารถของ Better Auth 1.7 ที่ติดตั้งจริง

## บริบท

- Better Auth เป็น identity อย่างเดียว สมาชิกองค์กรและสิทธิ์อยู่ในตารางของเรา (§5.1)
- FR-AUTH-001 ถึง FR-AUTH-003 ต้องการ: เชิญด้วยลิงก์ใช้ครั้งเดียว 72 ชั่วโมง · รหัสผ่านอย่างน้อย 12 ตัว · ล็อกหลังผิด 5 ครั้งใน 15 นาที · TOTP บังคับตามบทบาท พร้อมรหัสสำรอง 10 รหัส · session idle 30 นาที (LIFF 15 นาที) อายุสูงสุด 12 ชั่วโมง
- rate limit ในตัวของ Better Auth นับทุกครั้งที่เรียก ไม่แยกครั้งที่ผิด ผู้นำเสนอ demo ที่สลับผู้ใช้หลายคนจากมือถือเครื่องเดียวจึงจะถูกล็อก

## การตัดสินใจ

> ใช้ Better Auth: ล็อกการเข้าระบบนับเฉพาะครั้งที่ผิด · บังคับ 2FA ตามบทบาทและตำแหน่ง · TOTP ของผู้ใช้ตัวอย่างจาก `SEED_TOTP_KEY` (ไม่บังคับ) · plugin `liffIdToken`

- ล็อกการเข้าระบบเอง (ตาราง `AuthAttempt`): ผิด 5 ครั้งใน 15 นาทีต่อบัญชีหรือต่อ IP → ปฏิเสธด้วย 429 และบันทึก `auth.login_locked` · การเข้าระบบที่สำเร็จไม่นับ · ตีความ NFR-SEC-05 ("login 5 ครั้งต่อ 15 นาทีต่อบัญชีและต่อ IP") ว่านับเฉพาะครั้งที่ผิดตาม FR-AUTH-001 AC3 เพราะถ้านับทุกครั้ง ผู้นำเสนอที่สลับผู้ใช้ตัวอย่างจากมือถือเครื่องเดียวจะถูกล็อก · การอ่านนี้หลวมกว่าตัวอักษรของ NFR-SEC-05 จึงรอผู้ใช้ยืนยัน (§17.4)
- ขั้นที่สองของการเข้าระบบ (TOTP หรือรหัสสำรอง) ใช้ตัวนับเดียวกัน: รหัสผิดแต่ละครั้งเป็นครั้งที่ผิดของบัญชีนั้นและของ IP นั้น (NFR-SEC-05 "OTP ผิดได้ 5 ครั้ง") และเมื่อบัญชีถูกล็อก ขั้นที่สองก็ถูกปฏิเสธด้วย 429 · Better Auth จำกัดเองแค่ 5 ครั้งต่อการเข้าระบบหนึ่งรอบ ผู้ที่รู้รหัสผ่านจึงเริ่มใหม่ได้เรื่อย ๆ ถ้าไม่นับต่อบัญชี
- ตรวจและนับเป็นขั้นเดียวต่อบัญชี: ก่อนตรวจรหัสผ่านหรือรหัสยืนยัน ระบบจองครั้งนี้เป็น "ผิด" ไว้ก่อนในธุรกรรมเดียวกับที่นับ ภายใต้ advisory lock ของบัญชี (`AuthAttempt.pending`) แล้วเปลี่ยนเป็นสำเร็จเมื่อรหัสถูก · การเดาพร้อมกันหลายทางของบัญชีเดียวจึงถูกตรวจได้ไม่เกิน 5 ครั้ง · ตัวนับต่อ IP นับเฉพาะครั้งที่ตรวจเสร็จแล้ว คนในสำนักงานเดียวกันที่กดเข้าระบบพร้อมกันจึงไม่ล็อกกันเอง (ราคาของทางนี้: การเดาข้ามหลายบัญชีพร้อมกันจาก IP เดียวอาจเกิน 5 ได้ในชั่วขณะ แต่แต่ละบัญชียังได้ไม่เกิน 5) · ครั้งที่จองแล้วตรวจไม่เสร็จ (server หยุดกลางทาง) นับเป็นครั้งที่ผิดของบัญชีนั้น
- rate limit ต่อ IP ของ Better Auth ปิดสำหรับ `/sign-in/email` `/two-factor/verify-totp` และ `/two-factor/verify-backup-code` เพราะตัวนับของ Better Auth นับทุกคำขอจนกว่า IP นั้นจะเงียบครบหนึ่งช่วงเวลา ห้องที่เข้าระบบต่อกันบน Wi-Fi เดียวจะถูกปฏิเสธ ทั้งที่การกันเดารหัสอยู่ที่ตัวนับของเราแล้ว · route อื่นของ two-factor (เช่น เปิดใช้ 2FA ที่ตรวจรหัสผ่าน) ยังใช้กฎของ plugin (3 ครั้งต่อ 10 วินาที)
- 429 จากตัวนับของเราส่ง `code: LOGIN_LOCKED` พร้อม `reason` (`ACCOUNT` หรือ `IP`) และ `retryAt` · หน้าเข้าระบบและหน้าใส่รหัสบอกว่าล็อกที่บัญชีหรือที่เครือข่ายและลองใหม่ได้เมื่อไร โดยไม่แนะนำให้รีเซ็ตรหัสผ่าน (ล้างตัวนับไม่ได้) · 429 อื่นใช้ข้อความ `RATE_LIMITED` ของ §14.2
- 2FA: ผู้ที่มี role นอกจาก REQUESTER (และตั้งแต่ S2 ผู้ดำรงตำแหน่งที่ DOA อ้าง) ต้องตั้ง TOTP ก่อนทำงาน · ปิด 2FA เองไม่ได้ ทุกคนรวมผู้ขอที่เปิดเองโดยสมัครใจ (spec ไม่ได้ระบุกรณีผู้ขอ) · ORG_ADMIN รีเซ็ตให้พร้อมเหตุผล (เก็บใน Comment) และ event `auth.2fa_reset` · ยืนยันการตั้งค่าแล้วบันทึก `auth.2fa_enabled`
- cookie: `Secure` (และคำนำหน้า `__Secure-`) เปิดเมื่อ `APP_URL` เป็น https ตรวจจาก protocol ของ URL ไม่ใช่ตัวอักษรต้นสตริง (NFR-SEC-02) · env.ts นอก local รับ `APP_URL` เฉพาะรูป `https://host` ตัวเล็กอยู่แล้ว
- session: อายุ 12 ชั่วโมงไม่ต่ออายุ · idle ตรวจด้วยนาฬิกาจริง (ไม่ใช่นาฬิกาธุรกิจที่ e2e เลื่อนได้) ใน `resolveSession` และลบ session ที่หมดอายุ
- ผู้ใช้ตัวอย่าง (local และ staging เท่านั้น): รหัสผ่านจาก `SEED_DEV_PASSWORD` · ถ้ามี `SEED_TOTP_KEY` (ตัวแปรที่เพิ่มจากภาคผนวก B · `.env.example` ระบุในส่วนที่เพิ่ม) จะตั้ง TOTP ให้ล่วงหน้าด้วย secret ที่คำนวณจาก key (ใช้ใน e2e · ภาคผนวก A ไม่ได้ระบุการตั้ง TOTP ให้ผู้ใช้ตัวอย่าง) ถ้าไม่มี ผู้ใช้ตั้งแอปยืนยันตัวตนตอนเข้าระบบครั้งแรก จึงไม่ต้องเก็บ secret เพิ่มบน staging
- รับลิงก์เชิญของอีเมลที่มีบัญชีอยู่แล้ว (สมาชิกขององค์กรอื่น) แทนรหัสผ่านและออกจากระบบทุกอุปกรณ์ เหมือนการรีเซ็ตรหัสผ่านทางอีเมล · spec ไม่ได้ระบุกรณีนี้ (FR-AUTH-001 AC1 พูดถึงการตั้งรหัสผ่านครั้งแรกเท่านั้น) และผลนี้ตัด session ที่ใช้กับองค์กรอื่นด้วย จึงรอผู้ใช้ยืนยันใน NEW-10 · demo มีองค์กรเดียวจึงไม่กระทบ
- ตรวจ env (`src/lib/env.ts`): นอก local `BETTER_AUTH_URL` ต้องเท่ากับ `APP_URL` ทุกตัวอักษร · `LINE_API_BASE_URL` ถูกทำให้เป็นรูปมาตรฐาน และปฏิเสธ query fragment user:password หรือ scheme ที่ไม่ใช่ http ในทุก environment · `SEED_DEV_PASSWORD` ต้องยาวอย่างน้อย 12 ตัว (คู่มือขอ 16) แอปไม่เริ่มถ้าสั้นกว่า · นอก local คำสั่ง Prisma ทุกคำสั่งตรวจ env ทั้งชุดผ่าน `prisma.config.ts` รวม `postinstall` และ `pnpm db:migrate` ใน build ของ Vercel ค่าที่ผิดบน staging จึงทำให้ deploy ล้มก่อน migrate พร้อมบรรทัด `- KEY: ข้อความ` ใน build log
- LIFF: plugin `liffIdToken` ที่ `POST /api/auth/liff/session` ตรวจ ID token กับ endpoint verify ของ LINE ด้วย `LINE_LIFF_CHANNEL_ID` และตรวจ iss aud exp เอง แล้วสร้าง session ผ่าน API ภายในของ Better Auth (BR-LINE-02) · นอก local `LINE_API_BASE_URL` ต้องเป็น `https://api.line.me` เท่านั้น (env.ts) เพื่อไม่ให้ระบบเชื่อผลตรวจ token จากที่อื่น · ผูกบัญชี LINE กับสมาชิกใน S5 · spec §9.1 S5-03 และ ADR-024 เรียก route นี้ว่า `/api/liff/session` แต่ endpoint ของ plugin อยู่ใต้ `/api/auth` · S5-03 เพิ่ม route `/api/liff/session` ที่ส่งต่อมาที่นี่ หรือแก้ §9.1 และ ADR-024 ให้ตรงกัน
- คิวอาร์โค้ดของแอปยืนยันตัวตนสร้างด้วย `uqr` 0.1.3 (MIT ไม่มี dependency ตรึงเวอร์ชัน) วาดเป็น SVG โดยไม่แทรก HTML · `uqr` เป็น dependency ใหม่ที่ spec §5 ไม่ได้ระบุ และ QR มี secret ของ TOTP อยู่ด้วย จึงแจ้งผู้ใช้ตาม §17.4 · ถ้าผู้ใช้ไม่อนุมัติ หน้าตั้งค่าจะเหลือเฉพาะรหัสให้พิมพ์เอง

## ผลที่ตามมา

- เทสต์ AC ของ FR-AUTH-001 ถึง FR-AUTH-003 เรียก endpoint จริงของ Better Auth ผ่าน `auth.handler` รวมการเดาพร้อมกัน 10 ทางและการเข้าระบบสองขั้น 32 ครั้งต่อกันจาก IP เดียว (`tests/integration/auth.test.ts`) · เทสต์ LIFF จำลองการตอบของ LINE · e2e ให้แต่ละเทสต์มี IP ของตัวเอง (`tests/e2e/fixtures.ts`) ตัวนับต่อ IP จึงไม่ข้ามเทสต์
- ส่วนของ FR-AUTH-002 AC1 และ AC3 ที่เกี่ยวกับผู้ดำรงตำแหน่งที่ DOA อ้าง (`IDENTITY_RESET` · BR-AUTH-07) และส่วนของ FR-AUTH-003 AC2 ที่เพิกถอน LINE link ActionToken และ delegation ทำในข้อที่สร้างของเหล่านั้น (S2 S4 S5) ผ่าน registry ของการปิดใช้งาน
- ถ้าอัปเกรด Better Auth ต้องรันเทสต์ทั้งชุดนี้ก่อน เพราะใช้ hook และ API ภายใน (`internalAdapter` `setSessionCookie` `databaseHooks` `$context` และ `symmetricEncrypt` ที่ seed ใช้เข้ารหัส TOTP ใน `src/server/auth/provision.ts`)
