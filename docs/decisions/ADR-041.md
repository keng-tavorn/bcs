# ADR-041: นโยบายของ command pipeline และ outbox

- สถานะ: เสนอ
- วันที่: 2026-10-03
- ที่มา: ตัดสินระหว่างแก้ S1-05 และ S1-06 รอบที่ 3 หลังผู้ตรวจพบช่องโหว่ · agent เสนอ ใช้ได้ทันทีเว้นแต่ผู้ใช้คัดค้าน

## บริบท

- §4.3 กำหนดขั้นตอนของ `runCommand` และ ADR-030 กำหนด outbox แต่ไม่ได้ระบุ: key ของผู้ส่งต่างประเภทชนกันได้หรือไม่ · การส่งหลัง commit รอได้นานเท่าไร · เมื่อไรนับเป็นการส่งล้มเหลว · ข้อความที่ส่งไม่ได้ตลอดไปจะจบอย่างไร
- `inngest.send()` ลองซ้ำเองหลายครั้ง ทำให้คำสั่งของผู้ใช้ค้างนานเมื่อ Inngest ล่ม
- แผนฟรีของ Inngest ให้ 50,000 executions ต่อเดือน งาน `outbox-sweeper` รันทุก 1 นาที (43,200 ครั้งต่อเดือน)

## การตัดสินใจ

> นโยบายของ command pipeline และ outbox: key กันส่งซ้ำแยกตามผู้ส่ง · ส่งหลัง commit ครั้งเดียวไม่เกิน 2 วินาที · นับเฉพาะการปฏิเสธของ Inngest ครบ 10 ครั้งเป็นข้อความตายพร้อมแจ้งเตือน

1. **key กันส่งซ้ำ** `CommandLog.idempotencyKey` = `<ประเภท>:<ความยาวของตัวตน>:<ตัวตน>:<key ของ adapter>` ประเภท: `u` สมาชิก · `sys` งานระบบ · `pa` PLATFORM_ADMIN · `ai` agent · `sup` ผู้ติดต่อของผู้ขาย · ความยาวนำหน้าทำให้ตัวตนหรือ key ที่มี `:` ไม่ชนกัน ผู้ส่งคนหนึ่งจึงจอง key ล่วงหน้าหรือรับผลที่เก็บไว้ของคนอื่นไม่ได้ · ฟอร์มเว็บสร้าง key (UUID) ตอนเปิดฟอร์มตาม §4.3 ข้อ 1 ใช้ซ้ำเมื่อส่งรายการเดิมอีกครั้ง และสร้างใหม่เมื่อได้คำตอบ (`src/ui/form/submission-key.ts`) · การนำเข้าไฟล์ใช้ hash ของไฟล์เป็น key
2. **การปฏิเสธ** การปฏิเสธที่ไม่มี audit event ไม่ถูกบันทึก ส่งใหม่จึงรันใหม่ · การปฏิเสธที่มี audit event ถูกบันทึกและตอบผลเดิมสำหรับ key นั้น (INV-PLT-01) · key เดิมกับ input ใหม่ได้ `IDEMPOTENCY_CONFLICT` (FR-PLT-012 AC2) · `execute()` รันใน savepoint การปฏิเสธจึงย้อนทุกอย่างที่เขียน รวม Event ที่ต่อเอง
3. **ส่งหลัง commit** ส่งครั้งเดียว ไม่ลองซ้ำบนเส้นทางของคำขอ: รอการส่งไม่เกิน 1.5 วินาที รวมไม่เกิน 2 วินาที · ส่งไม่ได้ → เก็บสาเหตุ (ตัดค่าลับออกแล้ว) ใน `lastError` และให้ข้อความถึงคิวอีกใน 30 วินาที · relay ไม่ใช้ `inngest.send()` แต่ POST `/e/<event key>` ครั้งเดียวด้วยค่าเดียวกับ SDK และ event key ไม่ปรากฏในข้อความ error
4. **ชนิดของความล้มเหลว** 400 406 409 412 413 422 = ปฏิเสธ · 401 403 404 429 และการเชื่อมต่อไม่ได้ (DNS ปฏิเสธ หมดเวลาเชื่อมต่อ TLS) = ใช้ไม่ได้ · 5xx ไม่มีคำตอบ หรือหลุดกลางทาง = ไม่แน่ใจ
5. **sweeper** cron ทุก 1 นาที ไม่มี step และไม่ให้ Inngest ลองซ้ำ (ทุกครั้งเป็น execution) · ชุดละ 100 · งบเวลา 40 วินาที · ส่งครั้งละไม่เกิน 10 วินาที · จองแถวด้วย lease 2 นาที (`FOR UPDATE SKIP LOCKED`) · ชุดที่ถูกปฏิเสธแบ่งครึ่งหาข้อความที่ผิด · ชุดที่ไม่แน่ใจแบ่งครึ่งเช่นกัน แต่ถ้า Inngest ยังไม่ตอบอะไรตั้งแต่ครั้งก่อน จะลองส่งข้อความเดียวเป็นตัวเทียบก่อน · ข้อความเดียวที่ไม่แน่ใจเป็น "ผู้ต้องสงสัย" นับเป็นการปฏิเสธเมื่อ Inngest ตอบอย่างอื่นได้ในรอบเดียวกัน · ใช้ไม่ได้หรือผู้ต้องสงสัยสองตัวติดกัน → หยุดรอบนั้นโดยไม่นับ
6. **ลองซ้ำและข้อความตาย** `Outbox.attempts` นับเฉพาะการปฏิเสธ · ครั้งถัดไป = ตอนนี้ + min(30 วินาที × 2^attempts, 30 นาที) · ครบ `OUTBOX_MAX_ATTEMPTS` = 10 → ตั้ง `deadAt` และ log `alert: true` ข้อความ `outbox message is dead` · ใช้ไม่ได้หรือไม่แน่ใจไม่นับและไม่ทำให้ตาย ลองใหม่ทุก 30 วินาที ทุกอย่างจึงออกภายใน 2 นาทีหลัง Inngest กลับมา (FR-PLT-012 AC3) · รอบที่ส่งอะไรไม่ออกและไม่ได้นับการปฏิเสธเลย ขณะที่ข้อความเก่าสุดรอเกิน 10 นาที → log `outbox is stalled` ทุกรอบจนกว่าจะขยับ
7. **ล็อกและเวลา** `lock_timeout` 3 วินาที · `statement_timeout` 15 วินาที · รอเปิดธุรกรรม 10 วินาที · ธุรกรรมยาวสุด 20 วินาที · pool 10 connection ต่อ process รอ connection 10 วินาที · หมดเวลาหรือรอ connection ไม่ได้ = "ไม่ว่าง" ลองซ้ำ 1 ครั้งแล้วตอบ `RATE_LIMITED` · serialization failure และ deadlock ลองซ้ำได้ 3 ครั้งแบบสุ่มช่วงห่าง
8. **error ที่ไม่คาดคิด** ตอบ `INTERNAL` พร้อม requestId อย่างเดียว · log มีแค่ชนิดของ error รหัสของ Prisma และ Postgres ชื่อตาราง คอลัมน์ constraint และ stack ไม่มีข้อความของ error หรือค่าที่ส่งมา (FR-PLT-008 AC3 · `src/server/errors/describe.ts`)
9. **`/api/inngest`** `maxDuration = 60` วินาที พอสำหรับ sweeper หนึ่งรอบ (งบ 40 วินาที + ส่งครั้งสุดท้าย 10 วินาที)
10. **`/api/health`** นับว่า inngest `fail` เมื่อข้อความที่ยังไม่เคยถูกปฏิเสธรอเกิน 5 นาที ข้อความที่ Inngest ปฏิเสธมีการแจ้งเตือนของตัวเองแล้ว ข้อความผิดข้อความเดียวจึงไม่ทำให้ทั้งระบบดูล่มหลายชั่วโมง

## ผลที่ตามมา

- คำสั่งของผู้ใช้ช้าลงไม่เกิน 2 วินาทีเมื่อ Inngest ล่ม แทนที่จะค้างนาน
- ข้อความที่ส่งไม่ได้มีทางจบเสมอ: ออกไปได้ หรือตายพร้อมแจ้งเตือน วิธีหาและส่งใหม่อยู่ใน [docs/runbooks/outbox.md](../runbooks/outbox.md)
- sweeper ใช้ 43,200 executions ต่อเดือน อยู่ในโควตาฟรีของ Inngest ([p0-07-inngest.md](../runbooks/p0-07-inngest.md))
- ความเสี่ยงที่เหลือ: คำสั่งซ้ำจำนวนมากที่รอ advisory lock ถือ connection ใน pool ระหว่างรอ (สูงสุด 3 วินาที × 2) องค์กรอื่นจึงอาจรอนานขึ้นแต่ไม่ล้ม · ถ้าเจอจริงให้เปลี่ยนเป็น `pg_try_advisory_xact_lock` แล้วตอบ `RATE_LIMITED` ทันที
