# ADR-042: ชุดตั้งต้นและการแก้ผังองค์กรทันที

- สถานะ: เสนอ
- วันที่: 2026-10-03
- ที่มา: ตัดสินระหว่างทำ S2-16 (FR-DOA-002 AC3 · FR-ADM-002 · FR-AUTH-002 AC3) · agent เสนอ ใช้ได้ทันทีเว้นแต่ผู้ใช้คัดค้าน

## บริบท

- BR-DOA-19 ให้ส่งชุดตั้งต้น (ผู้ดำรงตำแหน่งที่ DOA อ้าง + DOA ฉบับแรก) เป็นแพ็กเกจเดียวให้ผู้มีอำนาจลงนามตามสัญญาอนุมัติพร้อม step-up แต่ spec ไม่ได้ระบุว่าเก็บรายชื่อผู้ดำรงตำแหน่งของแพ็กเกจไว้ที่ไหน และเส้นทางอนุมัติอ้าง DOA ข้อใด ในเมื่อยังไม่มี DOA ที่มีผล (INV-DOA-01 ให้ทุกการตัดสินอ้างฉบับและข้อ)
- FR-ADM-002 AC2 ให้ตำแหน่งที่ DOA ไม่อ้างเปลี่ยนผู้ดำรงได้ทันที แต่ BR-DOA-13 ให้เอกสารที่ส่งแล้วใช้เส้นทางเดิมจนจบ ตำแหน่งที่ DOA ฉบับปัจจุบันไม่อ้างแล้วจึงยังอาจมีงานอนุมัติค้างอยู่
- BR-DOA-17 ให้การทำให้ตำแหน่งที่ DOA อ้างว่างเป็น warning ที่ต้องยืนยัน แต่ lint ของ BR-DOA-08 นับว่าง เฉพาะเมื่อไม่มีใครดำรงตำแหน่งนั้นเลยทั้งองค์กร
- §6.4 ไม่มีทางยกเลิกการเปลี่ยนที่ `SCHEDULED` แล้ว การย้ายแผนกสองรายการที่อนุมัติไว้ล่วงหน้าจึงอาจเกิดวงวนตอนมีผลโดยแก้ไม่ได้
- spec ไม่ได้ระบุว่าการย้าย cost center ไปแผนกอื่นเป็นการแก้พื้นฐานหรือไม่

## การตัดสินใจ

> ชุดตั้งต้นส่งเป็นฉบับ DOA หนึ่งฉบับกับการเปลี่ยนชนิด `POSITION_ASSIGN` บนเส้นทางเดียวกันที่อ้างฉบับนั้นเองกับข้อ `BR-DOA-19` · ตำแหน่งที่มีงานค้างนับว่ามีอำนาจ · การทำให้ตำแหน่งว่างต้องยืนยันรายตำแหน่ง · ย้ายแผนกได้ครั้งละหนึ่งรายการ · cost center ไม่ย้ายแผนกด้วยการแก้พื้นฐาน · DOA ฉบับใหม่เริ่มก่อนหรือพร้อมฉบับที่อนุมัติล่วงหน้าไว้แล้วไม่ได้

1. **ชุดตั้งต้น** (`src/server/services/doa/initial-package.ts`) ORG_ADMIN ส่งฉบับร่างพร้อมรายชื่อผู้ดำรงตำแหน่งด้วย `admin.doa.submitForPublish` ได้เฉพาะเมื่อองค์กรยังไม่มีฉบับที่รออนุมัติ มีผล หรือเคยมีผล (`NOT_INITIAL`) และมีผู้มีอำนาจลงนามที่ยืนยันแล้ว (`SIGNATORY_NOT_VERIFIED`)
   - ผู้ส่งเป็นผู้ลงนามไม่ได้ (BR-SOD-06 · OQ-31) และใส่ตัวเองในตำแหน่งไม่ได้ (BR-SOD-08)
   - ทุกตำแหน่งในรายชื่อต้องเป็นตำแหน่งที่ฉบับนั้นอ้าง (`POSITION_NOT_IN_DOA`) และทุกตำแหน่งที่ฉบับนั้นอ้างซึ่งมีผู้ดำรงอยู่แล้วต้องอยู่ในรายชื่อ (`UNLISTED_HOLDER`) จึงไม่มีใครถืออำนาจที่ผู้ลงนามไม่ได้อนุมัติ
   - lint ชุดเต็มรันกับผังองค์กรหลังใส่ผู้ดำรงตำแหน่งของแพ็กเกจ และ warning ต้องยืนยันทีละข้อเหมือนการส่งฉบับปกติ
   - เส้นทางมีขั้นเดียวไปผู้ลงนาม อ้าง `doaVersionId` = ฉบับที่อนุมัติเอง และ `ruleCode` = `BR-DOA-19` · เวลาตาม SLA ของข้อ `DOA_CHANGE` ในฉบับนั้น · ไม่ผ่านผู้รักษาการ
   - ผู้ดำรงตำแหน่งแต่ละคนเป็นแถว `OrgAuthorityChange` ชนิด `POSITION_ASSIGN` ที่ `routeId` เป็นเส้นทางเดียวกัน · อนุมัติแล้วเผยแพร่ฉบับและอนุมัติทุกแถว แถวที่วันมีผลยังไม่ถึงรอ job `org-authority-apply` · ปฏิเสธแล้วทุกแถวเป็น `REJECTED`
   - PLATFORM_ADMIN ไม่มีสิทธิ์อ่านหรือตัดสินแพ็กเกจ · การยืนยันผู้ลงนามโดย PLATFORM_ADMIN ยังไม่มีหน้าจอและ capability (NEW-15) ระหว่างนี้ seed ตั้งให้องค์กรตัวอย่าง
2. **ตำแหน่งที่มีอำนาจ** (`positionHasAuthority`) = ตำแหน่งที่ฉบับที่มีผล ฉบับที่จะมีผล หรือฉบับที่รออนุมัติอ้าง หรือมีงานอนุมัติค้างที่มาจากตำแหน่งนั้น · การแก้ทันที (`admin.orgStructure.editBasic`) ปฏิเสธตำแหน่งเหล่านี้ด้วย `FORBIDDEN` เหตุผล `USE_ORG_AUTHORITY_CHANGE` พร้อมชนิดที่ต้องเสนอ · การแก้ทันทีล็อกแถว Organization เหมือนการส่งชุดตั้งต้น จึงไม่แทรกระหว่างการส่ง
3. **ตำแหน่งว่าง** การเสนอ `POSITION_END` โดยไม่มีผู้แทนของตำแหน่งที่ฉบับ ณ วันมีผลอ้าง ต้องยืนยัน warning `POSITION_VACANT:<ตำแหน่ง>@<รหัสแผนก>` และ warning `DOA_LINT_VACANT_POSITION` ของข้อที่ไม่เหลือผู้ดำรงเลย · เมื่อมีผล ORG_ADMIN ได้รับแจ้ง `position.vacant` พร้อมจำนวนงานค้างที่ยังอยู่กับผู้ดำรงเดิม
4. **ย้ายแผนก** ปฏิเสธเมื่อแผนกแม่ใหม่คือตัวเองหรือแผนกใต้ตัวเอง (`CYCLE`) หรืออยู่ใต้แม่เดิมแล้ว (`NO_CHANGE`) · มีการย้ายที่รออนุมัติหรือรอมีผลได้ครั้งละหนึ่งรายการต่อองค์กร (`REPARENT_WAITING`) trigger `Department_no_cycle` ในฐานข้อมูลยังเป็นด่านสุดท้าย
5. **cost center** การแก้พื้นฐานสร้าง แก้ชื่อ และเปิดปิดได้ แต่ไม่ย้ายแผนก เพราะเมื่อมีงบ (S3) แผนกของ cost center อาจกำหนดผู้อนุมัติ · event `cost_center.created` `cost_center.updated` (NEW-14)
6. **รีเซ็ต 2FA** ของสมาชิกที่ดำรงตำแหน่งที่ DOA อ้าง ถูกระบุเป็นผู้อนุมัติ หรือมีงานค้าง ถูกปฏิเสธด้วย `USE_ORG_AUTHORITY_CHANGE` ชนิด `IDENTITY_RESET` (BR-AUTH-07) · เมื่อ `IDENTITY_RESET` มีผล บันทึก `auth.2fa_reset` ที่อ้างการเปลี่ยน และส่งอีเมล `security.notice` ถึงเจ้าของบัญชีเหมือนการรีเซ็ตปกติ
7. **ลำดับของฉบับ DOA** ฉบับที่ส่งหรืออนุมัติต้องเริ่มหลังทุกฉบับของรหัสเดียวกันที่เผยแพร่แล้ว ถ้ามีฉบับที่อนุมัติไว้สำหรับเวลาเดียวกันหรือหลังกว่า ปฏิเสธด้วย `VALIDATION_FAILED` เหตุผล `LATER_VERSION_SCHEDULED` ทั้งตอนส่งและตอนอนุมัติ (ใช้เวลามีผลจริงหลังเลื่อนตาม BR-DOA-12) · ฉบับนั้นต้องถอนก่อน (BR-DOA-18 ใน S6) · ถ้าไม่ตรวจ การอนุมัติจะชน CHECK `doa_version_period` หรือ `doa_no_overlap` แล้วล้มเป็น error ที่ไม่คาดคิด

## ผลที่ตามมา

- ไม่ต้องเพิ่มตารางหรือ migration สำหรับแพ็กเกจ · ประวัติของผู้ดำรงตำแหน่งชุดแรกอยู่ในที่เดียวกับการเปลี่ยนครั้งต่อ ๆ ไป
- ไทม์ไลน์ของการอนุมัติชุดตั้งต้นแสดง "ฉบับ 1 ข้อ BR-DOA-19" ซึ่งบอกว่าอำนาจมาจากสัญญา ไม่ใช่จาก DOA
- การย้ายแผนกหลายรายการต้องทำทีละรายการ (เกิดไม่บ่อย)
- เทสต์: `tests/integration/initial-package.test.ts` `tests/integration/org-structure.test.ts` `tests/integration/org-authority.test.ts` `tests/integration/doa-versions.test.ts` `tests/generated/authority-writes.test.ts`

## ส่วนเพิ่ม (2026-10-03 · NEW-28 จากการรีวิวหน้าจอ S2-13)

- ข้อ 3 เพิ่ม: งานค้างที่ยังอยู่กับผู้ดำรงเดิมหลังตำแหน่งว่าง ย้ายไปผู้ดำรงคนถัดไปเมื่อการแต่งตั้งมีผล ทุกงานที่ `resolvedFrom` ตรงตำแหน่ง ไม่ว่าใครถืออยู่ (ผู้ดำรงเดิม ผู้รักษาการ) ยกเว้นงานที่ผู้ดำรงคนใหม่ถือในชื่อตัวเองอยู่แล้ว · งานที่รอผู้ขอตอบย้ายพร้อมสถานะ เวลาที่เหลือ และคำถามที่ยังไม่ตอบ
- `OrgAuthorityChange.impactSummary` มี `openTasks` (งานที่ย้ายไปผู้ดำรงใหม่) และ `openTasksStay` (งานที่ยังอยู่เพราะตำแหน่งว่าง)
- preview ของการเปลี่ยนโครงสร้างอำนาจที่ขัด BR-SOD-08 บันทึก `security.sod_blocked` (action `org_authority.preview`) ผ่านคำสั่งตรวจอย่างเดียว `org_authority.preview_sod_blocked` ด้วย idempotency key ของฟอร์ม หนึ่งครั้งต่อการกด
- ยังรอผู้ใช้ตัดสิน: ระหว่างตำแหน่งว่าง ผู้ดำรงเดิมยังตัดสินงานที่ค้างอยู่ได้จนกว่าจะมีผู้ดำรงใหม่หรือ ORG_ADMIN ย้ายงาน

## ส่วนเพิ่ม (2026-10-04 · ฝั่งผู้อนุมัติของ FR-DOA-009 AC3 จาก S3-09)

- ข้อ 7 เพิ่ม: เผยแพร่ฉบับที่อนุมัติแล้วจะจบเฉพาะฉบับ PUBLISHED ของรหัสเดียวกันที่ช่วงมีผลยาวเลยวันเริ่มของฉบับใหม่ (`effectiveTo` ว่างหรือหลังกว่า) ฉบับที่จบก่อนหรือตรงวันเริ่มอยู่แล้วคงวันจบเดิม จึงไม่ชน `doa_no_overlap`
- การติ๊กตารางผลที่ขอบของผู้อนุมัติผูกกับฉบับที่ตารางใช้เทียบ (`boundaryBaselineId` เป็น uuid หรือ null สำหรับฉบับแรก) · ถ้าตอนอนุมัติฉบับที่ใช้เทียบไม่ใช่ `comparisonBaselineId` แล้ว ปฏิเสธ `VALIDATION_FAILED` เหตุผล `BOUNDARY_TABLE_CHANGED` ก่อนใช้ step-up · ไม่ติ๊กเลยปฏิเสธ `BOUNDARY_NOT_CONFIRMED` · ทุกช่องทาง (หน้า LIFF ต้องส่งค่าเดียวกัน NEW-41)
- `approval_task.decided` บันทึก `boundaryTableConfirmed: true` เฉพาะฉบับที่มีตารางผลที่ขอบ
- ลิงก์ทดลองเส้นทาง (`admin.doa.simulate`) แสดงในหน้าตัดสินเฉพาะผู้ที่มีสิทธิ์นั้น ผู้อนุมัติ DOA ที่ไม่มีสิทธิ์ (เช่น CEO) จึงไม่เจอหน้าปฏิเสธ
- ยังรอผู้ใช้ตัดสิน: ควรให้ผู้อนุมัติฉบับ DOA ทดลองเส้นทางของฉบับที่รอตนอนุมัติได้หรือไม่ (เป็นการเพิ่มสิทธิ์ ตอนนี้มีเฉพาะ ORG_ADMIN)
