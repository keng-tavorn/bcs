# ADR-043: ลิงก์ตัดสินทางอีเมล การส่งการแจ้งเตือนทางอีเมล และการส่ง PO ให้ผู้ขาย

- สถานะ: เสนอ
- วันที่: 2026-10-03
- ที่มา: ตัดสินระหว่าง S4-06 (FR-P2P-005 · FR-NOTI-002 · §4.9) · agent เสนอ ใช้ได้ทันทีเว้นแต่ผู้ใช้คัดค้าน

## บริบท

- §4.9 กำหนดว่า ActionToken สร้างตอนมอบงาน เพิกถอนทันทีเมื่องานปิดหรือย้ายผู้รับ (BR-TOK-01) และลิงก์อีเมลเก็บเฉพาะ sha256 ของ secret (BR-TOK-03) แต่อีเมลออกจาก job ส่งการแจ้งเตือนภายหลัง จึงต้องมีวิธีให้ job รู้ secret โดยไม่เก็บ secret ไว้ในฐานข้อมูล
- งานถูกมอบและปิดจากหลายคำสั่ง (เส้นทางใหม่ ขั้นถัดไป ตัดสิน ยกเลิกเส้นทาง ย้ายงานเมื่อโครงสร้างอำนาจเปลี่ยน) การใส่โค้ด token ทุกจุดมีโอกาสลืม
- BR-TOK-05 ห้ามอนุมัติยอดสูงจากปุ่มในแชท แต่ spec ไม่ได้พูดถึงลิงก์อีเมล และ step-up ด้วย PIN (FR-AUTH-005) มาใน S5
- §6.4 ให้ `po.send` พา PO จาก APPROVED ไป SENT พร้อมส่งอีเมล แต่ FR-P2P-005 AC2 ให้ PO คงเป็น APPROVED เมื่ออีเมลตีกลับ และผู้ให้บริการอีเมลยังไม่ได้เลือก (ADR-031) e2e ไม่ส่ง outbox เข้า Inngest

## การตัดสินใจ

1. **วงจรของ token ตาม event ของงาน** `runCommand` เรียก `applyTokenLifecycle` ในธุรกรรมเดียวกับ event: `approval_task.assigned` และ `approval_task.reassigned` สร้าง token ช่องทาง EMAIL ให้ผู้รับใหม่ (อนุญาต APPROVE REJECT · อายุ 72 ชั่วโมง) · `approval_task.decided` `approval_task.cancelled` และงานต้นทางของ `approval_task.reassigned` เพิกถอน token ที่ยังไม่ใช้ · ปิดใช้งาน member เพิกถอน token ทั้งหมดของคนนั้น (`registerDeactivationRevoker`) · token ของ LINE เพิ่มที่จุดเดียวกันใน S5
2. **secret ของลิงก์** secret = HMAC-SHA256(`BETTER_AUTH_SECRET`, `bcs/action-token/email/v1/` + tokenId) แบบ base64url · ฐานข้อมูลเก็บ sha256 ของ secret เท่านั้น job ส่งอีเมลคำนวณ secret ใหม่ได้เอง ฐานข้อมูลที่รั่วอย่างเดียวจึงเปิดลิงก์ไม่ได้ · เปลี่ยน `BETTER_AUTH_SECRET` ทำให้ลิงก์ที่ค้างอยู่ใช้ไม่ได้ (เหมือน session)
3. **การตัดสินจากลิงก์** GET แสดงอย่างเดียว · ค่าเริ่มต้นต้อง login ก่อน (`email.actionLinksRequireLogin`) หน้า login พากลับมาที่ลิงก์ได้เฉพาะ path ของเว็บนี้ · POST เป็น server action ที่ตรวจค่า CSRF (HMAC ผูกกับ session หรือกับลิงก์เมื่อองค์กรไม่บังคับ login) · ใช้ token ด้วย update แบบมีเงื่อนไขในธุรกรรมเดียวกับการตัดสิน (BR-TOK-04 · ใช้ `ctx.now` แทน `now()` ของฐาน) การตัดสินที่ถูกปฏิเสธจึงไม่กิน token · คนอื่นใช้ลิงก์ → `TOKEN_INVALID` และเก็บ `security.token_misuse` · งานนโยบาย (DOA ORG_AUTHORITY_CHANGE) และงานที่ยอดตามฐาน DOA ≥ `stepUpThreshold` ตัดสินจากลิงก์ไม่ได้ ได้ `STEP_UP_REQUIRED` และหน้าลิงก์พาไปตัดสินในระบบแทน (ใช้กติกาเดียวกับ BR-TOK-05 เพราะเป็นทางเลือกที่ปลอดภัยกว่า จนกว่า PIN ของ S5 จะมา)
4. **ส่งการแจ้งเตือนแบบ IMMEDIATE** job `notification-deliver` รับ `bcs/notification.requested` · จองแถวก่อนด้วย `sentChannel` ที่ยังว่าง ทำซ้ำจึงส่งครั้งเดียว · ก่อน S5 ส่งทางอีเมลทุกฉบับ อีเมลของ `task.assigned` มีลิงก์ตัดสินคู่กับลิงก์เข้าระบบ · ผู้ให้บริการปฏิเสธถาวร → `FAILED` พร้อมรหัส · ติดต่อไม่ได้ → ปล่อยแถวคืนแล้วให้ Inngest ลองใหม่ · สถานะการส่งเป็นข้อมูลการส่งของแถว Notification เหมือนของ outbox ไม่ใช่ event ทางธุรกิจ
5. **การส่ง PO** ส่งอีเมลภายในคำสั่ง `po.send` หลังล็อกแถว PO คนกดพร้อมกันจึงส่งครั้งเดียว · ไม่ลองธุรกรรมซ้ำ (`maxRetries: 0`) การลองซ้ำจึงไม่ส่งสองครั้ง · SMTP รอเชื่อมต่อไม่เกิน 5 วินาทีและรอคำตอบไม่เกิน 10 วินาที อยู่ในเวลาธุรกรรม 20 วินาที · ผู้ให้บริการตอบปฏิเสธถาวร (5xx) = ตีกลับ: สถานะเดิม บันทึก `sendBouncedAt` `sendBounceReason` event `po.send_bounced` (NEW-25) และแจ้ง PROCUREMENT · ติดต่อไม่ได้ = `EXTERNAL_SERVICE_ERROR` ไม่มีอะไรเปลี่ยน · ส่งทุกครั้งหลังครั้งแรก (รวมหลังตีกลับ) ต้องมีเหตุผลและมี event ทุกครั้ง · ส่งซ้ำได้ขณะ SENT หรือ PARTIALLY_RECEIVED · ไฟล์ PDF ของทุกครั้งเก็บเป็น FileLink `PO_PDF` · อีเมลตีกลับภายหลังผ่าน webhook ของผู้ให้บริการรอ ADR-031
6. **รหัสความล้มเหลวของอีเมล** adapter แปลง error เป็น `EmailSendError` ที่มีแค่ `permanent` กับรหัสสั้น (`SMTP_550` `ECONNECTION`) ไม่เก็บข้อความของผู้ให้บริการเพราะอาจมีที่อยู่อีเมล (NFR-SEC-09)

## ผลที่ตามมา

- งานทุกงานมี token ตั้งแต่มอบ ไม่ว่ามอบจากคำสั่งไหน และ token ตายพร้อมงาน
- ถ้าธุรกรรมของ `po.send` ล้มหลังอีเมลออกไปแล้ว (เช่น ฐานข้อมูลหลุดตอน commit) ผู้ขายอาจได้อีเมลแต่ PO ยังเป็น APPROVED การกดส่งอีกครั้งต้องใส่เหตุผล ผู้ขายจึงอาจได้ PO เลขเดิมสองฉบับ
- ผู้อนุมัติยอดสูงต้องเข้าระบบเพื่อตัดสิน แม้มาจากอีเมล
