# ADR-047: PIN ยืนยันธุรกรรมและ step-up

- สถานะ: เสนอ (ข้อ 5 และข้อ 6 รอผู้ใช้ยืนยัน)
- วันที่: 2026-10-04
- ที่มา: S5-05 (FR-AUTH-005 · BR-TOK-05) · docs/sub-specs/S5.md แถว "PIN" และ "step-up" · agent เสนอ ใช้ได้ทันทีเว้นแต่ผู้ใช้คัดค้าน

## บริบท

- FR-AUTH-005: ตัดสินงานที่ยอดตั้งแต่ `stepUpThreshold` และงานเชิงนโยบายต้องยืนยันด้วย PIN 6 หลัก ผิด 5 ครั้งล็อก 15 นาที
- ตั้งแต่ S2-16 step-up ใช้รหัส TOTP เป็นการชั่วคราว (ADR-042) และ S5-05 เปลี่ยนเป็น PIN

## การตัดสินใจ

1. **เก็บ PIN** ด้วย argon2id ของ `node:crypto` (m = 19 MiB, t = 2, p = 1, salt 16 ไบต์, tag 32 ไบต์) พร้อม pepper จาก `ENCRYPTION_KEY` ผ่าน HMAC context `bcs/transaction-pin/argon2-secret/v1` และ keyid ใน PHC string · หมุน `ENCRYPTION_KEY` โดยไม่เก็บ key เดิมทำให้ทุกคนต้องตั้ง PIN ใหม่
2. **กฎของ PIN** ตรวจใน `src/core/pin` (บริสุทธิ์): 6 หลัก ห้ามเลขเดียวกันทั้งชุด ห้ามเลขเรียงขึ้นหรือลง ห้ามเลขยอดนิยมในรายการ
3. **ตั้งหรือเปลี่ยน PIN** ต้องยืนยันตัวตนด้วยรหัสผ่านหรือ TOTP ก่อน ได้หลักฐาน `proofToken` (HMAC ด้วย `BETTER_AUTH_SECRET` อายุ 5 นาทีบนนาฬิกาความปลอดภัย nonce 128 บิต ผูกกับ hash ของ PIN ปัจจุบันจึงใช้ได้ครั้งเดียว) · รหัสผ่านหรือ TOTP ที่ผิดนับรวมในการล็อกการเข้าระบบ · logger ลบ `proofToken` ทั้งเป็น key และในข้อความ
4. **การล็อก** ผิด 5 ครั้งติดกัน (ไม่มีช่วงเวลา) ล็อก 15 นาที · แต่ละครั้งถูกนับและ commit ก่อนตรวจ PIN แล้วจึงตรวจและสรุปผล ครั้งที่ 5 ล็อกทันทีก่อนตรวจ · ถ้าการสรุปผลล้ม การล็อกยังอยู่ (ขาดได้แค่ event และอีเมล) จึงไม่มีทางที่การล็อกเปิดเอง · ล็อกแล้วบันทึก `security.pin_locked` และส่งอีเมล `security.notice` ถึงเจ้าของบัญชีทางอีเมลเท่านั้น (§10.1)
5. **ตั้ง PIN ใหม่หลังยืนยันตัวตนใหม่ ปลดล็อก 15 นาทีที่กำลังมีผล** — รอผู้ใช้ยืนยัน
6. **การล็อกซ้ำไม่เพิ่มระดับ** คนที่ถือ session ได้ลอง 5 ครั้งทุก 15 นาที (ราว 480 ครั้งต่อวัน) และเจ้าของได้อีเมลทุกครั้งที่ล็อก · ทางเลือกที่เพิ่มได้: ล็อกครบ N ครั้งในหนึ่งวันต้องตั้ง PIN ใหม่ด้วยรหัสผ่าน — รอผู้ใช้ยืนยัน
7. **step-up หนึ่งครั้งต่อเอกสารหนึ่งฉบับ** grant ใหม่ใช้ grant เก่าที่ยังไม่ใช้ของสมาชิกและเอกสารเดียวกันทิ้ง · purpose `DECIDE` · อายุ 5 นาที ใช้ได้ครั้งเดียว
8. **ทุกคำสั่งตัดสินต้องระบุวิธีที่รับ** คำขอ PO และผลต่างการตรวจรับรับเฉพาะ PIN (`PIN_ONLY`) สำหรับ **ทุกการตัดสิน** (อนุมัติ ตีกลับ ไม่อนุมัติ) ของงานที่ยอดตั้งแต่ `stepUpThreshold` ตามคำว่า "ตัดสินงาน" ใน FR-AUTH-005 AC2 · งานเชิงนโยบายรับเฉพาะ PIN ทุกช่องทางเมื่อหน้าเว็บเปลี่ยนเป็น PIN (TOTP ใช้ step-up ไม่ได้อีก มีเทสต์ยืนยัน)
9. **seed** ให้ PIN จาก `SEED_DEV_PIN` (ไม่บังคับ ใช้ได้เฉพาะ local และ staging) แก่สมาชิกตัวอย่างทุกคนที่ดำรงตำแหน่งที่ DOA อ้าง คนที่มี PIN แล้วคง PIN เดิม · ไม่มีค่า = ผู้อนุมัติตั้งเองตอนใช้ครั้งแรก
10. `security.pin_locked` อยู่ใน `src/server/events/schemas/auth.ts` ใต้ aggregate Security

## ผลที่ตามมา

- ลิงก์อีเมลของงานที่ต้อง step-up ยังพาไปตัดสินใน workspace ตาม ADR-043
- e2e และฉาก demo ใช้ PIN ของ seed · ผู้ใช้ที่ลืม PIN ตั้งใหม่ได้เองที่ `/settings/pin` หลังยืนยันรหัสผ่าน

## ส่วนเพิ่ม (2026-10-04 · หลังสลับใน S5-05 และหน้า LIFF ของ S5-06)

- ข้อ 8 ทำแล้ว: `grantStepUp` รับเฉพาะ PIN · grant ของ TOTP ที่มีอยู่ไม่นับ ทั้งงานคำขอ PO ผลต่างการตรวจรับ และงานเชิงนโยบาย บนเว็บและ LIFF (tests/integration/step-up-decisions.test.ts step-up-pin.test.ts) · **passkey ยังไม่ทำ** PIN เป็นหลักฐาน step-up อย่างเดียวใน demo (FR-AUTH-005 AC2 ให้ passkey เป็นทางเลือก "ถ้าอุปกรณ์รองรับ" · NEW-53) — รอผู้ใช้ยืนยัน
- ข้อ 9 แก้: ไม่มี `SEED_DEV_PIN` = seed ไม่ให้ PIN ใคร ผู้อนุมัติตั้งเองตอนใช้ครั้งแรกที่ `/settings/pin` · ประวัติ demo ยืนยันด้วย PIN ใช้ครั้งเดียวแบบสุ่ม (ไม่พิมพ์ ไม่บันทึก `auth.pin_set`) ที่ให้ผู้อนุมัติที่ยังไม่มี PIN ระหว่างสร้างประวัติแล้วเอาคืนก่อน seed จบ เป็นข้อยกเว้นเฉพาะ seed ของ local และ staging · มีค่า: รายงานของ seed บอกรหัสพนักงานของผู้อนุมัติที่ไม่ได้ถือ PIN นี้ — รอผู้ใช้ยืนยันข้อยกเว้นนี้
- ข้อ 11 ใหม่ (NFR-SEC-04): หลังใส่ PIN ถูก token ของ session เปลี่ยนทันทีด้วย update แบบมีเงื่อนไขบนแถวเดิม เวลาเข้าระบบและอายุสูงสุดคงเดิม token เก่าใช้ไม่ได้ทันที ทั้ง session เว็บและ session ที่เปิดจาก LIFF ID token (token LIFF ใหม่ขึ้นต้น `liff_`) · action อ่าน session ตอนเริ่มก่อนตรวจ PIN action ที่ไม่พบ session ตอนเริ่มไม่ตรวจ PIN ไม่นับครั้งผิด และไม่ให้ step-up · หน้าที่ server action render ใหม่อ่าน cookie จาก `cookies()` (`src/app/_lib/session.ts` `held-cookies.ts`)
- ข้อ 12 ใหม่ (NFR-SEC-09): ฟอร์มที่มีช่อง PIN รหัสผ่าน หรือรหัส 2FA ใช้ `method="post"` และช่องกับปุ่มส่งรอจนสคริปต์ของหน้าทำงาน (`useHydrated` ใน `src/ui/form/hydrated.ts`) ค่าที่พิมพ์จึงไม่ไปอยู่ในที่อยู่ของหน้า ประวัติเบราว์เซอร์ log หรือ Referer แม้หน้าโหลดช้า (NEW-54)
- ผู้รักษาการใช้ PIN ของตัวเอง ไม่ใช่ของผู้มอบ · seed ให้ PIN เฉพาะผู้ดำรงตำแหน่งที่ DOA อ้าง ผู้รักษาการจึงตั้ง PIN เองก่อน — รอผู้ใช้ยืนยัน
