# ADR-055: seed ครั้งแรกของ staging รันเป็นงาน Inngest บน Vercel และ build ตรวจ role ของแอป

- สถานะ: เสนอ
- วันที่: 2026-10-07
- ที่มา: deploy staging ครั้งแรก (P0-08 ขั้น B6) · agent เสนอ ใช้ได้ทันทีเว้นแต่ผู้ใช้คัดค้าน · การ migrate และ seed ครั้งแรกบน staging ผู้ใช้อนุมัติแล้ว (ADR-038 ข้อ 14)

## บริบท

- คู่มือ p0-08 ขั้น B6 ให้ agent seed staging ครั้งแรก และตรวจว่าแอปบน staging ต่อฐานข้อมูลด้วย role `bcs_app` แต่ค่า `DATABASE_URL` และ `DIRECT_URL` ใน Vercel เป็นชนิด Secret ซึ่งไม่มีใครเปิดดูหรือดึงลงเครื่องได้ (`vercel env pull` ได้ค่าว่าง) จึงมีแค่โค้ดที่รันบน Vercel ที่ต่อฐานข้อมูล staging ได้
- deploy ครั้งแรก (2026-10-07) พบว่า build ของ Vercel รันที่ Washington (`iad1`) ส่วนฐานข้อมูลอยู่สิงคโปร์ ทุกคำสั่ง SQL ใช้เวลาไปกลับราว 0.22 วินาที
- seed ทั้งหมดใช้ราว 7,700 คำสั่ง (วัดบนเครื่อง 2026-10-07) ส่วนฐานราว 460 คำสั่ง ที่เหลือคือประวัติ demo ซึ่งสร้างผ่าน service จริง และ command หนึ่งตัวรันในธุรกรรมที่มีเวลาไม่เกิน 20 วินาที (`COMMAND_TX_TIMEOUT_MS`) ถ้ารันจาก build ทั้ง seed จะใช้ราว 30 นาที และ command ที่มีคำสั่งเกินราว 90 คำสั่งจะหมดเวลากลางทาง ประวัติ demo ที่สร้างไม่ครบจะทำให้ seed รอบต่อไปหยุด (`DemoHistoryIncompleteError`) แก้ได้ด้วยการล้าง staging ซึ่งต้องขอผู้ใช้ทุกครั้ง
- function ของแอปรันที่สิงคโปร์ (`sin1` · ADR-032) ใกล้ฐานข้อมูล

## การตัดสินใจ

> (agent เสนอ 2026-10-07) seed ครั้งแรกของ staging รันเป็นงาน Inngest `staging-first-seed` บน Vercel สิงคโปร์ ผู้ดูแลกดเริ่มเองจากหน้า Inngest · build ของ Vercel ตรวจ role ของแอปทุกครั้งหลัง migrate

1. งาน `staging-first-seed` (`src/server/jobs/staging-first-seed.ts`) ใช้ seed ชุดเดียวกับ `pnpm db:seed` (`src/server/services/demo-seed`) แบ่งเป็น step `check` `base` และ `history` · Inngest อาจรันหลาย step ในการเรียก `/api/inngest` ครั้งเดียว (checkpointing ของ SDK 4.21) แต่ละการเรียกมีเวลาไม่เกิน `maxDuration` 300 วินาที (Fluid compute ของ project เปิดอยู่)
2. ลงทะเบียนเฉพาะเมื่อ `APP_ENV=staging` และเริ่มด้วย event `bcs/staging.first_seed_requested` เท่านั้น คือผู้ดูแลกด Invoke ในหน้า Inngest ไม่มี endpoint ใหม่ที่คนนอกเรียกได้ (Inngest เรียก `/api/inngest` ด้วยลายเซ็นของ `INNGEST_SIGNING_KEY`) · `retries: 0` และ `concurrency` 1 (Inngest จำกัดที่จำนวน step ที่รันพร้อมกัน)
3. seed เฉพาะฐานข้อมูลที่ยังไม่มีองค์กรเลย หรือฐานที่มีแค่องค์กร demo ของไฟล์ input ซึ่งยังไม่มีประวัติ demo และยังไม่มีคำขอ (seed รอบก่อนที่หยุดก่อนสร้างประวัติ ส่วนฐานรันซ้ำได้โดยไม่ซ้ำ) ถ้าไม่ใช่สองแบบนี้งานจบโดยไม่แตะข้อมูล (`NOT_EMPTY`) · ถ้า `APP_ENV` ไม่ใช่ staging หรือไม่มี `SEED_DEV_PASSWORD` ก็ไม่ seed · step `check` อ่านไฟล์ input และตรวจที่เก็บไฟล์ก่อนเขียนอะไร เหตุที่ล้มบ่อยที่สุดจึงหยุดตอนฐานยังว่าง · การล้างแล้ว seed ใหม่บน staging เป็นเรื่องของ NEW-70 (spec §17.4)
4. ไฟล์ที่ seed อ่าน (`docs/inputs/BCS_inputs_v1_demo.xlsx` และ `prisma/seed/*.yaml`) อ่านจาก root ของโปรเจกต์ และ `next.config.ts` ใส่ไว้ใน function `/api/inngest` (`outputFileTracingIncludes`)
5. `vercel.json` สั่ง `pnpm db:migrate && pnpm db:check-role && pnpm build` · `db:check-role` (`scripts/check-runtime-role.ts`) ต่อด้วย `DATABASE_URL` แบบเดียวกับแอป แล้วหยุด build ถ้า role ไม่ใช่ `bcs_app` เป็น superuser เป็นสมาชิก `neon_superuser` หรือมีสิทธิ์ UPDATE DELETE TRUNCATE บนตาราง append-only (FR-PLT-006 AC3 · spec §6.3 · INV-EVT-01) · ถ้า `APP_ENV=local` ข้าม เพราะ `pnpm verify` ตรวจฐานบนเครื่องแล้ว

## ผลที่ตามมา

- ผู้ใช้ทำเพิ่ม 1 ขั้น: หลัง agent sync แอปกับ Inngest แล้วกด Invoke ที่ `staging-first-seed` ครั้งเดียว ([p0-07-inngest.md](../runbooks/p0-07-inngest.md) ส่วนที่ 3) · ผลของแต่ละ step ดูได้ในหน้า Runs ของ Inngest
- build ทุกครั้งของ staging (และ production ในอนาคต) ตรวจ role ของแอปเอง ไม่ต้องรอให้คนตรวจ · ข้อความใน log บอกแค่ชื่อ role และสิทธิ์ ไม่มี host หรือรหัสผ่าน (NFR-SEC-09)
- `/api/inngest` ให้เวลาต่อครั้งได้ถึง 300 วินาที (เดิม 60) เป็นเพดานเท่านั้น งานอื่นยังจบเร็วเท่าเดิม
- คู่มือ `docs/DEMO_RUNBOOK.md` ที่บอกให้ดึงค่า staging ด้วย `vercel env pull` ใช้กับค่าชนิด Secret ไม่ได้ จึงแก้ให้บอกว่ายังใช้ไม่ได้ และวิธี reset staging ที่ใช้ได้รอผู้ใช้ตัดสิน (NEW-70)
- ข้อจำกัดที่รู้: ระหว่าง step `history` ประวัติ demo เปลี่ยนตัวส่งอีเมลของทั้ง process เป็นตัวที่ไม่ส่งจริง (`setEmailProvider` · `src/server/services/demo-history`) งานอื่นที่ Vercel ส่งเข้า instance เดียวกันในช่วงนั้นจึงอาจไม่ได้ส่งอีเมลจริง โอกาสต่ำมากเพราะเกิดครั้งเดียวกับ staging ที่ยังไม่มีคนใช้ ถ้าจะใช้ seed แบบนี้ซ้ำ ควรส่งตัวส่งอีเมลผ่าน context แทน
- ถ้าภายหลัง build ของ Vercel รันใกล้ฐานข้อมูลได้ หรือมีวิธีอื่นที่ปลอดภัยกว่า ทบทวน ADR นี้ได้
