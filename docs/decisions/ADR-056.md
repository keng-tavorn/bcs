# ADR-056: reset staging ก่อน demo ด้วยปุ่มใน Inngest ที่ต้องพิมพ์ยืนยัน

- สถานะ: ตัดสินแล้ว (ผู้ใช้ 2026-10-07)
- วันที่: 2026-10-07
- ที่มา: NEW-70 · D-07 · ผู้ใช้เลือกทางเลือก (ก) "ปุ่มใน Inngest ต้องพิมพ์ยืนยัน DEMO-<วันที่> ก่อนล้าง" · รายละเอียดการทำเป็นของ agent

## บริบท

- D-07 เสร็จเมื่อคำสั่ง reset ใน `docs/DEMO_RUNBOOK.md` รันบน staging แล้วข้อมูลกลับเป็นสถานะก่อน demo
- คำสั่งเดิม `pnpm demo:reset --env=.env.staging --confirm=DEMO-<วันที่>` ต้องมีค่าของ staging ครบในเครื่อง แต่ค่าชนิด Secret ใน Vercel ดึงลงเครื่องไม่ได้ (`vercel env pull` ได้ค่าว่าง) และ `ENCRYPTION_KEY` ต้องตรงกับของ staging
- seed ต้องรันใกล้ฐานข้อมูล เพราะ build ของ Vercel รันที่ Washington (ADR-055)
- การล้าง staging ต้องให้ผู้ใช้อนุมัติทุกครั้ง (spec §17.4 · ADR-038 ข้อ 14)

## การตัดสินใจ

> (ผู้ใช้ตัดสิน 2026-10-07) ล้างข้อมูล staging ก่อน demo ด้วยปุ่มใน Inngest ต้องพิมพ์ยืนยัน DEMO-<วันที่> ก่อนล้าง

1. งาน Inngest `staging-demo-reset` (`src/server/jobs/staging-demo-reset.ts`) ลงทะเบียนเฉพาะเมื่อ `APP_ENV=staging` เริ่มด้วย event `bcs/staging.demo_reset_requested` คือผู้ดูแลกด Invoke ในหน้า Inngest พร้อมข้อมูล `{"confirm": "<รหัสองค์กร demo>-<วันที่วันนี้ตามเวลาไทย>"}` เช่น `{"confirm": "DEMO-2026-10-20"}` · คำยืนยันเหมือนของ `pnpm demo:reset` บนเครื่อง และการพิมพ์คำยืนยันของวันนี้คือการอนุมัติครั้งนั้น
2. step `check` ไม่แตะข้อมูล: ปฏิเสธถ้าไม่ใช่ staging ไม่มี `SEED_DEV_PASSWORD` คำยืนยันไม่ตรงกับวันนี้ (บอกคำที่ต้องพิมพ์) หรือมีองค์กรอื่นนอกจากองค์กร demo ของไฟล์ input (staging มีแต่ข้อมูลตัวอย่างจนกว่า OQ-19 ปิด องค์กรอื่นจึงเป็นของใครบางคน) · แล้วอ่านไฟล์ input และตรวจที่เก็บไฟล์ก่อนล้าง
3. step `wipe` ล้างทุกตารางใน schema `public` ยกเว้น `_prisma_migrations` ด้วยคำสั่ง `TRUNCATE ... RESTART IDENTITY CASCADE` เดียว ผ่าน role migrator (`DIRECT_URL` · `src/server/db/sql/staging-wipe.ts`) โครงสร้างตารางยังเป็นตาม migration ล่าสุด จึงไม่ต้องรัน `prisma migrate` ใน function · TRUNCATE ไม่เรียก trigger รายแถวที่กันการแก้ตาราง append-only ซึ่ง migration แรกบันทึกไว้ว่ามีแค่ migrator ที่ทำได้
4. step `base` และ `history` ใช้ seed ชุดเดียวกับ `pnpm db:seed` และงาน `staging-first-seed` (ADR-055)
5. งานนี้กับ `staging-first-seed` ใช้ concurrency group เดียวกันทั้ง environment (`scope: env` · key `"staging-demo-data"`) จึงไม่เขียนข้อมูล demo พร้อมกัน · `retries: 0`

## ผลที่ตามมา

- reset staging ทำได้จากหน้าเว็บของ Inngest ไม่ต้องมีค่าลับในเครื่อง ([DEMO_RUNBOOK.md](../DEMO_RUNBOOK.md) ข้อ 2)
- ถ้า run หยุดหลัง `wipe` กด Invoke ซ้ำด้วยคำยืนยันเดิมในวันเดียวกันได้ เพราะล้างฐานที่ว่างแล้วไม่เปลี่ยนอะไร หรือใช้ `staging-first-seed` ซึ่ง seed ฐานว่างได้
- ไฟล์ใน bucket ของ demo รอบก่อน (ใบเสนอราคาและ PDF) ยังอยู่โดยไม่มีแถวในฐานอ้าง แบบเดียวกับ `pnpm demo:reset` บนเครื่อง ไม่กระทบ demo
- งาน Inngest ที่รออยู่จากข้อมูลเดิม (เช่นตัวจับเวลา SLA) จะพบว่างานนั้นไม่มีแล้วและจบเอง (`NOT_FOUND`)
- ผู้ใช้ทุกคน login ใหม่หลัง reset (ตาราง session ถูกล้างด้วย) และต้องผูก LINE ของมือถือ demo ใหม่ (DEMO_RUNBOOK ข้อ 1.4)
- `pnpm inputs:check` ยังรันบนเครื่องและใน `pnpm verify` กับไฟล์ input ที่ commit ซึ่งคือไฟล์เดียวกับที่ deploy · งานนี้อ่านไฟล์ด้วยตัวอ่านของ seed เองก่อนล้าง
- `pnpm demo:reset --env=...` ยังใช้ได้ถ้าผู้ดูแลมีค่าของ staging ครบในเครื่อง
