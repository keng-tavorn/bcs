# ADR-056: reset staging ก่อน demo ด้วยปุ่มใน Inngest ที่ต้องพิมพ์ยืนยัน

- สถานะ: ตัดสินแล้ว (ผู้ใช้ 2026-10-07)
- วันที่: 2026-10-07
- ที่มา: NEW-70 · D-07 · ผู้ใช้เลือกทางเลือก (ก) "ปุ่มใน Inngest ต้องพิมพ์ยืนยัน DEMO-<วันที่> ก่อนล้าง" · รายละเอียดการทำเป็นของ agent

## บริบท

- D-07 เสร็จเมื่อคำสั่ง reset ใน `docs/DEMO_RUNBOOK.md` รันบน staging แล้วข้อมูลกลับเป็นสถานะก่อน demo
- คำสั่งเดิม `pnpm demo:reset --env=.env.staging --confirm=DEMO-<วันที่>` ต้องมีค่าของ staging ครบในเครื่อง แต่ค่าชนิด Secret ใน Vercel ดึงลงเครื่องไม่ได้ (`vercel env pull` ได้ค่าว่าง) และ `ENCRYPTION_KEY` ต้องตรงกับของ staging
- seed ต้องรันใกล้ฐานข้อมูล เพราะ build ของ Vercel รันที่ Washington (ADR-055)
- การล้าง staging ต้องให้ผู้ใช้อนุมัติทุกครั้ง (spec §17.4 · ADR-038 ข้อ 14)

## การตัดสินใจ

> (ผู้ใช้ตัดสิน 2026-10-07) ล้างข้อมูล staging ก่อน demo ด้วยปุ่มใน Inngest ต้องพิมพ์ยืนยัน DEMO-<วันที่> ก่อนล้าง

1. งาน Inngest `staging-demo-reset` (`src/server/jobs/staging-demo-reset.ts`) ลงทะเบียนเฉพาะเมื่อ `APP_ENV=staging` เริ่มด้วย event `bcs/staging.demo_reset_requested` คือผู้ดูแลกด Invoke ในหน้า Inngest แล้วพิมพ์ `{"data": {"confirm": "<รหัสองค์กร demo>-<วันที่วันนี้ตามเวลาไทย>"}}` เช่น `{"data": {"confirm": "DEMO-2026-10-20"}}` (กล่อง Invoke คือ payload ของ event · ถ้าพิมพ์ `{"confirm": …}` โดยไม่มี `data` งานก็อ่านได้) · คำยืนยันเหมือนของ `pnpm demo:reset` บนเครื่อง และการพิมพ์คำยืนยันของวันนี้คือการอนุมัติครั้งนั้น
2. step `check` ไม่แตะข้อมูล: ปฏิเสธถ้าไม่ใช่ staging ไม่มี `SEED_DEV_PASSWORD` คำยืนยันไม่ตรงกับวันนี้ (บอกคำที่ต้องพิมพ์) หรือมีองค์กรอื่นนอกจากองค์กร demo ของไฟล์ input (staging มีแต่ข้อมูลตัวอย่างจนกว่า OQ-19 ปิด องค์กรอื่นจึงเป็นของใครบางคน) · แล้วอ่านไฟล์ input ตรวจว่าวันนี้และวันเริ่มของทุกแถวในประวัติ demo (วันนี้ลบ `daysAgo`) อยู่ในปีงบของบรรทัดงบของแถวนั้น และตรวจที่เก็บไฟล์
3. step `reset` ตรวจข้อ 2 ซ้ำทั้งหมดก่อนทำอะไร (step ที่ถูกสั่งรันใหม่ทีหลัง เช่น Rerun from step ในหน้า Inngest จึงข้ามคำยืนยันของวันนั้นไม่ได้) → เก็บค่า LINE ขององค์กร demo ไว้ในหน่วยความจำ → ล้าง → seed ส่วนฐาน → ใส่ค่า LINE กลับให้องค์กรใหม่ · ค่าลับของ LINE ไม่ออกจาก step นี้ (ไม่เป็นผลของ step ไม่อยู่ใน log)
4. การล้าง (`src/server/db/sql/staging-wipe.ts`) ใช้ role migrator (`DIRECT_URL`) ในธุรกรรมเดียว: ตรวจซ้ำบน connection เดียวกันว่าไม่มีองค์กรอื่น แล้ว `TRUNCATE ... RESTART IDENTITY CASCADE` ทุกตารางใน schema `public` ยกเว้น `_prisma_migrations` โครงสร้างตารางยังเป็นตาม migration ล่าสุด จึงไม่ต้องรัน `prisma migrate` ใน function · TRUNCATE ไม่เรียก trigger รายแถวที่กันการแก้ตาราง append-only migration แรกเขียนว่ามีแค่ migrator ที่ทำได้ "ใน local/test เท่านั้น" ADR นี้เพิ่ม staging เมื่อผู้ดูแลพิมพ์คำยืนยันของวันนั้น ตามที่ผู้ใช้เลือก (`pnpm demo:reset` ที่มีอยู่แล้วก็ลบ schema ของ staging ด้วย migrator เช่นกัน) · migration ที่ apply แล้วแก้ไม่ได้ ข้อความนั้นจึงคงเดิม
5. ค่า LINE ที่ใส่กลับคง channelKey (path ของ webhook ที่ลงทะเบียนไว้กับ LINE) id ของ rich menu ทั้งสอง LIFF และสถานะเปิดใช้ ส่วนค่าลับเข้ารหัสใหม่ให้องค์กรใหม่ เพราะค่าลับผูกกับรหัสองค์กร (NFR-SEC-07) · การใส่กลับบันทึก Event `organization.settings_updated` (section `lineChannel`) ที่บอกชื่อช่องโดยไม่มีค่า เหมือนการบันทึกค่า LINE ทางอื่น · ถ้าค่าลับเดิมเปิดไม่ได้ ผลบอก `NOT_OPENED` และต้องตั้ง LINE ใหม่
6. step `history` ใช้ seed ชุดเดียวกับ `pnpm db:seed` และงาน `staging-first-seed` (ADR-055) · งานนี้กับ `staging-first-seed` ใช้ concurrency group เดียวกันทั้ง environment (`scope: env` · key `"staging-demo-data"`) จึงไม่เขียนข้อมูล demo พร้อมกัน · `retries: 0`

## ผลที่ตามมา

- คำยืนยันใช้ได้ทั้งวันนั้น: ถ้ากด Rerun run ของวันเดียวกันในหน้า Inngest งานจะตรวจผ่านและล้างอีกรอบ เพราะผู้ดูแลอนุมัติการล้างของวันนั้นไว้แล้ว วันถัดไปต้องพิมพ์ใหม่
- reset staging ทำได้จากหน้าเว็บของ Inngest ไม่ต้องมีค่าลับในเครื่อง ([DEMO_RUNBOOK.md](../DEMO_RUNBOOK.md) ข้อ 2)
- ถ้า run หยุดใน step `reset` หลังการล้าง ข้อมูลอาจว่าง และค่า LINE ที่ถือไว้ในหน่วยความจำหายไปด้วย · กด Invoke ซ้ำด้วยคำยืนยันเดิมในวันเดียวกันได้ หรือใช้ `staging-first-seed` ซึ่ง seed ฐานว่างได้ แล้วตั้ง LINE ใหม่ · ถ้าล้มซ้ำด้วยเหตุเดิม (เช่นที่ history) ให้หาสาเหตุก่อน ไม่กดซ้ำวน
- หลัง reset ผู้ใช้ต้องผูก LINE ของมือถือ demo ใหม่ เพราะการผูก (ตารางของผู้ใช้) ถูกล้าง ส่วน webhook และ rich menu ยังใช้ได้ (DEMO_RUNBOOK ข้อ 1.4)
- ไฟล์ใน bucket ของ demo รอบก่อน (ใบเสนอราคาและ PDF) ยังอยู่โดยไม่มีแถวในฐานอ้าง แบบเดียวกับ `pnpm demo:reset` บนเครื่อง ไม่กระทบ demo
- งาน Inngest ที่รออยู่จากข้อมูลเดิม (เช่นตัวจับเวลา SLA) จะพบว่างานนั้นไม่มีแล้วและจบเอง (`NOT_FOUND`)
- ผู้ใช้ทุกคน login ใหม่หลัง reset (ตาราง session ถูกล้างด้วย) และต้องผูก LINE ของมือถือ demo ใหม่ (DEMO_RUNBOOK ข้อ 1.4)
- `pnpm inputs:check` ยังรันบนเครื่องและใน `pnpm verify` กับไฟล์ input ที่ commit ซึ่งคือไฟล์เดียวกับที่ deploy · งานนี้อ่านไฟล์ด้วยตัวอ่านของ seed เองก่อนล้าง
- `pnpm demo:reset --env=...` ยังใช้ได้ถ้าผู้ดูแลมีค่าของ staging ครบในเครื่อง
