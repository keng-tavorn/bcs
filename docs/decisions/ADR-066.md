# ADR-066: ทำขนาน 3 สายด้วย git worktree และปรับ effort กับการรีวิวของรอบ P1

- สถานะ: เสนอ (ผู้ใช้ขอให้ทำขนานโดยความถูกต้องเท่าเดิม 2026-10-11 · ใช้ได้ทันทีเว้นแต่ผู้ใช้คัดค้าน)
- วันที่: 2026-10-11
- ที่มา: ผู้ใช้ถามวิธีทำให้เร็วขึ้น (แยก agent worktree ultracode) และวิธีประหยัด token ระหว่างแชต · spec §16.13 · §17.9 · ADR-062

## บริบท

- ผู้ใช้ยอมใช้ token มากขึ้นเพื่อความเร็ว แต่ความถูกต้องต้องเท่าเดิม · รอบ A ที่ใช้ ultracode และ `max` ช้าและกิน token มาก (ADR-062)
- ขั้น S6 S8 S9 S13 แตะคนละส่วนของโค้ด จึงทำพร้อมกันได้ถ้าแต่ละงานมีที่ทำงานแยกกัน
- repo มีวิธีแยกฐานข้อมูลและพอร์ตต่อ agent อยู่แล้ว (`BCS_TEST_DB` `BCS_VERIFY_DB` `BCS_E2E_DB` `E2E_PORT` `E2E_FAKE_LINE_PORT`) และเคยใช้ worktree ใน `.worktrees/` · บริการ Docker (Postgres RustFS Mailpit Inngest dev) ใช้ร่วมกันได้ ยกเว้น e2e เต็มชุดที่นับอีเมลใน Mailpit และใช้ CPU มาก
- `spec_check` บังคับเลข ADR OQ และ NEW ให้ต่อเนื่อง สองสายที่เพิ่มเลขพร้อมกันจะได้เลขซ้ำ · NEW รองรับแค่ 2 หลัก
- CI บน GitHub Free มีนาที Actions จำกัด และ e2e เต็มชุดใช้ราว 50 นาทีต่อรอบ

## การตัดสินใจ

> ทำขนาน 3 สายด้วย git worktree (สาย 1 S6 แล้ว S17 · สาย 2 S8 แล้ว S9 · สาย 3 S13) ฐานข้อมูลและพอร์ตแยก บริการ Docker ใช้ร่วม · รวม main เข้าสายก่อนทุกข้อ และส่งงานเข้า main เมื่อจบขั้นหลัง `/code-review high main...HEAD` · รวมด้วย merge เท่านั้น · ช่วงเลข ADR และ OQ ต่อขั้นที่ `spec_check` ตรวจ · effort `high` ในสายและรีวิวทั้งระยะ `xhigh` · Ultracode เฉพาะ P1-04 (ปรับ ADR-062)

## ผลที่ตามมา

- ตารางสาย (branch โฟลเดอร์ พอร์ต ฐานข้อมูล ช่วงเลข) อยู่ใน spec §16.13 · ขั้นตอนของ agent อยู่ใน skill `bcs-lane` · ขั้นตอนของผู้ใช้อยู่ใน `docs/runbooks/parallel-lanes.md` · เครื่องมือสร้างสายอัตโนมัติเป็นข้อ P1-01
- งานที่พบในสายเป็นข้อใหม่ท้ายขั้นของสาย ไม่ใช้เลข NEW · ADR และ OQ ใหม่ในสายใช้ช่วงของขั้น (S6 101–119 · S8 S9 121–139 · S13 141–159 · S17 161–179) · `spec_check` อ่านช่วงจากคอลัมน์ "เลข ADR" และ "เลข OQ" ของตารางสาย และรู้จักข้อ `P1-nn` กับ NEW 3 หลัก
- ส่งงานเข้า main ครั้งละขั้น (หรือบางส่วนเมื่อสายอื่นต้องใช้) จึงรีวิวได้ตรงงานของสาย และ CI รันน้อยครั้ง · branch ของสาย push ไป GitHub เป็นสำรองโดยไม่ทำให้ CI รัน
- ความเร็วมาจากจำนวนสาย ไม่ใช่ effort ที่สูงขึ้น · การตรวจแยกจากการสร้างด้วยบริบทใหม่ ใช้โมเดลเดียวกัน · `/code-review ultra` ผู้ใช้เลือกพิมพ์เองได้ (คิดเงินแยก)
- ข้อจำกัดของเครื่องเดียว: `pnpm verify --e2e` เต็มชุดรันทีละสาย · งานตามเวลาของ Inngest dev รันเฉพาะแอปที่พอร์ต 3000 · ทุกสายใช้ quota การใช้งานของผู้ใช้แยกกัน จึงใช้ token เร็วขึ้นราวจำนวนสาย
- ไฟล์ข้อมูลระยะ 1 สร้างใหม่จากสคริปต์ได้ทุกเมื่อ จึงแก้ conflict ของ xlsx ด้วยการสร้างใหม่ (ADR-065)
