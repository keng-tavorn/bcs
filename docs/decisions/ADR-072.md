# ADR-072: แผนเร่งของรอบ P1: S17 แบ่งสองสาย effort `xhigh` และรีวิวทันทีในข้อเงินและสิทธิ์ และ S9-02 S9-03 เขียนสองชุดเทียบกัน

- สถานะ: ยอมรับ (ผู้ใช้อนุมัติในแชตเมื่อ 2026-10-15 พร้อมเงื่อนไขเพิ่ม 3 ข้อ)
- วันที่: 2026-10-15
- ที่มา: แผนเร่งความเร็วจนถึงเส้นชัย A3 ที่แชตสาย 3 ร่างหลังเส้นชัย F (2026-10-15) · ข้อความอนุมัติของผู้ใช้: "อนุมัติแผนเร่ง: สาย 3 ทำ S17 ส่วน LINE สาย 1 ทำส่วน BCS Go · ปิด OQ-167 OQ-171 ตามผล P1-06 · ข้อเงินและสิทธิ์ใช้ xhigh รีวิวทันทีทุกข้อ และ S9-02 S9-03 เขียนสองชุดเทียบกัน" · ปรับ ADR-066

## บริบท

- สาย 3 ถึงเส้นชัย F แล้วและว่าง · สาย 1 ยังเหลือ S6-22 แล้วจึงเริ่ม S17 ทั้งขั้นคนเดียว ซึ่งเป็นงานที่ยาวที่สุดของรอบ (เส้นชัย G)
- S17 แยกได้เป็นสองกลุ่มที่แตะไฟล์ต่างกัน: ส่วน LINE (เมนู ขอผ่านแชท LIFF) และส่วนแอป BCS Go (Capacitor push ตรวจรับออฟไลน์ สแกน passkey)
- P1-06 อนุมัติทุกเรื่องตามที่แนะนำ รวมเรื่อง 82 (passkey ใช้ `@simplewebauthn/server`) และเรื่อง 86 (แจ้งผู้ตรวจรับทันทีเมื่อส่ง PO) แต่ OQ-167 และ OQ-171 ยังเขียนว่ารอผู้ใช้ จึงขวาง S17-15 และ S17-05
- ผู้ใช้ยอมใช้ token และเวลาเพิ่มในข้อที่แตะเงินและสิทธิ์ เพื่อให้ความถูกต้องสูงขึ้นระหว่างที่งานเร็วขึ้น (เดิมข้อเหล่านี้ใช้ `high` และในโหมดจนถึงเส้นชัยรีวิวรวมท้ายขั้นครั้งเดียว)
- engine ของรอบจ่าย (S9-02) และไฟล์ธนาคาร (S9-03) เป็นจุดที่เงินออกจากบริษัท · golden และตัวคำนวณ Python ใน `spec_check` ตรวจเฉพาะเคสที่เขียนไว้

## การตัดสินใจ

> 1. **S17 แบ่งสองสาย:** สาย 3 ทำส่วน LINE (S17-01 ถึง S17-04 และ S17-06 ถึง S17-08) · สาย 1 ทำส่วน BCS Go (S17-05 และ S17-09 ถึง S17-18) · เลขใหม่ของสาย 1 ADR-168 ถึง ADR-173 และ OQ-172 ถึง OQ-175 · ของสาย 3 ADR-174 ถึง ADR-179 และ OQ-176 ถึง OQ-179
> 2. **ปิด OQ-167 และ OQ-171 ตาม P1-06:** passkey ใช้ `@simplewebauthn/server` ตรวจในคำสั่งของ BCS ผ่าน `runCommand` (ไม่เปิด endpoint passkey ใต้ `/api/auth/*`) และอยู่ในตาราง §5.5 · ส่ง PO แล้วแจ้งผู้ตรวจรับทันทีทาง LINE หรือ push พร้อมลิงก์หน้าตรวจรับ ไม่มีราคา ผู้ขอยังเป็นสรุปรายวัน
> 3. **ข้อเงินและสิทธิ์ใช้ `xhigh` และรีวิวทันที:** ข้อในขั้นของสายที่แตะเงิน ภาษี งบ DOA การอนุมัติ สิทธิ์ scope step-up หรือ auth มี effort `xhigh` ในตารางของขั้น และหลัง `pnpm verify` ผ่าน agent เรียก `/code-review xhigh <ฐาน>...HEAD` ของข้อนั้นเองทันทีในทุกโหมด (รวมโหมดจนถึงเส้นชัย) แก้ข้อที่กระทบความถูกต้อง เงิน สิทธิ์ หรือ "เสร็จเมื่อ" แล้วจึงติ๊ก · รีวิวท้ายขั้นยังมีอยู่เพื่อดูปฏิสัมพันธ์ระหว่างข้อ
> 4. **S9-02 และ S9-03 เขียนสองชุดเทียบกัน:** นอกจาก engine ใน `src/core` มีชุดที่สองที่ subagent อีกตัวเขียนจาก spec และ sub-spec โดยไม่เห็นโค้ดชุดแรก เก็บเป็น oracle ใน `tests/support/oracles/` และมี property test ถาวรที่สุ่มข้อมูลแล้วผลต้องเท่ากันทุกช่อง · ผลต่างทุกจุดตัดสินจาก spec ไม่ใช่แก้ให้ตรงกัน · ตีความได้สองทางให้หยุดถาม

## ผลที่ตามมา

- ลำดับของ S17: สาย 3 ร่าง S17-01 (และแกน `src/core/line-menu` ของ S17-03) ได้ก่อน D เข้า main แต่ไม่ติ๊กและไม่ส่ง · หลัง D เข้า main สาย 3 รวม main ทำ S17-01 ให้จบ (ค่าตั้งใหม่ทำงานกับ UAT sandbox ของ S6 ทั้งการคัดลอกค่าตั้งและกฎปิด LINE) ติด tag `p1-s17-start` บน main แล้วส่ง S17-01 เข้า main ครั้งเดียว · จากนั้นทำ S17-03 S17-04 S17-06 S17-02 S17-07 S17-08 แล้วรีวิว `/code-review high main...HEAD` และส่งส่วน LINE เข้า main
- สาย 1 หลัง S6-22: ระหว่างรอ S17-01 เข้า main ร่างแกนคิวออฟไลน์ของ S17-11 กับเทสต์จาก golden ใน sub-spec ได้แต่ไม่ติ๊ก · แล้วทำ S17-09 S17-10 S17-05 S17-11 S17-12 S17-13 S17-14 S17-15 · S17-16 ถึง S17-18 ทำหลังส่วน LINE อยู่ใน main · S17-18 รีวิวด้วย `/code-review high p1-s17-start...HEAD`
- S17-05 อยู่สาย 1 เพราะ `deliverNotification` และแม่แบบข้อความต้องแก้จากสายเดียว (S17-10 เพิ่มช่องทาง PUSH ที่นั่น) · ลิงก์ `/liff/gr/<poId>` มีอยู่แล้ว
- สาย 2 ทำ S9 คนเดียวเหมือนเดิม · S9-11 รีวิว `main...HEAD` ถ้ายังไม่มีงานของ S9 เข้า main ก่อน ถ้ามีใช้ `c11cbd7...HEAD`
- ไฟล์ที่แก้จากสายเดียวเท่านั้น: `permissions.ts` (สิทธิ์ใหม่ของ S9 อยู่สาย 2 · ของ S17 อยู่สายที่เป็นเจ้าของข้อ) · `deliverNotification` และแม่แบบข้อความ (สาย 1) · migration ของแต่ละขั้นอยู่สายเดียว ถ้าสองสายต้องแก้ตารางเดียวกันให้หยุดถาม · S17-04 S17-12 S17-14 ใช้ตัวตรวจสิทธิ์รับของเดิมใน `receiving/access.ts` ไม่เขียนใหม่ · S17-09 เพิ่มเทสต์ถาวรที่ล้มเมื่อคำสั่งใดรับช่องทาง WEB แต่ไม่รับ APP
- Ultracode เปิดได้เฉพาะ S9-02 คู่ S9-03 (สองชุด) S9-09 S17-16 P1-08 และ P1-09 นอกจาก P1-04 · เปิดตอนทำข้อนั้นแล้วปิดทันที · agent สองตัวในสายเดียวห้ามรันเทสต์ verify หรือ git พร้อมกัน เพราะใช้ฐานทดสอบเดียวกัน
- แชตในสายที่ทำต่อเนื่องหลายข้อใช้ effort สูงสุดของข้อที่เหลือในตาราง (สาย 2 กับ S9 และทั้งสองส่วนของ S17 คือ `xhigh`) · ช้ากว่าเดิมต่อข้อ แต่ได้เวลาคืนจากสายที่สามและการรีวิวท้ายขั้นที่สั้นลง
- e2e เต็มชุดรันทีละสายตามคิว: S6-22 → ส่ง S17-01 → S9-11 หรือส่งส่วน LINE (อันที่พร้อมก่อน) → S17-18 → P1-08 → P1-10 · ระหว่างทำงานรันเฉพาะฉากที่เกี่ยวข้อง (`--grep @tag`) · แดงให้หาสาเหตุจริง ห้ามเพิ่ม timeout แบบเหมารวม · ส่งงานบางส่วนเข้า main ให้น้อยที่สุด
- แชตที่ main เตรียมงานท้ายระยะล่วงหน้าได้เฉพาะเอกสารร่างใน `docs/drafts/p1/` (รายชื่อฉากของ P1-08 · runbook ของ P1-12 · แม่แบบแบบฟอร์มข้อมูลจริง · แนวคิดตัวกันข้อมูลของ staging ใน P1-11 · รายการปัญหาที่เห็นล่วงหน้าใน S8 S13 ให้สายเจ้าของแก้) · ไม่แก้โค้ด ไม่ติ๊ก ไม่เริ่มข้อ P1-08 ถึง P1-13 ก่อนเวลาในตาราง · P1-10 ยังเป็นคำสั่งเดียว `/code-review xhigh p1-start...HEAD`
- ข้อที่แบ่งไม่ได้: S9-04 กับ S9-05 (กันโกงชุดเดียวกัน) · S9-06 ถึง S9-08 และ S9-10 (สถานะต่อเนื่อง) · การรีวิวท้ายขั้น · การรวมงานข้ามสายต้องผ่าน main เท่านั้น · deploy และ reset staging ทีละครั้งและผู้ใช้อนุมัติทุกครั้ง
