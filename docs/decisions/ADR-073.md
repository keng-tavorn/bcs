# ADR-073: สายชั่วคราวของรอบเส้นชัย A3: สาย l1 รีวิวล่วงหน้า สาย l2 โค้ดของ P1-11 สาย l3 ร่างเอกสาร ส่วน main ทำ P1-08 ถึง P1-12 ตามลำดับเดิม

- สถานะ: ยอมรับ (ผู้ใช้อนุมัติในแชตเมื่อ 2026-10-17)
- วันที่: 2026-10-17
- ที่มา: แผน "ทาง B" ที่แชตสาย l1 เสนอหลังเส้นชัย G (2026-10-17 · 8 agent ร่างแผน 3 แบบแล้วเทียบกัน: ทำบน main อย่างเดียว ~32 ชม. · main กับ 3 สายชั่วคราว ~26 ชม. · ขนานสูงสุด ~23 ชม. แต่เสี่ยงสูง) · ข้อความอนุมัติของผู้ใช้: "อนุมัติแผน ADR-073" ซึ่งอ้างข้อความอนุมัติฉบับเต็มในข้อ 3 ของแผนนั้น (คัดไว้ในหัวข้อ "ข้อความที่อนุมัติ") · ปรับ ADR-066 และ ADR-072

## บริบท

- เส้นชัย D E F G เสร็จและอยู่ใน main แล้ว (G 2026-10-17 · `10d2087`) และ CI บน main เขียวหลัง NEW-91 (`4fb8d05`) · เหลือ P1-08 ถึง P1-13 ซึ่งกติกาเดิมให้ทำบน main ทีละข้อ (§16.13 แถว "เลข ID ในสาย": ข้อ P1-nn ทำบน main เท่านั้น)
- เวลาส่วนใหญ่ของข้อที่เหลือหมดไปกับการรอ e2e (รอบ strict ราว 2.5 ชม.) รอ CI และรอผู้ใช้ ไม่ใช่การคิด · effort หรือ agent ที่มากขึ้นในโฟลเดอร์เดียวไม่ทำให้เร็วขึ้น
- งานบางส่วนไม่ขึ้นกับ P1-08 และ P1-09: รีวิวโค้ดของระยะ 1 ที่อยู่ใน main แล้ว · โค้ดของ P1-11 (reset staging เลือกชุดข้อมูลและ seed แบบแบ่งช่วง) · ร่างเอกสารของ P1-11 P1-12 และรายการหน้าของ P1-09
- ผู้ใช้ต้องการเร็วที่สุดโดยความถูกต้องเท่าเดิม และคุม 3 สายมาตลอดรอบ P1

## การตัดสินใจ

> 1. **สาย l1 รีวิวล่วงหน้าก่อน P1-10:** หลังรวม main เข้าสาย จด commit ของ `origin/main` ตอนนั้นเป็น `<pin>` แล้วเรียก `/code-review xhigh p1-start...<pin>` แก้ข้อที่กระทบความถูกต้อง เงิน สิทธิ์ หรือ "เสร็จเมื่อ" ของข้อที่ติ๊กแล้ว ข้ออื่นจดไว้ให้ออกเลข NEW `[go-live]` ตอนส่ง · บันทึกใน `docs/reports/p1-review-pre.md` · ไม่ติ๊กข้อใด · commit ใส่ `ADR-073` (ไม่ใส่ `P1-10` เพื่อไม่ให้ฐานของการตรวจ P1-10 เพี้ยน)
> 2. **สาย l2 ทำเฉพาะส่วนโค้ดของ P1-11:** งาน reset ของ staging (ADR-056) เลือกชุดข้อมูลได้ (demo หรือระยะ 1) และ seed แบบแบ่งช่วงให้จบในเวลาของ Inngest · ตัวกัน (guard) ของ reset ที่ปฏิเสธเมื่อมีองค์กรอื่นนอกจากองค์กร demo (`OTHER_ORGANIZATIONS`) ยอมเพิ่มเฉพาะองค์กรตัวอย่างของระยะ 1 ที่ seed สร้าง คือ `SIMEC` และ `SIMEC-UAT` (ผู้ใช้อนุมัติในข้อความนี้) · องค์กรอื่นยังปฏิเสธเหมือนเดิม · พร้อมเทสต์ · ไม่ deploy ไม่ reset staging ไม่ติ๊ก P1-11 · ส่งเข้า main ก่อน P1-10 เริ่ม
> 3. **สาย l3 เขียนร่างเอกสารใน `docs/drafts/p1/` เท่านั้น:** ขั้นตอนของ P1-11 · runbook ระยะ 1 คำอธิบายการกรอกแบบฟอร์มข้อมูลจริง และโครงรายงานของ P1-12 · รายการหน้าใหม่ของระยะ 1 สำหรับ P1-09 · ไม่แก้โค้ด ไม่ติ๊ก
> 4. **main ทำ P1-08 → P1-09 → P1-10 → P1-11 → P1-12 ตามลำดับเดิม:** P1-10 ยังเป็นคำสั่งเดียว `/code-review xhigh p1-start...HEAD` ทั้งระยะ (เห็นงานแก้ของ l1 และโค้ดของ l2 ด้วย) · P1-12 ทำ runbook และแบบฟอร์มได้หลัง P1-10 ส่วนรายงาน `p1-demo-ready.md` ทำท้ายสุดหลัง P1-11
> 5. **e2e ทั้งเครื่อง:** Playwright รันพร้อมกันได้ไม่เกิน 2 ชุด (เต็มชุดหรือ `--grep`) และ main มาก่อน · ช่วงรันจบของ P1-08 (`@p1demo` 2 รอบติด) และ `pnpm verify --strict --e2e` ของ P1-10 สายห้ามรัน Playwright เลย · e2e แดงให้หาสาเหตุจริง ห้ามเพิ่ม timeout แบบเหมารวม
> 6. **เลข NEW ADR และ OQ ของสายชั่วคราวออกตอนส่งเข้า main เท่านั้น** ต่อจากเลขล่าสุดของ main หลังรวม (แบบสายชั่วคราวก่อน P1-07) · ไม่ใช้ช่วงเลขของขั้นในตารางสาย
> 7. **Ultracode:** เปิดได้เฉพาะ P1-08 (แยกตามกลุ่มฉาก) และ P1-09 (แยกตามกลุ่มหน้า) ตาม ADR-072 · แชตของสายปิด

## ผลที่ตามมา

- แชตที่เปิดพร้อมกันสูงสุด 5 แชต: ADR นี้ (ครั้งเดียว) แล้ว main กับ 3 สาย · ลำดับเปิดและ effort อยู่ใน `docs/runbooks/parallel-lanes.md` หัวข้อ "สายชั่วคราวของเส้นชัย A3"
- แต่ละสายใช้ worktree branch ฐานข้อมูล และพอร์ตเดิมของตารางสาย (§16.13) · รวม main เข้าสายก่อนเริ่ม · ส่งงานเข้า main ด้วย `git push origin HEAD:main` (fast-forward) หลังรวม main `pnpm verify` และ `pnpm test:e2e --grep @demo` (เมื่อแก้โค้ด) ตาม skill `bcs-lane` หัวข้อ 8
- ความถูกต้องไม่ลดลง: ทุกงานยังผ่าน `pnpm verify` · มีรีวิว `xhigh` เพิ่มหนึ่งรอบก่อน P1-10 · P1-10 ยังตรวจทั้งระยะรวมโค้ดของ P1-11
- P1-10 เริ่มเมื่อ P1-09 ติ๊กแล้ว และโค้ดของ l2 อยู่ใน main · ถ้า l1 ยังรีวิวไม่จบ ให้ l1 ส่งงานแก้ที่เสร็จแล้วเข้า main แล้วหยุด (P1-10 ตรวจส่วนที่เหลือเอง)
- ข้อที่แบ่งไม่ได้: ฉากของ P1-08 (ต่อกันบนฐานเดียวและต้องผ่าน 2 รอบติดในที่เดียว) · P1-10 (คำสั่งเดียวทั้งระยะ) · deploy และ reset staging (ทำใน P1-11 บน main และผู้ใช้อนุมัติทุกครั้ง)
- งานหาสาเหตุ CI ล้มที่แผนเดิมเผื่อไว้ให้ l3 เสร็จแล้วใน NEW-91 จึงไม่อยู่ในงานของ l3
- ข้อความ Ultracode ที่ล้าสมัยใน spec (ส่วน "เริ่มที่นี่" และรายการเปลี่ยนแปลงของฉบับ 0.4) แก้ให้ตรง ADR-072 และ ADR นี้
- หลังเส้นชัย A3 สายทั้งสามว่าง · การลบสายต้องถามผู้ใช้ก่อน (CLAUDE.md หัวข้อ 2)
