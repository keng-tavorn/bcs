# ADR-075: เริ่มออกแบบระยะ 2 (sub-spec S7 S10 S11) ก่อนจบเส้นชัย A3 และ C โดยยังไม่เขียนโค้ด

- สถานะ: ตัดสินแล้ว (ผู้ใช้ 2026-11-01)
- วันที่: 2026-11-01
- ที่มา: คำสั่งของผู้ใช้ในแชตบน main (2026-11-01) อ้าง spec §16.2 ข้อ 6 ("สลับลำดับได้เมื่อผู้ใช้สั่งเท่านั้น") · §16.0 แถว 11–13 เดิมให้ S7 S10 S11 เริ่ม "หลัง C และลูกค้าตกลงขอบเขตระยะ 2"

## ข้อความที่สั่ง

```text
เริ่มออกแบบระยะ 2 ก่อนจบ A3 และ C ตามที่ฉันสั่ง (spec §16.2 ข้อ 6 · บันทึกเป็น ADR): เขียน sub-spec S7 S10 S11 ระดับ §7–§8 พร้อม AC ของทุก FR ใน §16.8 ร่าง golden case ที่คำนวณตัวเลขแล้ว และ checklist ใน §16.19 ถึง §16.21 · เขียน S7 ก่อน แล้ว S10 กับ S11 ขนานกัน · ให้ตัวตรวจบริบทใหม่ตรวจแต่ละขั้นและตรวจไขว้รอยต่อ แล้วแก้ตามผล · เลข ADR และ OQ: S7 181–199 · S10 201–219 · S11 221–239 · รวมเรื่องที่ฉันต้องตัดสินไว้ใน docs/reports/p2-decisions.md ภาษาง่าย พร้อมค่าที่แนะนำ · ให้ pnpm spec:check และ pnpm inputs:check ผ่าน แล้ว commit บนเครื่อง · ห้าม push ห้าม deploy และห้ามเขียนโค้ด แล้วหยุดรอฉันอนุมัติ
```

## บริบท

- รอบ P1 ใกล้เส้นชัย A3 (เหลือข้อที่รอผู้ใช้และรายงาน P1-12 · `docs/reports/p1-demo-ready.md`) · เส้นชัย B และ C ยังไม่เริ่ม เพราะต้องรอข้อมูลจริงและคำตอบจากลูกค้า ซึ่งเป็นช่วงที่ agent ว่าง
- ระยะ 2 (S7 Supplier Onboarding · S10 Sourcing · S11 Risk Orchestration · ADR-057) ยังไม่มี sub-spec checklist หรือ ADR ของขั้น · §16.2 ข้อ 7 กำหนดว่าทุกขั้นตั้งแต่ S6 ต้องมี sub-spec ระดับ §7–§8 ที่ผู้ใช้อนุมัติก่อนเขียนโค้ด การเขียนล่วงหน้าจึงไม่ข้ามด่านใด แค่ย้ายเวลา
- การออกแบบไม่แตะโค้ด migration หรือ staging จึงไม่กระทบ `pnpm verify` ฉาก demo หรือรอบ A3 ที่กำลังปิด · ของที่ได้ (sub-spec ADR OQ และคำถามถามลูกค้า) ใช้คุยขอบเขตระยะ 2 กับลูกค้าได้ทันทีหลัง demo ระยะ 1 และคำถามของระยะ 2 เข้าแบบฟอร์มเส้นชัย B ชุดเดียวกัน

## การตัดสินใจ

> เขียน sub-spec ของ S7 S10 S11 ล่วงหน้าในรอบนี้ (ออกแบบอย่างเดียว) ส่วนลำดับการเขียนโค้ดของ §16.0 แถว 11–13 ไม่เปลี่ยน: โค้ดของระยะ 2 เริ่มหลังเส้นชัย C เมื่อลูกค้าตกลงขอบเขต และหลังผู้ใช้อนุมัติ sub-spec กับเรื่องใน `docs/reports/p2-decisions.md` แล้ว เว้นแต่ผู้ใช้สั่งเป็นอย่างอื่น

1. ผลงานของรอบ: `docs/sub-specs/S7.md` `S10.md` `S11.md` ระดับ §7–§8 (entity · state machine · กฎ BR INV · ร่าง golden case ที่คำนวณตัวเลขแล้ว · AC ของทุก FR ในแถว S7 S10 S11 ของ §16.8 รวมเงื่อนไข §8.12 · สิทธิ์ event error การแจ้งเตือน · การอ่านชีตของไฟล์ระยะ 1 · หน้าจอ · เรื่องที่ผู้ใช้ต้องตัดสิน · interface กับขั้นอื่น) · checklist และตาราง effort ใน §16.19 §16.20 §16.21 · ADR และ OQ ของขั้นในช่วง S7 181–199 · S10 201–219 · S11 221–239 (ตารางช่วงเลขของระยะ 2 อยู่หัว §16.19 และ `scripts/spec_check.py` อ่านคอลัมน์ "เลข ADR" "เลข OQ" ของตารางนั้นเหมือนตารางสายของ §16.13) · `docs/reports/p2-decisions.md` ภาษาง่าย · `docs/reports/p2-review.md` ผลตรวจ
2. ลำดับเขียน: S7 ก่อน (S10 และ S11 ต่างพึ่งโมดูล `SUPPLIER` พอร์ทัล และ `SupplierDocument` ของ S7) แล้ว S10 กับ S11 ขนานกัน · ทุกขั้นผ่านตัวตรวจบริบทใหม่ 4 มุม (ความสอดคล้องกับ spec · เงิน อำนาจ สิทธิ์ ความปลอดภัย PDPA · รอยต่อกับโค้ดและขั้นระยะ 1 ใน main · คำนวณ golden ซ้ำอิสระ) แล้วตรวจไขว้รอยต่อ S7↔S10 S7↔S11 S10↔S11 และระยะ 2↔ระยะ 1 ก่อนแก้ตามผล · ผู้เขียนและผู้ตรวจเป็นโมเดลเดียวกัน (สิ่งที่แยกคือบริบท · แบบเดียวกับ P1-05)
3. สิ่งที่ยังไม่ทำจนกว่าผู้ใช้อนุมัติ: โค้ด migration เทสต์ seed ชีตใหม่ของไฟล์ระยะ 1 (ยกเว้นแถวคำถามของ OQ ใหม่ในชีต Questions ซึ่งเป็นข้อมูลที่ `pnpm inputs:check` บังคับ) การเปิดโมดูล การ push และ deploy · ร่างทั้งหมดอยู่บนเครื่องและ commit บน main เท่านั้น
4. การอนุมัติ: ผู้ใช้อ่าน `docs/reports/p2-decisions.md` แล้วตอบรายเรื่องหรือพิมพ์ "อนุมัติตามที่แนะนำ" (แบบ P1-06) · agent บันทึกคำตอบลง sub-spec และ ADR ในแชตเดียวกัน แล้วเปลี่ยนสถานะ ADR-181 ขึ้นไปจาก "ร่าง ADR-075 รออนุมัติ" เป็น "ยอมรับ" · เลข BR INV GC event error และความสามารถในร่างเพิ่มลง spec ในข้อที่สร้างโค้ดนั้น (กติกาเดียวกับรอบ P1 · §16.13 แถว sub-spec) ส่วนตระกูลที่หลายขั้นใช้ร่วม (GC-DOA BR-SOD GC-SOD BR-NOTI BR-AI GC-AI) ร่างจองช่วงเลขไว้ต่อขั้นและเรียงเลขจริงตอนเพิ่มลง spec
5. แท็ก `[demo]` ของข้อใน §16.19 ถึง §16.21 หมายถึงต้องเสร็จก่อนเส้นชัย H (demo ระยะ 2 กับลูกค้า) · `[go-live]` คือของจริงหลังลูกค้าเปิดใช้โมดูลนั้น · บรรทัดความคืบหน้าสู่เส้นชัย H ของ `pnpm spec:check` นับข้อ `[demo]` ของ S7 S10 S11 อยู่แล้ว
6. สายขนานของระยะ 2 (worktree branch ฐานข้อมูล พอร์ต) ตัดสินตอนเริ่มโค้ดและเพิ่มแถวในตารางสายตอนนั้น · ร่างสมมติว่า S7 ทำก่อนในสายเดียว แล้ว S10 กับ S11 คนละสาย

## ผลที่ตามมา

- §16.0 แถว 11–13 คงเงื่อนไขเริ่มโค้ดเดิม แต่คอลัมน์สถานะบอกว่า sub-spec ร่างแล้วรออนุมัติ · §16.2 ข้อ 6 และ 7 อ้าง ADR นี้ · ส่วน "เริ่มที่นี่" เพิ่มแถวคำสั่งสำหรับการอนุมัติและการแก้ร่างของระยะ 2
- ADR-181 ขึ้นไปและ OQ-181 ขึ้นไปเป็น "ร่าง" จนผู้ใช้ตอบ · ค่าเริ่มต้นของ OQ ใช้ได้ตาม §0.6 เมื่อถึงเวลาเขียนโค้ด
- ไฟล์ `docs/inputs/BCS_inputs_p1.xlsx` ถูกสร้างใหม่จาก `scripts/inputs_p1/make.py` เพราะชีต Questions ได้แถวของ OQ ใหม่ (ข้อมูล ไม่ใช่โค้ด · seed และเทสต์ไม่อ่านชีตนี้)
- ถ้าลูกค้าตกลงขอบเขตระยะ 2 ต่างจากร่าง (เช่น ตัด S10 หรือสลับ S10 กับ S11) ให้แก้ sub-spec และ checklist ก่อนเริ่มโค้ด ไม่ต้องรื้อ ADR นี้ · การสลับลำดับ S10 กับ S11 ยังต้องให้ผู้ใช้สั่ง (§16.2 ข้อ 6)
- ความเสี่ยง: ร่างเขียนก่อนได้ข้อมูลจริง (เส้นชัย B) จึงอิงข้อมูลสังเคราะห์ SIMEC และ OQ ของระยะ 1 ที่ยังไม่ปิด · ทุกเรื่องที่ขึ้นกับคำตอบลูกค้าเป็น OQ พร้อมค่าเริ่มต้น ไม่เดา (§17.3)
