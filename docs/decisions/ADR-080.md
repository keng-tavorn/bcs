# ADR-080: สายชั่วคราวของรอบผู้ช่วย BCS: สาย l1 l2 l3 ทำข้อ NEW ของผู้ช่วยพร้อมกัน สายละชุดที่แตะไฟล์ชุดเดียวกัน

- สถานะ: ยอมรับ (ผู้ใช้อนุมัติในแชตเมื่อ 2026-11-03)
- วันที่: 2026-11-03
- ที่มา: ผู้ใช้ถามว่าข้อใดของรอบผู้ช่วยทำพร้อมกันได้ (`docs/reports/bcs-assistants.md` · NEW-117 ถึง NEW-126) แล้วสั่งให้เขียนกติกา (คัดไว้ในหัวข้อ "ข้อความที่อนุมัติ") · ปรับ ADR-073 ที่จำกัดสายไว้กับงานของ P1

## บริบท

- NEW-121 และ NEW-122 เสร็จบน main แล้ว ทำทีละข้อ · ข้อที่เหลือหลายข้อไม่รอกัน แต่บางข้อใช้ไฟล์หรือกลไกเดียวกัน
- ทำสองแชตในโฟลเดอร์เดียวไม่ได้ เพราะใช้ฐานข้อมูลและพอร์ตชุดเดียวกัน เคยรัน verify ซ้อนกับ e2e ในโฟลเดอร์เดียวแล้วเทสต์ล้มปนกัน
- สาย l1 l2 l3 (`.worktrees/l1` ถึง `l3`) ว่าง ส่งงานเก่าเข้า main ครบแล้ว และมีฐานข้อมูลกับพอร์ตของตัวเองตามตารางสาย (§16.13) · ADR-073 ให้สายทำเฉพาะงานของ P1 ซึ่งเสร็จแล้ว
- ผู้ใช้ต้องการเร็วขึ้นโดยความถูกต้องเท่าเดิม · ข้อที่แตะเงินหรือสิทธิ์ใช้ `xhigh` และรีวิวทันที (ADR-072)

## การตัดสินใจ

> 1. **สายและลำดับ:** แชตละหนึ่งข้อ สั่งด้วย `ทำ NEW-nn` ในโฟลเดอร์ของสาย · ทำเฉพาะข้อของสายตัวเองในตารางนี้ และเฉพาะข้อที่ไม่มี "— รอยืนยัน" ใน §16.11 · ถ้าข้อที่สั่งยังรอยืนยันหรือเป็นของสายอื่น → หยุดและบอกผู้ใช้
>
> | สาย | ลำดับ | effort | อยู่ด้วยกันเพราะ | ไฟล์ที่สายนี้เป็นเจ้าของ |
> | --- | --- | --- | --- | --- |
> | l1 | NEW-126 → NEW-124 | `xhigh` · `xhigh` | ร่างข้อความที่คนอ่านแล้วกดส่งเองทาง LINE และอีเมลเหมือนกัน · NEW-126 สร้างชิ้นนี้ NEW-124 ใช้ต่อ · ทางส่งข้อความแก้ได้จากสายเดียว (ADR-072) | `src/server/notifications/**` · ส่วนรายการไม่ตรงของใบแจ้งหนี้ (`variance-list.tsx` `exception-actions.tsx` `invoice-page.tsx`) · `src/ui/assistants/document-panel.tsx` |

> 2. **ไฟล์ร่วม:** ทุกสายแก้ได้แบบเพิ่มต่อท้ายเท่านั้น: capability ใหม่ใน `permissions.ts` · model ใหม่ท้าย `prisma/schema.prisma` และ migration ของตัวเอง · ชนิดเรื่องใหม่ใน `src/server/services/assistants/suggestions.ts` และ `src/lib/assistant-suggestions.ts` · event ใหม่ · คีย์ใหม่ใน `messages/src/**` · แถวและข้อใหม่ใน spec `docs/feature-status.yaml` `docs/traceability/ac-map.yaml` · ไฟล์ของอีกสายแก้ให้น้อยที่สุดและบอกในสรุป · conflict ตอนรวมทำตาม skill `bcs-lane` หัวข้อ 5 (เงิน สิทธิ์ หรือ migration ที่ไม่ใช่การเพิ่มต่อท้ายทั้งสองฝั่ง → หยุดถาม)
> 3. **แชตแรกของแต่ละสายในรอบนี้:** `pnpm lane:check` → รวม main เข้าสาย (skill หัวข้อ 2) → `pnpm install` → `pnpm messages:build` → `pnpm db:reset` (ฐานของสาย) → `pnpm verify` · สายตามหลัง main 43 ถึง 74 commit ตอนเริ่มรอบ แชตที่ main จึงเลื่อน branch ของสายไปที่ main ให้แล้ว (fast-forward ครั้งเดียว)
> 4. **effort และการตรวจ:** ข้อ `xhigh` (เงิน หรือสิทธิ์): หลัง `pnpm verify` ผ่านและ commit แล้ว agent เรียก `/code-review xhigh <ฐาน>...HEAD` เอง (ฐานแบบเดียวกับบรรทัด "ตรวจก่อน:") แก้ข้อที่กระทบความถูกต้อง เงิน สิทธิ์ หรือ "เสร็จเมื่อ" รัน `pnpm verify` อีกครั้ง บันทึกใน `docs/reports/review-NEW-nn.md` แล้วจึงติ๊ก · ข้อ `medium` ไม่รีวิวซ้ำ · ไม่มีบรรทัด "ตรวจก่อน:" ในสาย
> 5. **ติ๊กในสายได้:** ติ๊กพร้อมเลข commit ตามปกติ (รวม main ด้วย `git merge` ไม่ squash เลข commit จึงคงอยู่)
> 6. **เลข NEW ADR และ OQ:** ระหว่างทำใช้เลขถัดไปของ main ตอนนั้น · ตอนส่งเข้า main หลังรวม `origin/main` ถ้าเลขนั้นถูกใช้แล้ว ให้เปลี่ยนเป็นเลขถัดไปทุกที่ที่อ้าง (ไฟล์ ADR · แถว §18.1 · ข้อ NEW · ข้อความในโค้ดและเทสต์) แล้วรัน `pnpm spec:check`
> 7. **e2e:** Playwright ทั้งเครื่องพร้อมกันไม่เกิน 2 ชุด และ main มาก่อน · e2e เต็มชุดรันทีละแชต · ก่อนรันดูโปรเซส `playwright` ด้วยคำสั่งอ่านอย่างเดียว ถ้ามี 2 ชุดแล้วให้รอ · ห้ามปิดโปรเซสของสายอื่นหรือของ main · เทสต์ที่ล้มตอนเครื่องหนักให้รันตัวนั้นซ้ำเดี่ยวก่อนสรุป ถ้าผ่านให้บอกในสรุป (แบบ NEW-110 NEW-131) · ห้ามข้ามหรือลบเทสต์
> 8. **ส่งงานเข้า main เมื่อผู้ใช้พิมพ์ `ส่งเข้า main ได้` ในแชตของสายนั้นเท่านั้น:** การ push เข้า main ทำให้ CI รัน (ราว 2 ชั่วโมง) และ deploy staging เมื่อผ่าน · แนะนำให้ส่งเมื่อสายทำครบทุกข้อที่ยืนยันแล้ว · ขั้นตอนตาม skill หัวข้อ 8 ข้อ 5 (`pnpm verify` และ `pnpm test:e2e --grep @demo` แล้ว `git push origin HEAD:main` · fast-forward เท่านั้น ห้าม `--force`) และก่อนขออนุญาตให้บอกจำนวน commit ที่จะขึ้นไป · `git push origin HEAD` เข้า branch ของสายเองทำได้ตลอด (CI ไม่รันบน branch นี้)
> 9. **main ระหว่างรอบนี้:** ไม่ทำข้อในตารางข้อ 1 · ทำงานอื่นได้ตามปกติ (เช่น NEW-127 ถึง NEW-131) · เมื่อสายส่งงานเข้า main แล้ว แชตบน main เริ่มด้วย `git pull --ff-only` · ถ้าไม่ผ่านเพราะ main บนเครื่องมี commit ที่ยังไม่ push ให้ `git pull --no-rebase` แล้ว `pnpm verify`

## ผลที่ตามมา

- แชตที่เปิดพร้อมกันได้สูงสุด 4 แชต: main กับ 3 สาย · ลำดับเปิดและคำสั่งอยู่ใน `docs/runbooks/parallel-lanes.md` หัวข้อ "สายรอบผู้ช่วย BCS"
- เวลาจริงเร็วขึ้นราว 2 เท่าเมื่อเทียบกับทำทีละข้อ ไม่ถึง 3 เท่า เพราะ e2e ต้องเข้าคิวและต้องรวมงาน · quota ถูกใช้เร็วขึ้นราว 3 เท่า
- ความถูกต้องไม่ลดลง: ทุกข้อผ่าน `pnpm verify` และ e2e ของข้อนั้น · ข้อเงินและสิทธิ์รีวิว `xhigh` ทันที (ADR-072)
- ผู้ใช้เลือกทุกข้อของรอบ (NEW-117 ถึง NEW-126) · ชุดประเมินจริงของ NEW-118 และ NEW-120 เรียก Claude และเสียค่า API ตามที่ผู้ใช้อนุญาต · สรุปของข้อนั้นบอกจำนวนครั้งที่เรียก
- เมื่อทุกสายส่งเข้า main แล้ว เส้นชัย A3 เหลือ P1-11 P1-12 บน main และ P1-13 ที่ผู้ใช้ซ้อมเอง · การลบสายต้องถามผู้ใช้ก่อน (CLAUDE.md หัวข้อ 2)
