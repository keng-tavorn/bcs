# ADR-085: เริ่มโค้ดระยะ 2 ก่อนเส้นชัย C ด้วย 3 สาย: l1 S7 · l2 S10 · l3 S11 · งานที่ไม่ต้องรอ S7 ทำก่อน และส่งฐาน S7 เข้า main ก่อนจบขั้น

- สถานะ: ยอมรับ (ผู้ใช้อนุมัติในแชตเมื่อ 2026-11-06)
- วันที่: 2026-11-06
- ที่มา: ผู้ใช้ถามว่าระยะ 2 ทำพร้อมกับการรอข้อมูลจริงได้ไหม เพราะลูกค้าน่าจะขอรายงาน pentest จากบุคคลที่สามก่อนส่งข้อมูลจริง (เส้นชัย B) · ปรับ §16.0 แถว 11–13 และเงื่อนไข "เริ่มได้เมื่อ" ของ S7-01 S10-01 S11-01 ที่ ADR-075 เขียนไว้ว่า "หลังเส้นชัย C"

## บริบท

- sub-spec ของ S7 S10 S11 ผู้ใช้อนุมัติแล้วทั้ง 41 เรื่องเมื่อ 2026-11-01 (ADR-075) · ลูกค้ายังไม่ตอบ OQ-181 ขึ้นไป จึงใช้ค่าที่อนุมัติ (= ค่าเริ่มต้นของ OQ) ไปก่อน
- เส้นชัย B รอลูกค้า และลูกค้าน่าจะขอรายงาน pentest ก่อนส่งข้อมูลจริง · C ต้องอยู่หลัง B เพราะ go-live ใช้ข้อมูลจริง · ถ้ารอ C ก่อนเริ่มระยะ 2 เวลาที่รอลูกค้าจะเสียเปล่า
- เส้นชัย A3 เหลือ P1-11 P1-12 บน main และ P1-13 ที่ผู้ใช้ซ้อมเอง · สาย l1 l2 l3 ว่าง ไม่มีงานค้าง (ส่งงาน ADR-080 เข้า main ครบแล้ว 2026-11-06)
- §16.19 ถึง §16.21 ให้ S10 และ S11 รอ S7-19 (S7 ทั้งขั้น) แต่ที่ S10 S11 ใช้จาก S7 จริงคือฐาน: ตารางและ enum ของ S7-01 · ชนิดเอกสาร `SUPPLIER_APPROVAL` (S7-02) · `normalizeScope` และ engine ของ S7-03 · ตัวตนพอร์ทัล (S7-04) · ใบสมัครและการเป็นผู้ขาย (S7-05) · เอกสารผู้ขายและ `supplierDocumentStatus` (S7-06)
- กฎ BR INV ของขั้น และ engine pure ใน `src/core` (S10-03 · S11-03) ไม่ต้องใช้ตารางใหม่ ทำได้ก่อน migration
- ระยะ 2 มีข้อ `xhigh` (เงิน สิทธิ์ DOA) 19 ข้อ: บัญชีธนาคารจากพอร์ทัล ผลมอบงานเป็น PO ด่านความเสี่ยงก่อนออก PO และการอนุมัติข้าม · การแยกเป็น 6 สายไม่เร็วขึ้นตามจำนวนสาย เพราะ S10 S11 รอฐาน S7 ทั้งสามขั้นแก้ไฟล์ DOA ชุดเดียวกัน และ Playwright รันพร้อมกันได้ไม่เกิน 2 ชุด

## ข้อความที่อนุมัติ

```text
เริ่มระยะ 2 ก่อน C แบบ 3 สาย ทำส่วนที่ไม่ต้องรอ S7 ก่อน แนะนำหน่อย แบ่งงานให้สายยังไง
```

```text

```

ข้อความที่สองตอบแผน 3 ช่วงที่ agent เสนอ (l1 ฐาน S7 แล้วส่งเข้า main ก่อน (agent ขยายฐานเป็น S7-01 ถึง S7-06 ตอนบันทึก เพราะ S10 S11 ใช้ `supplierDocumentStatus` ของ S7-06) · l2 l3 ทำส่วนที่ไม่ต้องรอ S7 · แล้วทำขนานเต็มที่) · ที่ต่างจากแผนที่เสนอ: P1-11 P1-12 อยู่บน main ตาม ADR-080 อยู่แล้ว สาย l2 l3 จึงเริ่มระยะ 2 ได้ทันที

## การตัดสินใจ

> 1. **ลำดับ:** โค้ดระยะ 2 เริ่มได้ตั้งแต่ 2026-11-06 ไม่ต้องรอเส้นชัย B C หรือลูกค้าตกลงขอบเขตระยะ 2 · เส้นชัย C ยังอยู่หลัง B · go-live ของระยะ 2 ยังต้องผ่านข้อ `[คน]` และ `[go-live]` ของแต่ละขั้น · main ทำ P1-11 P1-12 ต่อตามเดิม
> 2. **สาย:** ใช้ worktree branch (`p1/l1` `p1/l2` `p1/l3`) ฐานข้อมูล และพอร์ตเดิมของตารางสาย §16.13 · l1 = S7 (§16.19) · l2 = S10 (§16.20) · l3 = S11 (§16.21) · สั่งด้วย `ทำข้อถัดไปของเส้นชัย H` ในโฟลเดอร์ของสาย · เลข ADR และ OQ ใช้ช่วงของขั้นในตารางของ §16.19 (181–199 · 201–219 · 221–239) · งานที่พบเป็นข้อใหม่ท้ายขั้น
>
> | ช่วง | l1 · S7 | l2 · S10 | l3 · S11 |
> | --- | --- | --- | --- |
> | 1 | S7-01 → S7-06 (`xhigh` ยกเว้น S7-01 S7-03 S7-06) | ส่วนกฎของ S10-01 (BR INV ลง §7.23 · ไม่มี migration) → S10-03 | ส่วนกฎของ S11-01 (BR INV ลง §7.24 · ไม่มี migration) → S11-03 (ยกเว้นส่วนที่ import `normalizeScope` ของ S7-03) |
> | 2 | S7-25: รีวิวฐาน S7-01 ถึง S7-06 (`/code-review high main...HEAD`) แล้วส่งฐานเข้า main | รอ S7-25 · รวม main เข้าสาย | รอ S7-25 · รวม main เข้าสาย |
> | 3 | S7-07 → S7-19 | migration ของ S10-01 → S10-02 (ส่ง S10-02 เข้า main เร็วตามข้อ 5) → S10-04 → S10-21 | migration ของ S11-01 · ต่อ `normalizeScope` ใน S11-03 → S11-04 → … (S11-02 หลัง S10-02 เข้า main) → S11-17 |
>
> 3. **ข้อที่ทำได้ครึ่งเดียวในช่วง 1:** S10-01 และ S11-01 ทำส่วนกฎและโฟลเดอร์ก่อน commit แล้วต่อท้ายข้อด้วย `— ส่วนกฎเสร็จ <commit> · migration รอ S7-25` (คง `[ ]`) · S11-03 ที่เหลือแค่ `normalizeScope` ต่อท้าย `— รอ normalizeScope ของ S7-03 (S7-25)` · ข้อเหล่านี้ไม่นับเป็น "ติดอยู่" ตาม CLAUDE.md หัวข้อ 13 และติ๊กเมื่อส่วนที่เหลือเสร็จ · engine pure ไม่ import Prisma ตามกฎ §4.10 อยู่แล้ว
> 4. **ที่จองไว้ให้แต่ละขั้น (agent หลักจองแล้วใน commit ของ ADR นี้):** หัวข้อ §7.22 (S7) §7.23 (S10) §7.24 (S11) และบล็อก `// --- S7 ---` `// --- S10 ---` `// --- S11 ---` ใน model ที่หลายขั้นแก้ของ `prisma/schema.prisma` (Organization Member Event FileObject RequestType Request RequestLine ApprovalRoute BudgetLine Supplier PurchaseOrder Invoice BankAccountChange) · สายแก้เฉพาะบล็อกของขั้นตัวเอง · model ใหม่วางท้ายไฟล์ · ไฟล์ร่วมอื่น (`permissions.ts` `DOC_TYPE_TRAITS` event คีย์ข้อความ แถวใน spec `feature-status.yaml` `ac-map.yaml`) แก้แบบเพิ่มต่อท้าย · conflict ตาม skill `bcs-lane` หัวข้อ 5
> 5. **ส่งเข้า main:** เมื่อผู้ใช้พิมพ์ `ส่งเข้า main ได้` ในแชตของสายนั้นเท่านั้น (เหมือน ADR-080 ข้อ 8) · จุดส่งที่ตั้งใจ: S7-25 (ฐาน S7) · S10-02 (เพื่อให้ S11-02 เรียงชนิดเอกสาร `RFX_AWARD` ก่อน `RISK_OVERRIDE`) · ข้อรีวิวท้ายขั้น S7-19 S10-21 S11-17 · ก่อนส่ง: `pnpm verify` และ `pnpm test:e2e --grep @demo` และ `--grep @p1demo` ผ่าน (ระยะ 1 ต้องไม่เสีย)
> 6. **ช่วง pentest:** push เข้า main ทำให้ staging เปลี่ยนเมื่อ CI ผ่าน · เมื่อผู้ใช้แจ้งว่าบริษัททดสอบเริ่มทดสอบ staging สายหยุดส่งเข้า main จนผู้ใช้แจ้งว่าจบ แต่ทำงานในสายต่อได้ · ส่งไม่ได้แล้วงานของสายอื่นรอ (เช่น S7-25) → บอกผู้ใช้ใน "รอคุณ"
> 7. **effort และการตรวจ:** ตามตาราง effort ของแต่ละขั้น · ข้อ `xhigh` รีวิวทันทีตาม ADR-072 (`/code-review xhigh <ฐาน>...HEAD` บันทึกใน `docs/reports/p2-review-<ขั้น>.md` แล้วจึงติ๊ก) · ข้ออื่นไม่รีวิวซ้ำ · ไม่มีบรรทัด "ตรวจก่อน:" ในสาย · e2e ตาม ADR-080 ข้อ 7 (ทั้งเครื่องไม่เกิน 2 ชุด main ก่อน)
> 8. **แชตแรกของแต่ละสายในรอบนี้:** `pnpm lane:check` → รวม main เข้าสาย (skill หัวข้อ 2) → `pnpm install` → `pnpm messages:build` → `pnpm db:reset` (ฐานของสาย) → `pnpm verify` แล้วจึงเริ่มข้อ

## ผลที่ตามมา

- เวลาโค้ดระยะ 2 ประมาณ 1.5–2 สัปดาห์ แทนการเริ่มหลัง C · เวลารอลูกค้าที่ B และรอ pentest ใช้ทำระยะ 2 ได้
- ถ้าลูกค้าตอบ OQ ของระยะ 2 ต่างจากค่าที่อนุมัติ ต้องกลับมาแก้บางจุดหลัง B (ความเสี่ยงที่ผู้ใช้รับแล้ว)
- quota ถูกใช้เร็วขึ้นราว 3 เท่าเมื่อสามสายทำพร้อมกัน · ผู้ใช้ดูแล 3 แชตพร้อมกับแชตบน main
- การส่งฐาน S7 ก่อนจบขั้นทำให้ main มีตารางและคำสั่งของ S7 ที่ยังไม่มีหน้าจอครบ · ฉาก demo ระยะ 1 (`@demo` `@p1demo`) ต้องผ่านก่อนส่งทุกครั้ง (ข้อ 5) จึงไม่กระทบ demo ที่จะให้ลูกค้าดู
- pentest รอบแรกทดสอบระยะ 1 · พอร์ทัลผู้ขายของระยะ 2 ควรอยู่ในการทดสอบรอบถัดไปก่อนเปิดใช้ (ผู้ใช้ตัดสินกับบริษัททดสอบ)
