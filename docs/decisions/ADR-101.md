# ADR-101: อนุมัติคู่ขนานและกรรมการด้วย slot

- สถานะ: เสนอ (ร่าง P1-04 · รอผู้ใช้อนุมัติใน P1-06)
- วันที่: 2026-10-11
- ที่มา: docs/sub-specs/S6.md หัวข้อ "Entity และ migration" "State machine" และ "กฎ" (BR-WF-01 ถึง BR-WF-06) · ข้อ P1-04

## บริบท

- ชั้น 1 มีผู้อนุมัติหนึ่งคนต่อขั้น และการตัดสินแรกของขั้นคือผลของขั้น (BR-SLA-04 · `completeStep`) ใช้ร่วม 4 flow และปุ่ม LINE กับลิงก์อีเมล
- FR-WF-101 ต้องการผู้ตรวจหลายฝ่ายพร้อมกันแบบครบทุกคน คนใดคนหนึ่ง หรือตามจำนวน และ FR-WF-102 ต้องการคณะกรรมการแบบองค์ประชุมหรือเสียงข้างมาก
- golden GC-DOA-01 ถึง 27 และฉาก `@demo` ต้องไม่เปลี่ยน · `next-step.ts` หาผู้อนุมัติขั้นถัดไปด้วย stepNo ของ `resolveRoute` ซึ่งจะเลื่อนเมื่อมีขั้นผู้ตรวจนำหน้า

## การตัดสินใจ

> อนุมัติคู่ขนานและกรรมการใช้ slot: `ApprovalTask.slotNo` · การตัดสินแรกของ slot คือผลของ slot · `stepOutcome` เป็น pure function ใน `src/core` ที่คิดผลต่อกลุ่ม (ขั้น REVIEW มีหลายกลุ่ม ALL ANY COUNT) · step เดิมทั้งหมดเป็น slot เดียวจึงทำงานเหมือนเดิม · ผู้ตรวจหาด้วย engine แยกแล้วต่อหน้าขั้น DOA ใน service และขั้น DOA หาผู้อนุมัติด้วย doaStepNo โดยไม่เปลี่ยนผลของ `resolveRoute` สำหรับ step ผู้อนุมัติคนเดียว

## ผลที่ตามมา

- `ApprovalTask.slotNo` default 1 และ `ApprovalStep.kind` `doaStepNo` `reviewGroups` เพิ่มใน migration ของ S6-01 · ขั้นเดิม backfill doaStepNo = stepNo
- `stepOutcome` คิดผลต่อกลุ่มด้วยกติกาเดียว ขั้น APPROVAL มีกลุ่มเดียว ขั้น REVIEW มีกลุ่มต่อข้อ ALL หนึ่งกลุ่มรวมของข้อ ANY และกลุ่มต่อข้อ COUNT · golden GC-WF-01 ถึง 18 และ 31 ถึง 34
- S6 แก้เฉพาะ `step-complete.ts` และ `next-step.ts` · decide flow ต้องเปลี่ยนสถานะตามผลของ step ซึ่งเป็นงานของ P1-07 ในไฟล์กลาง
- property test เทียบ engine ใหม่กับสำเนา engine เดิมเป็นด่านของ INV-WF-01
