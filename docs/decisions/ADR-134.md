# ADR-134: S9 เรียกฟังก์ชันของ S8 ในธุรกรรมเดียวกัน และส่งอีเมลผู้ขายผ่าน SupplierNotice

- สถานะ: ยอมรับ (ร่าง P1-04 · ผู้ใช้อนุมัติตามที่แนะนำใน P1-06 เมื่อ 2026-10-12)
- วันที่: 2026-10-11
- ที่มา: docs/sub-specs/S9.md หัวข้อ "interface กับขั้นอื่นและความเสี่ยง" และ BR-PAY-03 BR-PAY-12 BR-PAY-13 · คำตัดสินของ agent หลักข้อ 10 · ข้อ P1-04

## บริบท

- การถือ ปล่อย และจ่ายใบแจ้งหนี้และเงินประกันผลงานเปลี่ยนสถานะของ S8 (`IN_PAYMENT_RUN` `PAID`) และต้องเกิดพร้อมสถานะของรอบจ่าย ไม่เช่นนั้นจ่ายซ้ำได้ (INV-PAY-01)
- การบันทึกจ่ายต้องออกภาษีหัก ณ ที่จ่ายและ 50 ทวิ หนึ่งฉบับต่อรายการจ่าย (กฎของ S8) ในธุรกรรมเดียวกับผลการจ่าย
- `runCommand()` ซ้อนกันจะได้ธุรกรรมและ event แยก ถ้าตัวนอกล้มตัวในอาจค้างอยู่
- อีเมลที่ส่งในธุรกรรมแล้วธุรกรรมล้ม จะทำให้ผู้ขายได้อีเมลของการจ่ายที่ไม่เกิดขึ้น · S8 มีตาราง `SupplierNotice` และงานส่งจาก outbox พร้อม dedupeKey ให้ขั้นอื่นใช้แล้ว

## การตัดสินใจ

> การเรียกจาก S9 ไป S8 (ถือ ปล่อย และบันทึกจ่ายใบแจ้งหนี้และเงินประกันผลงาน ออกภาษีหักและ 50 ทวิ สร้างอีเมลถึงผู้ขาย) เป็นฟังก์ชัน service ของ S8 ที่รับ `tx` ในธุรกรรมเดียวกับคำสั่งของ S9 ไม่ใช่ `runCommand()` ซ้อน · บันทึกจ่ายใช้ `recordInvoicePayment` ตัวเดียวครั้งเดียวต่อรายการ (ใบและเงินประกันของรายการรวมกัน) · อีเมลถึงผู้ขายเป็นแถว `SupplierNotice` ที่สร้างด้วย `enqueueSupplierNotice` ของ S8 แล้วงานส่งของ S8 ส่งจาก outbox ไม่ส่งในธุรกรรมของคำสั่ง และ S9 ไม่มีงานส่งของตัวเอง

## ผลที่ตามมา

- S9 เรียก `holdInvoicesForPayment` `releaseInvoicesFromPayment` `holdRetentionsForPayment` `releaseRetentionsFromPayment` และ `recordInvoicePayment` (ครั้งเดียวต่อรายการ พร้อมใบ เงินประกัน และบรรทัดภาษีของรายการ) ภายในธุรกรรมของคำสั่ง S9 · แต่ละฟังก์ชันเขียน event ของ S8 เอง · ไม่มีฟังก์ชันบันทึกจ่ายเงินประกันแยก
- ธุรกรรมที่ล้มกลางทางไม่เปลี่ยนอะไรทั้งฝั่ง S8 และ S9 (เทสต์ใน S9-08)
- อีเมลแจ้งการชำระ (`payment.advice`) และแจ้งเปลี่ยนบัญชี (`bank_account.notice`) เป็นแถว `SupplierNotice` ที่สร้างในธุรกรรมด้วย `enqueueSupplierNotice(tx, ctx, { templateKey, supplierId, subjectType, subjectId, dedupeKey, data })` ของ S8 · งานส่งของ S8 ส่งหลัง commit และกันส่งซ้ำด้วย dedupeKey · สถานะอ่านจาก `SupplierNotice`
- S9 ไม่มีงาน Inngest ของตัวเองในชั้น demo · ส่งไม่สำเร็จใช้ event `supplier_notice.failed` ของ S8 เพื่อแจ้งผู้เตรียม
- ชื่อและพารามิเตอร์ของฟังก์ชันต้องตรวจไขว้กับ S8 ก่อน S9-01 (P1-05)
