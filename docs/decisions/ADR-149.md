# ADR-149: ช่องข้อความที่ว่างได้ส่งเป็น "" ใน schema ของ API และรุ่นโมเดลต่อ purpose

- สถานะ: ยอมรับ (S13-13 · ตามกติกา "ใช้รุ่นที่ถูกกว่าที่ผ่านเกณฑ์" ของ OQ-145)
- วันที่: 2026-10-14
- ที่มา: ข้อ S13-13 S13-14 · `docs/reports/p1-ai-eval.md`

## บริบท

- วัดผลกับ Claude จริงครั้งแรก (S13-13) พบว่า Messages API ปฏิเสธ schema ของผลอ่านเอกสาร (`DocumentReading`) ด้วย 400: structured outputs รับ parameter ที่เป็น union ได้ไม่เกิน 16 ตัว (`["string","null"]` นับเป็นหนึ่ง) แต่ schema มี 17 · โหมด live ของ Document Agent จึงไม่เคยทำงาน เทสต์ทั้งหมดผ่านเพราะรันโหมด fixture
- รุ่นโมเดลตั้งต่อ agent (`AI_MODEL_DOCUMENT`) แต่ผลวัดต่างกันตาม purpose: Sonnet ผ่านใบเสนอราคาและใบส่งของ แต่อ่านเลขที่ใบกำกับที่ภาพเบลอผิด (DOC-030 · ฟิลด์สำคัญ 95.65% < 98%) ขณะที่ Opus ผ่านทุกชนิด

## การตัดสินใจ

> adapter แปลง schema ก่อนส่ง: ทุกช่องข้อความที่ว่างได้ส่งเป็น string ที่ "" แปลว่าไม่มีหรือไม่ปรากฏ แล้วแปลง "" กลับเป็น null เฉพาะช่องเหล่านั้นก่อนตรวจด้วย Zod schema เดิม (`src/integrations/ai/wire-schema.ts`) · โค้ดส่วนอื่นยังเห็น null เหมือนเดิม · รุ่นโมเดลมีค่าเริ่มต้นต่อ purpose ได้ (`modelForPurpose`) โดยตัวแปรของ agent และ `AI_MODEL_DEFAULT` ยังชนะ · ใบแจ้งหนี้ใช้ `claude-opus-5-5` purpose อื่นของ Document Agent ใช้ `claude-sonnet-5-5`

## ผลที่ตามมา

- prompt ที่เคยบอกให้ตอบ null เปลี่ยนเป็น "" จึงขึ้นรุ่น prompt ใหม่ (`@2`) และวัดผลใหม่ทั้งหมดก่อนบันทึก gate (BR-AI-09)
- เทสต์ใน `tests/unit/ai-adapter.test.ts` ตรวจว่าทุก schema ของ agent อยู่ในเพดาน 16 ตัว · schema ใหม่ที่เกินจะล้มในเทสต์ก่อนถึง API
- gate ผูกกับ purpose อยู่แล้ว (ADR-143) จึงรับรุ่นต่อ purpose ได้โดยไม่เปลี่ยนโครงสร้าง · ตั้ง `AI_MODEL_DOCUMENT` เป็นรุ่นเดียว ใบแจ้งหนี้จะตอบ `AI_NOT_EVALUATED` จนกว่าวัดรุ่นนั้นผ่าน
- ต้นทุนอ่านใบแจ้งหนี้ประมาณ 24 credits ต่อฉบับ (Sonnet ประมาณ 13)
