# ADR-165: push ผ่าน FCM HTTP v1 โดยไม่เพิ่ม dependency

- สถานะ: เสนอ (ร่าง P1-04 · รอผู้ใช้อนุมัติใน P1-06)
- วันที่: 2026-10-11
- ที่มา: docs/sub-specs/S17.md หัวข้อ "กฎ" (BR-NOTI-05 ถึง BR-NOTI-08 · BR-APP-12) และ golden `notification-route` · ข้อ P1-04

## บริบท

- FR-PLT-301 ให้ push เป็นช่องทางที่สามของ Notification service (§4.7) · OQ-164 แนะนำ FCM HTTP v1 · OQ-165 แนะนำให้ push แทน LINE เมื่อผู้ใช้เปิดในแอป
- `firebase-admin` ไม่อยู่ในตาราง §5.5 · token ของเครื่องเป็นข้อมูลที่ต้องเข้ารหัสและห้าม log (NFR-SEC-07 NFR-SEC-09)
- ขั้นอื่น (S6 S8 S9) เพิ่ม template ใน `LINE_TEMPLATES` ซึ่งเป็นชุดของ string จึง typecheck จับไม่ได้ว่าลืมข้อความ push

## การตัดสินใจ

> push: adapter `src/integrations/push` ส่ง FCM HTTP v1 ด้วย fetch และ OAuth JWT ที่เซ็นด้วย node:crypto (ไม่เพิ่ม dependency) มี fake ใน fake LINE server เดิม (path `/fcm/` ไม่เพิ่มพอร์ตของสาย) · token เข้ารหัส AES-256-GCM + sha256 · `NotificationChannel.PUSH` · `deliverNotification` เลือกช่องทางด้วย pure function ใน `src/core/notification-route` · ข้อความ push สร้างด้วยตัวสร้างเดียวจากคีย์ `push.<templateKey>.title`

## ผลที่ตามมา

- ลำดับส่ง PUSH → LINE → อีเมลสำหรับผู้ที่เปิดในแอป · ผู้ที่ไม่เปิดได้ทางเดิมทุกประการ · ต้องแก้ §4.7 ข้อ 2 และถ้อยคำในแถว §5.5 ใน S17-10
- เนื้อหาบนหน้าจอล็อกมีแค่ชนิดงานและเลขเอกสาร (เข้มกว่า BR-NOTI-01 · คำถามรวมกับการ์ด LINE ใน OQ-107 ของ S6)
- template ที่ไม่มีคีย์หัวเรื่องใช้ข้อความกลาง และเทสต์วนทุก template ใน `LINE_TEMPLATES` จึงล้มเมื่อขั้นใดลืมเพิ่มคีย์
- e2e ใช้ fake FCM ในพอร์ตเดิมของ fake LINE · demo บนเครื่องจริงต้องมี Firebase project ของ BCS (runbook ของ S17-17)
- Google เพิ่มในรายการ sub-processor (NFR-PRIV-06)
