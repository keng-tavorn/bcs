# ADR-174: ค่าตั้งของ S17 ใน UAT sandbox — ขอผ่านแชทปิด ไม่ส่ง push ค่าตั้งของแอปคัดลอกตาม production

- สถานะ: ยอมรับ (agent ตัดสินตามกฎเดิม BR-UAT-01 ใน S17-01 · ทางที่ปลอดภัยที่สุด · ผู้ใช้ทบทวนได้ใน P1-10)
- วันที่: 2026-10-16
- ที่มา: spec §16.18 ข้อ S17-01 ("ค่าตั้งใหม่ `chatIntake` และ `bcsGo` ทำงานกับ UAT sandbox ของ S6") · BR-UAT-01 · ADR-110

## บริบท

- UAT sandbox ของ S6 (S6-21) เป็นองค์กร `kind = SANDBOX` ที่คัดลอกค่าตั้งของ production ตอนสร้าง โดยปิด LINE (`features.lineChannel = false`) · `deliverNotification` ไม่ส่ง LINE ให้องค์กร SANDBOX และอีเมลขึ้นต้น "[UAT]" (BR-UAT-01)
- S17 เพิ่มค่าตั้ง `chatIntake` (ขอผ่านแชท LINE) และ `bcsGo` (สำเนาและคิวของแอป) และช่องทาง push ของแอป BCS Go
- ค่าตั้งเหล่านี้แก้ได้จาก seed หรือชีต Settings เท่านั้น (`organization.save_settings` แก้ได้เฉพาะปฏิทินและเลขที่เอกสาร) จึงจุดที่ค่าเข้า sandbox มีสองจุด: คำสั่ง `organization.create_sandbox` และ seed ของ `SIMEC-UAT`

## การตัดสินใจ

> ค่าตั้งของ sandbox สร้างด้วยฟังก์ชันเดียว `sandboxSettingsOf` (`src/lib/uat.ts`) ทั้งในคำสั่งสร้าง sandbox และ seed: คัดลอกค่าตั้งของ production ทั้งหมด แล้วปิด LINE และตั้ง `chatIntake.enabled = false` (ค่าอื่นของ `chatIntake` และ `bcsGo` ทั้งก้อนคัดลอกตามเดิม) · ตอนอ่าน `chatIntakeSettingsFor` ถือว่าองค์กร SANDBOX ปิดขอผ่านแชทเสมอแม้ค่าที่เก็บจะเปิด · push ของแอปไม่ส่งในองค์กร SANDBOX แบบเดียวกับ LINE (ส่งทางอีเมล "[UAT]" แทน) · หน้า `/go/receive` และค่าตั้ง `bcsGo` ใช้ได้ใน sandbox ตามปกติ เพราะเป็นเว็บที่ไม่ส่งข้อความออกนอกระบบ

## ผลที่ตามมา

- ไม่มีข้อความ LINE หรือ push จากระบบทดลองที่ผู้ใช้อาจเข้าใจว่าเป็นของจริง (เจตนาเดียวกับ "[UAT]" ของอีเมล)
- ลูกค้าลองขอผ่านแชทและ push ใน sandbox ไม่ได้ ต้องลองกับ channel ของ BCS ในชั้น demo (D-03) หรือหลัง go-live · ถ้าลูกค้าต้องการลองใน sandbox ต้องเปิด OQ ใหม่
- S17-06 อ่านสวิตช์ขอผ่านแชทด้วย `chatIntakeSettingsFor` (ไม่ใช่ `chatIntakeSettingsOf` ตรง ๆ) · S17-10 (สาย 1) เพิ่มเงื่อนไข "ไม่ใช่ SANDBOX" ในการเลือกช่องทาง push ตาม BR-NOTI-05
