# ADR-175: ขอผ่านแชท LINE — การตัดสินใจระหว่างสร้าง (S17-06 ถึง S17-08)

- สถานะ: ยอมรับ (agent ตัดสินตาม spec และผลรีวิว xhigh ของแต่ละข้อ · ผู้ใช้ทบทวนได้ใน P1-10)
- วันที่: 2026-10-16
- ที่มา: spec §16.18 ข้อ S17-06 S17-07 S17-08 · BR-LINE-10 ถึง BR-LINE-15 · ADR-162 · OQ-162 · `docs/reports/p1-review-S17.md`

## บริบท

ADR-162 ตัดสินแนวทางขอผ่านแชท (ร่างใน LIFF ทางเดียว AI เป็นส่วนเสริม) · ระหว่างสร้างมีเรื่องที่ spec ไม่ได้ระบุละเอียด ต้องเลือกทางที่ปลอดภัยและดูแลง่าย และควรบันทึกไว้ให้การรีวิวทั้งขั้น (S17-18 สาย 1) และงานถัดไปไม่ต้องอ่านจากโค้ด

## การตัดสินใจ

1. **เวลาของข้อความ** = timestamp ที่ LINE บอกว่าผู้ใช้ส่ง (ใช้เวลาที่รับเมื่อ LINE ไม่บอกหรือบอกช้ากว่า) ใช้กับช่วงเติมร่าง `lastMessageAt` และอายุร่าง · reply token นับจากเวลาที่รับ · เหตุ: ร่างตามสิ่งที่ผู้ใช้ทำ ไม่ใช่เวลาที่ job ลองซ้ำ
2. **การนับ `hourlyLimit`** = ข้อความที่รับเข้าร่าง และที่ตอบปฏิเสธด้วยคำแนะนำหรือเพดานรูป ในชั่วโมงก่อนหน้า (จาก Event) · ข้อความที่ถูกปฏิเสธเพราะส่งถี่ไม่นับ จึงรับใหม่ได้หนึ่งชั่วโมงหลังข้อความที่ทำให้ถึงเพดาน · ทุกข้อความที่ไม่รับยังมี `chat_intake.message_refused` เป็นหลักฐาน
3. **ล้างรูป** ตาม OQ-162: ร่างที่ปิดแล้วและเปิดมาเกิน `textRetentionDays` ล้างข้อความ และรูปที่ไม่มีเอกสารใช้ (ไม่มี FileLink) ลบออกจาก bucket หลัง commit และตั้ง `FileObject.status = REJECTED` (ไม่เพิ่มค่า enum ใหม่ใน migration · ไม่มีทางดาวน์โหลดไฟล์ที่ไม่ใช่ AVAILABLE) · `chat_intake.purged` บอก `fileIds` · ผลอ่านของ AI ที่ยังเป็นของร่างล้างในธุรกรรมเดียวกัน (`purgeChatIntakeAiContent` ของ S13)
4. **job รายชั่วโมงทำทุกองค์กรทุกสถานะ** (รวมองค์กรที่ถูกพัก) เพราะระยะเก็บข้อมูลส่วนบุคคลใช้กับทุกองค์กร · เวลาอ่านครั้งเดียวต่อ run ชั่วโมงจึงเป็น idempotency key ของทุก step ที่ลองซ้ำ · บน staging รันทุก 3 ชั่วโมง (แนวเดียวกับ ADR-054 · ไม่มีข้อมูลจริงตาม OQ-19)
5. **รูปที่ดึงเสร็จหลังเจ้าของสร้างร่างคำขอ** แนบเข้าคำขอเป็น OTHER เอง (ถ้าคำขอยังเป็นร่างหรือถูกตีกลับ และไม่เกินจำนวนไฟล์) · คำขอที่ส่งแล้วคงตามที่ส่ง · ร่างที่ล้างแล้วไม่รับรูปใหม่
6. **ค่าของ AI ใน LIFF**: รายการที่ AI อ่านใช้ทั้งชุดหรือไม่ใช้เลย (ไม่ให้รายการเลื่อนตำแหน่งจน path ไม่ตรงกับที่เสนอ) · ค่าที่ไม่ต้องยืนยันทีละช่องนับว่ายืนยันเมื่อเจ้าของเลือกใช้ · ประเภทที่ AI เสนอนับว่ายืนยันเมื่อเจ้าของเลือกประเภทนั้น · ค่าตาม BR-AI-16 รอยืนยันในหน้าแก้ร่าง LIFF ด้วย `request.edit` + `aiAssist` · หน้า LIFF แสดง `pendingPaths` ซึ่งคำนวณด้วยกติกาเดียวกับ `request.submit`
7. **ผลอ่านของร่างจากแชทเป็นของเจ้าของ**: `applyAiAssist` รับผลอ่านที่ subject เป็น `CHAT_INTAKE` เฉพาะจากผู้เรียก (ผู้อื่น `NOT_FOUND`)
8. **การผูกผลอ่าน**: ผลอ่านที่เก่ากว่าไม่ทับผลอ่านที่ใหม่กว่า (id uuid v7) · ผลอ่านที่ล้มถูกผูกไว้และไม่อ่านซ้ำด้วย key เดิมจนกว่าจะมีข้อความใหม่ (key ตาม BR-LINE-13)

## ผลที่ตามมา

- การตัดสินใจทั้งหมดอยู่ในขอบเขตของ spec เดิม ไม่เปลี่ยนกฎเงิน อำนาจ หรือขอบเขต
- ถ้าภายหลังต้องการสถานะไฟล์ "ถูกล้าง" แยกจาก REJECTED ต้องเพิ่ม enum ใน migration ใหม่และย้ายแถวที่มี `chat_intake.purged` อ้าง `fileIds`
- เรื่องที่ไม่แก้และเหตุผลอยู่ใน `docs/reports/p1-review-S17.md` (S17-06 ข้อ 6 · S17-08 ข้อ 3 4)
