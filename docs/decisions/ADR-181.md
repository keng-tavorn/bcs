# ADR-181: ใบสมัครผู้ขายแยกจากทะเบียนผู้ขาย และกลายเป็นผู้ขายเมื่ออนุมัติ

- สถานะ: ร่าง ADR-075 (2026-11-01) รอผู้ใช้อนุมัติ
- วันที่: 2026-11-01
- ที่มา: docs/sub-specs/S7.md หัวข้อ "ขอบเขต" "Entity และ migration" และ "State machine" · ผู้ใช้สั่งออกแบบระยะ 2 ก่อนจบ A3 และ C (ADR-075)

## บริบท

- CORE มี `Supplier` ตั้งแต่ S4 (unique `(org, taxId, branchCode)` · ตรวจทะเบียนตาม BR-SUP-01 ถึง BR-SUP-05) และคำขอ `NEW_SUPPLIER` ของชั้น 1 ที่เข้าคิวจัดซื้อโดยไม่ผ่าน DOA (OQ-23) · ระยะ 1 จัดซื้อสร้างผู้ขายเองในหน้าทะเบียน
- FR-SUP-101 ถึง FR-SUP-104 ต้องให้ผู้ขายกรอกเอง มีเอกสารที่ต้องยืนยัน และอนุมัติผ่าน DOA ก่อนเป็นผู้ขายที่สั่งซื้อได้ · §6.5 จองชื่อ `SupplierApplication` ไว้แล้ว
- ถ้าให้ผู้ขายแก้แถว `Supplier` โดยตรงระหว่างสมัคร ผู้ขายที่ยังไม่อนุมัติจะปรากฏในตัวเลือกของ PO ทันที และผู้ขายซ้ำจะชน unique ก่อนจัดซื้อได้ตัดสิน · ถ้าทำสำเนาข้อมูลผู้ขายไว้สองตาราง S8 S9 S10 S11 ต้องเลือกว่าอ่านตารางไหน

## การตัดสินใจ

> ใบสมัครผู้ขาย (`SupplierApplication`) เป็นเอกสารแยกจาก `Supplier` ของ CORE ไม่ทำสำเนา: ผู้ขายกรอกและส่ง จัดซื้อยืนยันเอกสารและส่งเข้าเส้นทาง เมื่ออนุมัติจึงสร้างแถว `Supplier` ACTIVE หรือผูกผู้ขายเดิม (kind EXISTING) · คำขอ `NEW_SUPPLIER` ของชั้น 1 ยังอยู่และเป็นต้นทางให้จัดซื้อเชิญเมื่อเปิด `SUPPLIER` · เลขใบสมัคร `SUP-{BE}-{SEQ5}` ออกตอนส่ง · ใบที่ไม่ APPROVED ไม่มีแถว `Supplier` (INV-SUP-02)

- สถานะของใบสมัคร: `INVITED → DRAFT → SUBMITTED → PENDING_APPROVAL → APPROVED` และ `RETURNED` `REJECTED` `EXPIRED` `CANCELLED` ตามตารางใน sub-spec · ทุกการเปลี่ยนผ่าน `runCommand()` มี Event
- การอนุมัติทำในธุรกรรมเดียวของ `decide` (adapter): สร้าง `Supplier` ด้วย helper ระดับธุรกรรม `createSupplierInTx(tx, ctx, input)` ที่ S7-05 แยกออกจาก `createSupplierCommand.execute` ของ CORE (เพราะ `createSupplier()` เป็น `runCommand` ที่เปิดธุรกรรมเองและ `CreateSupplierInput` ไม่รับ `registry*` `payeeType` `defaultWhtIncomeTypeCode` `paymentTermDays` `portalEnabled` · ขยาย input โดยเทสต์ `supplier.create` เดิมไม่เปลี่ยน · code จาก `suggestSupplierCode` เดิม · `registryStatus registrySource registryData registryCheckedAt` คัดลอกจากใบตรง ๆ ไม่ตรวจทะเบียนใหม่) · event `supplier.created` ใช้ฟิลด์ `via` เดิมขยาย enum เป็น `'APPLICATION'` (schemaVersion 2) · ย้าย `SupplierContact` และ `SupplierDocument` ไปที่ผู้ขาย และสร้าง `BankAccountChange` source PORTAL (`submittedById` ว่าง) เมื่อใบมีบัญชี (ADR-190)
- เชิญผู้ขายเดิมเข้าพอร์ทัล = ใบสมัคร kind `EXISTING` ที่ผูก `supplierId` ไม่ผ่านการอนุมัติซ้ำ (ผู้ขายอนุมัติอยู่แล้วตอนสร้างในชั้น 1) · state machine มีแถว INVITED (EXISTING) → APPROVED ในธุรกรรมของ `portal.verifyOtp` ครั้งแรก ไม่ออกเลข SUP มี event · ต้องแจ้งอีเมลในทะเบียนตาม BR-SUP-17 (ADR-190)

## ผลที่ตามมา

- `Supplier` ยังเป็นตารางหลักเดียวที่ S8 S9 S10 S11 อ่าน · ตัวเลือกผู้ขายในฟอร์มคำขอและ PO ไม่เปลี่ยน
- ใบสมัครที่เปิดอยู่มีได้ใบเดียวต่อ (taxId, branchCode) ด้วย partial unique · unique ของ `Supplier` ยังเป็นด่านสุดท้ายของผู้ขายซ้ำ (ADR-186)
- `Supplier` เพิ่มคอลัมน์ `applicationId` `portalEnabled` `onboardedAt` ใต้บล็อก `// --- S7 ---`
- คำขอ `NEW_SUPPLIER` (RQ) ไม่เปลี่ยน state machine · หน้าคำขอมีปุ่ม "เชิญผู้ขาย" ที่พาไป `/suppliers/invite` พร้อมค่าตั้งต้น และคำขอเป็น DONE เมื่อใบสมัคร APPROVED (S7-05 เพิ่ม hook อ่าน event ไม่แก้คำสั่งของ RQ)
- ถ้าผู้ใช้เลือกให้ผู้ขายแก้ `Supplier` ตรง: ต้องเพิ่มสถานะ `PENDING` ใน `SupplierStatus` และกรองทุกที่ที่เลือกผู้ขาย (แตะโค้ดเดิมหลายจุด) จึงไม่แนะนำ
