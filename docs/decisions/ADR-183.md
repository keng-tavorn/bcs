# ADR-183: ตัวตนและ session ของพอร์ทัลผู้ขายเป็นของ BCS เอง (ลิงก์ + OTP)

- สถานะ: ยอมรับ (ร่าง ADR-075 · ผู้ใช้อนุมัติตามที่แนะนำเมื่อ 2026-11-01)
- วันที่: 2026-11-01
- ที่มา: docs/sub-specs/S7.md หัวข้อ "Entity และ migration" "State machine" และ "กฎ" (BR-PORTAL-01 ถึง BR-PORTAL-06) · ADR-007 ที่บอกให้ sub-spec S7 กำหนดช่องทาง OTP · ADR-075

## บริบท

- ADR-007 ตัดสินแล้วว่าพอร์ทัลเข้าด้วยลิงก์ + OTP 6 หลัก อายุ 10 นาที ผิดได้ 5 ครั้ง และใช้ session แยกจากผู้ใช้ภายในโดยสิ้นเชิง (§9.8 · NFR-SEC-05) แต่ไม่ได้ระบุช่องทางส่ง OTP และวิธีเก็บ session
- ผู้ใช้ภายในใช้ Better Auth (`Member.userId`) · ถ้าให้ผู้ขายเป็น user ของ Better Auth ด้วย จะมีตารางผู้ใช้ร่วม สิทธิ์และ middleware ร่วม และต้องกันไม่ให้ผู้ขายกลายเป็น member ด้วยกฎเพิ่ม · passkey ของ S17 ก็เลือกตรวจในคำสั่งของ BCS แทนปลั๊กอิน (OQ-167)
- `Event.actorType` มี `SUPPLIER` และ `channel` มี `PORTAL` อยู่แล้ว (§4.5) แต่ไม่มีคอลัมน์บอกว่าผู้ติดต่อคนไหน (มีแค่ `actorMemberId` `actorPlatformAdminId`)
- SMS ต้องซื้อบริการและเป็น dependency ใหม่ด้าน auth ที่ต้องให้ผู้ใช้ยืนยัน (§5.5) ส่วนอีเมลผู้ขายมีอยู่ในทะเบียนแล้ว (รับ PO และอีเมลของ S8 S9)

## การตัดสินใจ

> ตัวตนพอร์ทัลเป็นของ BCS เอง ไม่ใช้ Better Auth: ทุก route ของพอร์ทัลมีองค์กรใน path `/portal/[org]/…` · `SupplierContact` + ลิงก์ใช้ครั้งเดียว (`PortalInviteLink`) + OTP 6 หลัก (`PortalOtpChallenge` · อีเมลเป็นค่าเริ่มต้นตาม OQ-181 · ผูกอุปกรณ์ที่ขอ) + `PortalSession` cookie `bcs_portal` path `/portal/<org>` idle 30 นาที สูงสุด 24 ชั่วโมง + CSRF token ผูก session · rate limit ใน `PortalRateLimit` (ผูก tenant) และ `PortalIpRateLimit` (global ไม่มี `organizationId`) · Event ของพอร์ทัลใช้ `actorType = SUPPLIER` กับคอลัมน์ใหม่ `Event.actorSupplierContactId` (เพิ่มได้ทันทีเพราะ main ยังไม่มี `EventSeal`) · ไม่มี endpoint ใต้ `/api/auth/*` · ไม่มี session ร่วมกับ Workspace (ADR-007)

- องค์กรใน path: `[org]` = `Organization.code` ตัวพิมพ์เล็ก (ลิงก์เชิญและลิงก์เข้าระบบฝัง org เสมอ) จึงรู้ `organizationId` ตั้งแต่คำขอแรก `requireModule(SUPPLIER)` ทำงานได้ ผู้ติดต่อคนเดียวที่อยู่สององค์กรมี session และ cookie path แยกกัน และ `PortalSession.organizationId` ต้องตรงกับ `[org]` ทุกคำขอ (ไม่ตรง → 404 ไม่เผยว่ามีองค์กรอื่น) · route handler อยู่ที่ `/portal/[org]/api/*` เพื่อให้อยู่ใต้ path ของ cookie (ไม่มี `/api/portal/*` ซึ่งเบราว์เซอร์จะไม่ส่ง cookie ไปด้วย)
- ลิงก์ทุกชนิดเก็บ sha256 ใช้ครั้งเดียวด้วย UPDATE แบบ BR-TOK-04 · GET แสดงหน้า POST ใช้ลิงก์ (BR-TOK-03)
- OTP: CSPRNG · เก็บ `sha256(challengeId:code)` · เทียบ constant-time · ตรวจล็อก → หมดอายุ → รหัส · หมดอายุที่นาทีที่ 10 · ครั้งที่ 5 ที่ผิดล็อก 15 นาที · ขอใหม่ไม่เกิน 3 ครั้งต่อ 15 นาทีต่อผู้ติดต่อ (BR-PORTAL-02 BR-PORTAL-04 · golden GC-SUP-20 ถึง 25 และ 50) · OTP ทางอีเมลเป็นปัจจัยเดียวกับลิงก์ จึงมีการควบคุมชดเชย: challenge ผูก `tokenHash` ของลิงก์และ `userAgentHash` `ipHash` ของคำขอที่ขอ · เข้าจากอุปกรณ์ใหม่แจ้งอีเมลในทะเบียน · การเสนอบัญชียังคุมด้วย FINANCE โทรยืนยัน + DOA BA step-up (ADR-190)
- session id เปลี่ยนหลัง OTP ผ่าน (NFR-SEC-04) · ทุก POST ใต้ `/portal/[org]/api/*` และ server action ต้องมี CSRF token ที่ผูก session และ `Origin` ตรง `APP_URL` (NFR-SEC-06 · ไม่พึ่ง `SameSite=Lax` อย่างเดียว) · เพิกถอนทั้งหมดในธุรกรรมเดียวเมื่อผู้ติดต่อ DEACTIVATED ผู้ขาย INACTIVE หรือใบสมัครปิด (BR-PORTAL-03)
- ctx ของพอร์ทัล = `{ organizationId, actor: { type: 'SUPPLIER', supplierContactId, supplierId?, applicationId? }, channel: 'PORTAL' }` (ชื่อฟิลด์ตาม Actor union เดิมใน `src/server/context/index.ts` ซึ่ง S7-04 ขยายเพิ่ม `supplierId?` `applicationId?`) · session เก็บเฉพาะ contactId และ actor ประกอบใหม่จาก `SupplierContact` ทุกคำขอ · `portalDb(ctx)` เติมเงื่อนไขผู้ขายในทุก query ตามรายการ model พร้อมเงื่อนไข where (BR-PORTAL-05 · INV-SUP-01)

- `PortalInviteLink.purpose` เป็น enum Prisma ชื่อ `PortalInviteLinkPurpose` (`INVITATION` `LOGIN` `DOCUMENT_REQUEST`) · S10 S11 ต่อท้ายค่าของตน (`RFX_INVITE` `RISK_QUESTIONNAIRE`) ด้วย migration `ALTER TYPE … ADD VALUE` ของขั้นตน · อายุลิงก์: `LOGIN` = `supplier.loginLinkMinutes` · purpose อื่นทุกค่าที่ส่งทางอีเมลเพื่อทำงานภายหลัง = `supplier.inviteLinkDays` (BR-PORTAL-01) · ใบสมัคร kind NEW ที่ INVITED เป็น DRAFT ที่ `portal_session.signed_in` ครั้งแรกไม่ว่าลิงก์ purpose ใด
- อีเมลถึงผู้ติดต่อของใบสมัครที่ยังไม่มีแถว `Supplier` ใช้ `SupplierNotice` ของ S8 โดย S7-01 ทำ `supplierId` nullable + `applicationId?` `contactId?` (CHECK อย่างน้อยหนึ่งไม่ว่าง) และ S7-04 ให้ `SupplierNoticeInput` รับ `{ supplierId?, applicationId?, contactId?, locale? }` กับแม่แบบรับ `locale` (BR-NOTI-09) · S10 S11 ใช้ตามโดยไม่แก้ S8 ซ้ำ
- ประกาศความเป็นส่วนตัวของพอร์ทัลมีเลขฉบับ `PORTAL_PRIVACY_NOTICE_VERSION` ใน `src/server/portal/privacy.ts` · ผู้ติดต่อฉบับเก่าเห็นประกาศใหม่ในการเข้าระบบถัดไปและอัปโหลดไม่ได้จนรับทราบ · ขั้นที่เพิ่มขอบเขตข้อมูลเพิ่มเลขฉบับที่เดียวกัน (BR-PORTAL-08)
- `portalDb` และ `portalAuthorize` เปิด registry (`PORTAL_MODELS` `PORTAL_ACTIONS`) และ query ของขั้นอื่นอยู่ในไฟล์พี่น้อง `queries-<ขั้น>.ts` ที่เทสต์ INV-SUP-01 อ่านด้วย glob `src/server/portal/queries*.ts`

## ผลที่ตามมา

- โค้ดตัวตนทั้งหมดอยู่ใน `src/server/portal` และข้อ S7-04 เป็น `xhigh` รีวิวทันที (ADR-072) · ไม่มีการตั้งค่า Better Auth เพิ่ม
- rate limit ต่อ IP นับใน `PortalIpRateLimit` ที่ไม่มีคอลัมน์ `organizationId` เลย (เทสต์ INV-TEN-02 นับเฉพาะ model ที่มีคอลัมน์นั้น จึงไม่ต้องขอยกเว้น · `BreakGlassSession` ไม่ใช่แบบอย่างเพราะมี organizationId NOT NULL) · S7-01 เพิ่มชื่อในรายการ "ตารางที่ไม่ผูก tenant" ของ §4.8 · bucket ต่อผู้ติดต่อ ผู้ขาย และใบสมัครอยู่ใน `PortalRateLimit` ที่ผูก tenant ปกติ · ไม่มี Redis ใน stack จึงนับใน Postgres
- `Event` เพิ่มคอลัมน์ nullable เท่านั้น (trigger ห้ามเฉพาะ UPDATE DELETE) · ตัดสินตอนนี้ว่าเพิ่มได้ทันที เพราะ main ยังไม่มี `model EventSeal` และไม่มี job `audit-seal-daily`/`audit-verify` (เป็นงาน S5-14 และ NEW-05 `[go-live]` ที่ยังไม่ติ๊ก) จึงไม่มี hash ใดให้กระทบ · เมื่อทำ S5-14/NEW-05 seal ต้อง hash จากรายการคอลัมน์ที่ประกาศคงที่ (รวม `actorSupplierContactId`) ไม่ใช่ทุกคอลัมน์ของแถว เพื่อให้คอลัมน์ nullable ที่เพิ่มภายหลังไม่เปลี่ยน hash เดิม (แจ้ง ADR-020) · `appendEvents` (`actorColumns`) map actor SUPPLIER → `actorType SUPPLIER` + `actorSupplierContactId` และ `actorMemberId` null (INV-SUP-05 · เทสต์ใน S7-01)
- SMS เป็นข้อ `[go-live]` (S7-21) ผ่าน adapter `otp-sms` โหมด stub/live เมื่อลูกค้าเลือกใน OQ-181
- S10 S11 ใช้ session และ `portalAuthorize` ชุดนี้ ห้ามสร้าง OTP หรือ session ของตัวเอง
- ถ้าผู้ใช้เลือกใช้ Better Auth สำหรับผู้ขาย: ต้องแยก instance หรือ namespace ของผู้ใช้ และเขียนกฎกันผู้ขายเป็น member ในทุกจุดที่อ่าน `Member.userId` ซึ่งแตะโค้ดเดิมมาก
