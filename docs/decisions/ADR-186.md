# ADR-186: ตรวจผู้ขายซ้ำด้วยเลขผู้เสียภาษี ชื่อหลัง normalize และอีเมล

- สถานะ: ร่าง ADR-075 (2026-11-01) รอผู้ใช้อนุมัติ
- วันที่: 2026-11-01
- ที่มา: docs/sub-specs/S7.md หัวข้อ "กฎ" (BR-SUP-09) และ "ร่าง golden case" (GC-SUP-09 ถึง GC-SUP-19) · FR-SUP-102 "ตรวจเลขผู้เสียภาษีและผู้ขายซ้ำ" · ADR-075

## บริบท

- FR-SUP-102 ต้องตรวจเลขผู้เสียภาษี (BR-TAXID-01 มีแล้ว) และผู้ขายซ้ำ · ชั้น 1 มี `checkNewSupplier` ที่ดูเลข + สาขากับ `Supplier` และ unique `(org, taxId, branchCode)` เท่านั้น
- ข้อมูล SIMEC มีผู้ขายรายเดียวกันสองสาขา (SP0001 SP0196 · เลข 0999998010014 สาขา 00000 และ 00003 ในชีต Suppliers) ซึ่งถูกต้องไม่ใช่ซ้ำ · ชื่อบริษัทไทยเขียนได้หลายแบบ ("บริษัท … จำกัด" "บจก. …") และผู้ขายต่างชาติเขียน "Co., Ltd." หรือ "Company Limited" · ชื่ออังกฤษอาจมีคำบอกรูปแบบเป็นส่วนของชื่อจริง ("Prince", "Unlimited Steel") จึงตัดเฉพาะคำเต็ม · ผู้ขายต่างประเทศไม่มีเลขผู้เสียภาษีไทย
- ใบสมัครที่เปิดอยู่ก็นับเป็นซ้ำได้ (เชิญรายเดียวกันสองครั้ง) · ผู้อนุมัติต้องเห็นว่าจัดซื้อตัดสินเรื่องซ้ำอย่างไร (G-2 audit)
- การเทียบชื่อแบบ fuzzy (ระยะห่างของตัวอักษร) เสี่ยงเตือนผิดกับชื่อไทยที่สะกดต่างและไม่มีชุดทดสอบจริง

## การตัดสินใจ

> ตรวจผู้ขายซ้ำใน core: เลขผู้เสียภาษี + สาขาตรง = บล็อก (`DUPLICATE_SUPPLIER`) · เลขเดียวกันสาขาอื่น ชื่อหลัง normalize หรืออีเมลผู้ติดต่อตรง = เตือนที่ต้องกรอกเหตุผลและแสดงให้ผู้อนุมัติ · normalize = NFC ตัวพิมพ์เล็ก ลบคำบอกรูปแบบนิติบุคคล (รายการค่าคงที่ใน core) และช่องว่างเครื่องหมาย โดยคงข้อความในวงเล็บ · ตรวจตอนเชิญ บันทึกร่าง และส่ง · ไม่ทำ fuzzy ในระยะ 2

- `findSupplierDuplicates(candidate, existing)` ใน `src/core/supplier-onboarding` เทียบกับ `Supplier` ทุกสถานะและ `SupplierApplication` ที่เปิดอยู่ · ผลเป็น error (`DUPLICATE_TAXID` · ไม่คืน warnings ร่วม · GC-SUP-14) หรือรายการเตือน (`SAME_TAXID_OTHER_BRANCH` `DUPLICATE_NAME` `DUPLICATE_EMAIL`) พร้อมรหัสผู้ขายที่ตรง · `taxId` ว่าง (ต่างประเทศ) ข้ามการเทียบเลข ตรวจเฉพาะชื่อและอีเมล (GC-SUP-49)
- คำบอกรูปแบบนิติบุคคลตัดเฉพาะเมื่อเป็นคำเต็ม: คำอังกฤษเมื่อตัวอักษรข้างหน้าและข้างหลังไม่ใช่ a–z 0–9 ("Prince Co., Ltd." → `prince` · GC-SUP-48) · คำไทยเมื่ออยู่หัวหรือท้ายข้อความและติดกับช่องว่าง จุด หรือวงเล็บ · ตัวรัน golden เทียบผลทั้ง object
- เลขที่ check digit ไม่ผ่าน → `VALIDATION_FAILED` reason `TAXID_CHECKSUM` ก่อนตรวจซ้ำ (GC-SUP-19)
- เหตุผลของเตือนเก็บใน `SupplierApplication.duplicateWarnings` และอยู่ใน `facts` ของงานอนุมัติ (ADR-182)
- บล็อกเสนอทางออก "เชิญผู้ขายเดิมเข้าพอร์ทัล" (ใบสมัคร kind EXISTING · ADR-181)

## ผลที่ตามมา

- golden GC-SUP-09 ถึง 19 และ 48 ถึง 49 กำหนดผล normalize และการตรวจ · รายการคำบอกรูปแบบนิติบุคคลเป็นค่าคงที่ใน core เพิ่มได้พร้อม golden
- unique ของ `Supplier` และ partial unique ของใบสมัครยังเป็นด่านสุดท้ายเมื่อสองคนเชิญพร้อมกัน (INV-SUP-02)
- ไม่มี dependency ใหม่ · ไม่ใช้ AI ในการตรวจซ้ำ (EG-1)
- ตัวตรวจ fuzzy เป็นงานหลังระยะ 2 เมื่อมีข้อมูลจริงให้วัดอัตราเตือนผิด
- ถ้าผู้ใช้เลือกให้ชื่อซ้ำเป็นบล็อก: ผู้ขายคนละนิติบุคคลที่ชื่อเหมือนกัน (เลขต่าง) จะสมัครไม่ได้ จึงไม่แนะนำ
