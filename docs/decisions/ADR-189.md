# ADR-189: Supplier Onboarding Agent ระดับ L1 ด้วย credits ขององค์กร

- สถานะ: ยอมรับ (ร่าง ADR-075 · ผู้ใช้อนุมัติตามที่แนะนำเมื่อ 2026-11-01)
- วันที่: 2026-11-01
- ที่มา: docs/sub-specs/S7.md หัวข้อ "กฎ" (BR-AI-29 BR-AI-30) "ร่าง golden case" (suite ai-supplier-verify) และ "FR และ AC" (FR-AI-304) · บรีฟระยะ 2 ถามว่าใครเป็นผู้เรียก AI เมื่อผู้ใช้เป็นผู้ขาย · ADR-075

## บริบท

- FR-AI-304 ทำพร้อม S7 เมื่อเปิดโมดูล AI (§8.11) · agent ของระยะ 1 ทุกตัวถูกเรียกโดย member และคิด credits ขององค์กร (BR-AI-11 BR-AI-23) · BR-AI-17 เขียนว่าผู้กระทำที่รับค่าของ AI ต้องเป็นคน (actor USER)
- ผู้ที่อัปโหลดเอกสารในพอร์ทัลเป็น `SupplierContact` (actorType SUPPLIER) ไม่ใช่ member จึงใช้ "10 ครั้งต่อนาทีต่อสมาชิก" และ `ai.assist` (ทุก member OWN) ตรงตัวไม่ได้
- BR-AI-18 ห้าม schema ของผลอ่านมีเลขบัญชีธนาคาร ส่วน FR-AI-304 บอกให้อ่านหน้าสมุดบัญชี · NFR-PRIV-02 ห้ามเก็บเกินจำเป็นและสำเนาบัตรต้องปิดศาสนา · ข้อมูลจริงส่ง Claude ได้เมื่อ OQ-144 ปิด
- ทุก FR ต้องทำงานครบเมื่อปิด AI (EG-1) และ AI ไม่อนุมัติหรือเปลี่ยนสถานะเงิน (BR-AI-01)

## การตัดสินใจ

> Supplier Onboarding Agent (FR-AI-304) ระดับ L1 เรียกจาก job `supplier-document-ai` หลังไฟล์ CLEAN ด้วย credits ขององค์กร (BR-AI-23) อัตราต่อใบสมัคร (แก้ถ้อยคำ BR-AI-11) · อ่านเฉพาะประเภท `aiReadable` ที่ `payeeType` ของใบอยู่ใน `aiReadablePayeeTypes` (ค่าเริ่มต้น: หนังสือรับรองและ ภ.พ.20 ของนิติบุคคล · ไม่อ่านหน้าสมุดบัญชี บัตรประชาชน และเอกสารของบุคคลธรรมดา) และ schema ไม่มีเลขบัญชี (BR-AI-18) · ค่าเข้าใบสมัครผ่าน `supplierApplication.update` + `aiAssist` (`applyAiAssist` purpose `SUPPLIER_DOC_READ`) โดยคนยืนยัน ซึ่งเป็นผู้ติดต่อในพอร์ทัล (actorType SUPPLIER · แก้ถ้อยคำ BR-AI-17) หรือ PROCUREMENT · ชุดประเมินชั้น demo ด้วยเอกสารสังเคราะห์ ชั้นจริงรอ P0-02 · ปิด AI ทุกอย่างทำงานครบ (EG-1)

- ข้อมูลขาเข้า: ภาพเอกสาร **ทั้งใบ** ถูกส่งให้ Anthropic การตัด `accountNo` ออกจาก schema ป้องกันเฉพาะผลอ่าน ไม่ได้ป้องกันข้อมูลขาเข้า และ redactor ของ BR-AI-18 ใช้กับข้อความเท่านั้น → `BANK_BOOK.aiReadable = false` ตามค่าเริ่มต้น (ผู้ขายกรอกธนาคารและชื่อบัญชีเอง 2 ช่อง) · `VAT_CERT` อ่านได้เฉพาะ `payeeType = JURISTIC` เพราะ ภ.พ.20 ของบุคคลธรรมดามีเลขบัตรประชาชน (BR-AI-08) · ตรวจต่อฉบับใน job (`shouldReadDocument` · GC-AI-95) · ลูกค้าเปิดอ่านสมุดบัญชีได้เมื่อยอมรับความเสี่ยงและบันทึก ROPA (OQ-186 ทาง (ข) ของส่วนที่ 2 · ตารางตัดสินบอกผู้ใช้ชัดว่าเลขบัญชีเต็มจะออกไปยังผู้ประมวลผลภายนอก)
- ผู้เรียก: job ของระบบที่ระบุองค์กร (`isAgentAvailable(orgCtx, SUPPLIER_ONBOARDING)`) และ `settings.supplier.aiAssist = true` (OQ-186) · `AgentAction.requestedByContactId` บอกว่าผู้ติดต่อคนไหนเป็นต้นเหตุ · อัตราไม่เกิน 10 ครั้งต่อนาทีต่อใบสมัคร
- enum Prisma `AiAgent.SUPPLIER_ONBOARDING` `AiPurpose.SUPPLIER_DOC_READ` และคอลัมน์ `AgentAction.requestedByContactId` อยู่ใน migration เดียวของ S7-01 (ไม่ใช่ S7-14) · `src/lib/ai-config.ts` เติมรุ่น gate และ env ใน S7-14
- ผลอ่าน: `nameTh` `nameEn?` `taxId` `branchCode` `registeredAddress` `registrationDate?` `issuedOn` `isVatRegistered?` `bankName?` `accountName?` `documentNumber?` · ไม่มี `accountNo` (ผู้ขายพิมพ์เอง)
- การตรวจ (ชุด `ai-supplier-verify` · GC-AI-92 ถึง 95): `TAXID_CHECKSUM` `TAXID_MISMATCH` (FAIL) · `REGISTRY_NAME_MISMATCH` `REGISTRY_ADDRESS_MISMATCH` `BANK_UNKNOWN` (WARN) · `DOC_DATE_FUTURE` `DOC_EXPIRED` (FAIL) · ความมั่นใจตาม BR-AI-16
- ช่องสำคัญ (`taxId` `branchCode` `nameTh` `isVatRegistered` `bankCode` `accountName`) ยืนยันทีละช่อง · `supplierApplication.submit` เรียก `assertNoPendingAiReview`
- ชุดประเมินชั้น demo: เอกสารสังเคราะห์ 12 ฉบับแบบ ADR-146 · เกณฑ์ตั้งต้นใน OQ-186 · gate ชั้น `SYNTHETIC` · ชั้น `REAL` ด้วย P0-02 ตาม OQ-142 (S7-23)

- กลไกจริงของ S13 (`src/server/services/ai/assist-contract.ts`): purpose → subject เป็น registry `registerAssistSubject(type, kind)` ที่ service ของเอกสารเรียกเอง ไม่ใช่ตารางเดียว และด่าน actor ปฏิเสธทุก actor ที่ไม่ใช่ USER พร้อมเขียน `appliedById` เป็น FK Member → S7 สร้าง `src/server/services/suppliers/ai-assist.ts` เรียก `registerAssistSubject('SUPPLIER_APPLICATION', { purposes: ['SUPPLIER_DOC_READ'], final: false, read, supplierActor: true })` และแก้ `assist-contract.ts` 2 จุดใน S7-14 (`xhigh` · ADR-072): ด่าน actor ยอม `SUPPLIER` เมื่อ `kind.supplierActor === true` · เขียน `appliedById = null` + คอลัมน์ใหม่ `AgentAction.appliedByContactId` (migration S7-01) · subject อื่นไม่ตั้งธงจึงพฤติกรรมเดิม · S11 ใช้ธงเดียวกันกับ `RISK_ASSESSMENT`

## ผลที่ตามมา

- แก้ถ้อยคำกฎเดิม 2 ข้อใน S7-01 (ข้อความในหัวข้อ F ของ `docs/drafts/p2/S7-spec-additions.md` · ผู้ใช้อนุมัติผ่าน ADR นี้): BR-AI-17 "โดยผู้กระทำเป็นคน (actor USER หรือ SUPPLIER = ผู้ติดต่อในพอร์ทัล เฉพาะ subject `SUPPLIER_APPLICATION`) … · `SUPPLIER_DOC_READ` → ใบสมัครผู้ขาย (S7)" และ BR-AI-11 "ไม่เกิน 10 ครั้งต่อนาทีต่อสมาชิก หรือต่อใบสมัครเมื่อผู้เรียกไม่ใช่ member (BR-AI-29)" เพื่อไม่ให้ spec ขัดกันเองเมื่อวาง BR-AI-29/29 · `applyAiAssist` เพิ่ม purpose → subject หนึ่งแถว · ตารางราคาและ gate อยู่ใน `src/lib/ai-config.ts` ตามเดิม (ADR-143)
- ชุดประเมินชั้น demo ไม่มีหน้าสมุดบัญชี (หนังสือรับรอง 7 · ภ.พ.20 นิติบุคคล 5) · เกณฑ์ `bankCode` ใช้เฉพาะเมื่อลูกค้าเปิดอ่านสมุดบัญชี
- INV-AI-01 ถึง INV-AI-05 ยังจริง: event `drafted` `failed` เป็น AI_AGENT · `src/server/portal` และ `services/suppliers` ไม่ import `src/integrations/ai`
- ไม่มีปุ่ม AI ในพอร์ทัลเมื่อปิด (ระบบ โมดูล agent หรือค่าตั้ง) · ฉาก demo ผ่านทั้งเปิดและปิด AI
- ผลอ่านของใบสมัครที่ปิดโดยไม่ apply ล้างตาม BR-AI-18 · เอกสารนิติบุคคลมีชื่อกรรมการ จึงใช้ข้อมูลสังเคราะห์จน OQ-144 ปิด
- ถ้าผู้ใช้เลือกไม่ให้ AI อ่านเอกสารผู้ขาย (OQ-186 ทาง ค): ปิดค่าตั้งและข้าม S7-14 S7-15 โดยไม่กระทบ FR อื่น · ถ้าเลือกให้เฉพาะจัดซื้อเห็น (ทาง ข): พอร์ทัลไม่แสดงค่าที่อ่านและผู้ขายกรอกเอง
