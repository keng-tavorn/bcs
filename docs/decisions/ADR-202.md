# ADR-202: ชนิดเอกสาร DOA RFX_AWARD ยอดที่มอบ และช่องทางอนุมัติผลการจัดหา

- สถานะ: ยอมรับ (ร่าง ADR-075 · ผู้ใช้อนุมัติตามที่แนะนำเมื่อ 2026-11-01)
- วันที่: 2026-11-01
- ที่มา: docs/sub-specs/S10.md หัวข้อ "กฎ" (BR-DOA-27 BR-SOD-13 BR-RFX-12) และ "ร่าง golden case" (GC-DOA-75 ถึง GC-DOA-80) · บรีฟของ ADR-075 ที่จอง `RFX_AWARD` ให้ S10

## บริบท

- FR-SRC-204 "อนุมัติผลแล้วสร้าง PO จากผู้ชนะ" ต้องมีการอนุมัติที่อ้าง DOA ฉบับและข้อ (G-2) · P1-07 มีชนิดเอกสาร 11 ชนิดและ S7 เพิ่ม `SUPPLIER_APPROVAL` (ADR-182) · §4.11 ข้อ 7 บังคับว่าเปิดโมดูลต้องมีข้อของชนิดบังคับ
- ผลมอบงานมียอดเงิน (ยอดที่มอบ) จึงต่างจาก `SUPPLIER_APPROVAL` ที่ไม่มียอด · ยอดนี้ยังไม่ผูกงบ (PO ผูก) แต่เป็นการเลือกผู้ขายและราคาที่มีผลต่อเงินที่จะจ่าย
- ผู้ที่เกี่ยวข้องกับผล (ผู้สร้าง RFx ผู้ประเมิน ผู้ขอของบรรทัดต้นทาง) ไม่ควรเป็นผู้อนุมัติผลเดียวกัน (แบบแผน BR-SOD-01/03/09)

## การตัดสินใจ

> ชนิดเอกสาร DOA `RFX_AWARD` ยอด REQUIRED มี VAT (ยอด = ยอดที่มอบ ก่อน VAT + VAT ต่อผู้ขาย ฐานตาม `amountBasis`) subject `AWARD_DECISION` บังคับมีข้อเมื่อเปิด `SOURCING` (BR-DOA-27 · แก้ถ้อยคำ BR-DOA-23 และ §4.11 ข้อ 7) · step-up ตาม `stepUpThreshold` เหมือน PO ไม่อยู่ใน `ALWAYS_STEP_UP_SUBJECTS` · `channels` ของ adapter เปิดคงที่ (`chatButton: () => true, emailLink: true, liff: true`) ส่วนการปิดปุ่มเมื่อต้อง PIN มาจาก `stepUpNeeded` ของ P1-07 นอก adapter · `allowsRequestInfo: false` · ผู้ขัดกัน = ผู้สร้าง RFx ผู้ประเมิน ผู้ขอของบรรทัดต้นทาง ผู้ส่งผล ผู้บันทึกใบแทน (BR-SOD-13) · adapter `subjects/award-decision.ts` ตาม ADR-068 · ต่อท้าย fixture `doa-versions-p2.yaml` ของ S7 ด้วยข้อ RA-01 ถึง RA-03 (ADR-069)

- `DOC_TYPE_TRAITS.RFX_AWARD = { amount: 'REQUIRED', vat: true, governance: false, requiredWithModules: ['SOURCING'], subjects: ['AWARD_DECISION'] }` ต่อท้าย `SUPPLIER_APPROVAL` ใน `DOA_DOCUMENT_TYPES` (ก่อน `RISK_OVERRIDE` ของ S11 · ตรวจไขว้)
- ยอดของผล: `net = Σ lineNet(quantity, unitPrice ก่อน VAT)` · `vat = Σ ต่อผู้ขาย vatFromNet(net ของผู้ขาย, vatRateBp ของผู้ขาย)` (ผู้ขายไม่จด VAT 0) · DOA ใช้ฐาน GROSS หรือ NET ตามฉบับที่มีผล เหมือน PO · demo ของ SIMEC: 300,950.00 + 21,066.50 = 322,016.50
- ข้อร่างของ SIMEC (OQ-207 · ลูกค้ายืนยันในเส้นชัย B): RA-01 (0, 500,000] → `PROC_MGR@HQ` · RA-02 (500,000, 5,000,000] → COO · RA-03 > 5,000,000 → CEO · เป็นข้อมูลใน fixture และชีต DOA ไม่ใช่โค้ด (P-2)
- SoD สองชั้นแบบ BR-SOD-01: ตอนคำนวณเส้นทาง (`conflictMemberIds` → ยกช่วงถัดไป) และตอนตัดสิน (`SOD_VIOLATION`) · ชั้นตัดสินทำตามสัญญากลางที่ `decide.ts` มีอยู่ (ส่ง `requesterMemberIds` เข้า `checkSod` แล้วตรวจ `sodContext().extra` ต่อ · ไม่แก้ `decide.ts`): adapter คืน `extra = awardDecisionSodExtra(...)` → `[{ rule: 'BR-SOD-13', memberIds: [ผู้สร้าง RFx, ผู้ประเมินทุกคน, ผู้ขอของบรรทัดต้นทาง, ผู้บันทึกใบแทน] }]` แบบ `paymentRunSodExtra` ของ BR-SOD-04/10 · `SodRule` เพิ่ม `BR-SOD-13` `BR-SOD-14` · คีย์ optional `rfxCreatorMemberIds` `evaluatorMemberIds` `sourceRequesterMemberIds` `recordedOnBehalfMemberIds` ใน `SodAction.DECIDE_APPROVAL` มีไว้ให้ golden/`run_sod` ตรวจกฎเดียวกัน (แบบ `invoiceRecorderMemberIds`)
- แผนกของเส้นทาง (`RouteInput.chargedDepartmentId` ค่าเดียว): แผนกเจ้าของงบของบรรทัดต้นทางเมื่อทุกบรรทัดอยู่แผนกเดียว · หลายแผนกหรือ NEED → แผนกหลักของผู้สร้าง RFx · รายชื่อแผนกต้นทางทั้งหมดอยู่ใน facts · ข้อ RA ของ SIMEC เป็น `POSITION_OF_ORG` จึงไม่ขึ้นกับแผนก แต่กฎนี้ทำให้ RA แบบ `POSITION_OF_DEPARTMENT` ของลูกค้าอื่น deterministic
- `award.submit` อ่าน `registryFlag` และ `supplierDocumentStatus` ของผู้ชนะสด (reason code `SUPPLIER_FLAGGED` `DOCS_INCOMPLETE`) เทียบยอดกับที่คำขอต้นทางอนุมัติ (`ABOVE_REQUEST`) และตรึง `rankingSnapshot` · ตัดสิทธิ์ใบระหว่างผลเปิดอยู่ไม่ได้ (`AWARD_OPEN`)
- เมื่อองค์กรเปิด `RISK` (ตรวจด้วย `enabledModules` ไม่ import S11 ตอนคอมไพล์ · อ่านผ่าน provider `registerSupplierRiskProvider` ที่ S11 ลงทะเบียน): `award.submit` อ่าน `supplierRiskStatus` ของผู้ชนะสด → ผู้ขาย HIGH ที่ `status ∉ {CURRENT, EXPIRING}` และไม่มี `openOverrideId` = reason code `RISK_NOT_CLEARED` บังคับเหตุผล (ผู้อนุมัติผลเห็นก่อนว่า PO จะติดด่าน `RISK_ASSESSMENT_REQUIRED` ของ S11) · `registryFlag = CEASED` → ปฏิเสธ `SUPPLIER_FLAGGED` 422 ไม่ใช่แค่เหตุผล เพราะ S11 BR-RSK-12 บล็อก PO ถาวรและการอนุมัติข้ามใช้ไม่ได้ (กลับเป็นเหตุผลบังคับเมื่อลูกค้าเลือก `registryFlagBlocks = false` · OQ-227 ของ S11) · ตารางเทียบและ facts แสดงป้ายระดับ/สถานะ (BR-RFX-03 BR-RFX-08 BR-RFX-12) · ด่านจริงยังอยู่ที่ PO ของ S11 ที่ `po.submit` `po.send` `po_change`
- `channels` ตามสัญญากลาง `subjects/index.ts` (`emailLink` ค่าคงที่ · `chatButton(facts)` ไม่รู้ยอด): adapter คืน `{ chatButton: () => true, emailLink: true, liff: true }` แบบ `po-change.ts` · ปุ่มในแชทและลิงก์อีเมลถูกปิดเมื่อยอดตามฐาน ≥ `stepUpThreshold` โดย `stepUpNeeded` ใน `line-postback.ts`/`action-link.ts` ของ P1-07 ก่อนอ่าน `channels` (BR-TOK-05) จึงไม่เขียนตรรกะยอดซ้ำใน adapter
- ขอข้อมูลเพิ่มใช้ `approval.return` ตีกลับ (สัญญากลาง `allowsRequestInfo: false` · ไม่แก้ `decide.ts`)

## ผลที่ตามมา

- migration S10-01 เพิ่มค่า enum `RFX_AWARD` และ `AWARD_DECISION` · `APPROVAL_SUBJECTS` เพิ่มค่าเดียว typecheck ชี้ทุกจุดที่ต้องเติม
- `scripts/spec_check.py`: `DOC_ORDER` เพิ่ม `RFX_AWARD` ต่อจาก `SUPPLIER_APPROVAL` · `AMOUNT_REQUIRED` เพิ่ม `RFX_AWARD` (ตัวรัน `run_doa` ใช้เซ็ตนี้ตัดสินยอด ≤ 0 → `VALIDATION_FAILED` ตรง BR-DOA-27 · S11 เพิ่ม `RISK_OVERRIDE` ในเซ็ตเดียวกัน) · `MODULE_DOCS["SOURCING"] = ("RFX_AWARD",)` · `AMOUNT_NONE` ไม่เพิ่ม · `run_sod` เพิ่มกฎ BR-SOD-13 และ action `SCORE_RFX` (BR-SOD-14)
- §4.11 กติกาข้อ 7 ต่อท้ายวงเล็บด้วย "· `SOURCING` → `RFX_AWARD`" พร้อมถ้อยคำ BR-DOA-23 (S10-01) · reason code `RISK_NOT_CLEARED` และการปฏิเสธ CEASED มีผลเฉพาะเมื่อเปิด `RISK` และมี provider ของ S11 จึงไม่เปลี่ยนผลเทสต์ขององค์กรที่ปิด `RISK`
- golden GC-DOA-75 ถึง 80 ต่อท้าย `doa-p2.yaml` และ `doa-p2-lint.yaml` ของ S7 · GC-DOA-01 ถึง 74 ไม่เปลี่ยน
- เปิด `SOURCING` ของ SIMEC ใน seed ได้เมื่อชีต DOA มีแถว RA · องค์กร DEMO ไม่เปิด `SOURCING` ฉาก `@demo` จึงไม่เปลี่ยน
- `dm_proc` ของ SIMEC ดำรงทั้ง DM@PROC และ PROC_MGR@HQ จึงเป็นผู้อนุมัติ RA-01 ที่ต้องไม่สร้างหรือประเมิน RFx นั้น (GC-DOA-76 แสดงการยกไปช่วงถัดไป)
