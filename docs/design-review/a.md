# Design review — หน่วย a: แคตตาล็อก ฟอร์มคำขอ ร่าง ไฟล์แนบ งบคงเหลือ (S2-11 · S2-17 ส่วนหน้าจอ · S3-06 · การเลือกบรรทัดงบของ S3-07)

ขั้นตอนตาม spec §9.9: (1) แผนสั้นต่อหน้า (2) ตรวจแผนกับรายการ "สิ่งที่ห้ามใช้" ก่อนเขียนโค้ด (3) เขียนด้วย token
(4) screenshot 375 px และ 1440 px แล้วตรวจอีกรอบ (5) axe ไม่มี serious หรือ critical · ตารางผลตรวจอยู่ท้ายไฟล์

หลักที่ใช้: ประตูเดียว (หลัก 2 — เริ่มจากเลือกประเภทแล้วถามทีละขั้นเท่าที่จำเป็น) · บอกล่วงหน้า (หลัก 3 — ก่อนกดส่ง
ผู้ขอเห็นงบคงเหลือ เส้นทางอนุมัติ และเอกสารที่ต้องแนบ) · ตัวเลขเงินอ่านง่าย (หลัก 6) · ปุ่มบอกผล (หลัก 7) · หน้าว่างบอก
ขั้นต่อไป (หลัก 8) · ฟอร์มยาวแบ่งขั้น (ห้ามเกิน 8 ฟิลด์ต่อหน้า)

## 1. แผนต่อหน้า

### A. `/requests/new` ขอซื้อ / ขอจ้าง (แคตตาล็อก)

- ต้องบอก: ประเภทคำขอที่เปิดใช้ทั้งหมด (4–6 ประเภท) แต่ละประเภทใช้เมื่อไร · หาประเภทด้วยคำสำคัญ · ร่างที่ค้างไว้ทำต่อได้
- ลำดับ: หัวข้อ "ขอซื้อ / ขอจ้าง" + ประโยคบอกว่าเลือกแล้วจะถามเฉพาะที่จำเป็น → ช่องค้นหา (พร้อมตัวอย่างคำ) → จำนวนที่พบ
  (role=status) → การ์ดประเภท → "ร่างและคำขอที่ถูกตีกลับของคุณ"
- โครงหน้า: การ์ดใช้กับประเภทคำขอเท่านั้น (ของที่เป็นหน่วยเดียวกันจริง ตาม §9.9) จอกว้าง 2 คอลัมน์ มือถือ 1 คอลัมน์ ·
  การ์ดทั้งใบเป็นลิงก์ ขอบเส้น `line` ไม่มีเงา ชี้แล้วขอบเป็นสี primary และพื้น `surface` (ไม่ยก ไม่เด้ง)
- ข้อความในการ์ด: ชื่อประเภท · "ใช้เมื่อ: …" (คำอธิบายเป็นข้อมูลขององค์กร) · ลิงก์ "เริ่มคำขอ …" บอกผลที่จะเกิด
- หน้าว่าง: ค้นไม่พบ → บอกคำที่ค้นพร้อมปุ่ม "ล้างคำค้นและดูทุกประเภท" · ไม่มีประเภทเลย → บอกให้ติดต่อผู้ดูแลระบบ ·
  ไม่มีร่าง → บอกว่าร่างจะบันทึกเองเมื่อเริ่มกรอกและเปิดทำต่อจากที่นี่ได้ทุกอุปกรณ์

### B. `/requests/new/[type]` และ `/requests/[id]/edit` ฟอร์มคำขอ (หน้าเดียวกัน)

- ต้องบอก: ประเภทคำขอและใช้เมื่อไร · ร่างบันทึกแล้วหรือยัง · ข้อมูลที่ต้องกรอกแบ่งเป็น 4 ขั้นจริง (มีเลขขั้นได้เพราะเป็นขั้นตอนจริง)
  1) รายละเอียดคำขอ 2) รายการที่ขอ 3) ใบเสนอราคาและเอกสาร 4) ตรวจและส่ง
- ส่วนหัว: ลิงก์ "เลือกประเภทคำขออื่น" (ไม่มีลูกศร) · H1 "คำขอใหม่: ซื้อของ" (ร่าง: "ร่างคำขอ: …" ถูกตีกลับ: "แก้ไขคำขอที่ถูกตีกลับ: …")
  · คำอธิบายประเภท · บรรทัดสถานะร่าง (role=status: จะบันทึกเอง / ยังไม่บันทึก / กำลังบันทึก / บันทึกแล้ว เวลา / บันทึกไม่สำเร็จ
  พร้อมเหตุและวิธีแก้ตามรหัสที่ได้ เช่น หมดเวลาการเข้าระบบ ระบบกำลังทำรายการอื่น ร่างใหญ่เกิน บัญชีไม่มีฝ่าย หรือการเชื่อมต่อ — ไอคอน + ข้อความ) +
  ปุ่มรอง "บันทึกร่างตอนนี้" · ร่างชนกันจากอีกอุปกรณ์ → Notice สีแดงพร้อมปุ่ม "โหลดฉบับล่าสุด" · ถูกตีกลับ → Notice บอกเหตุผลของผู้อนุมัติ
- ตัวบอกขั้น: จอกว้างเป็นรายการปุ่มเรียง 1–4 ขั้นปัจจุบันขอบหนาสี primary ตัวหนา และ `aria-current="step"` (ไม่ใช้สีอย่างเดียว) ·
  มือถือเป็นข้อความ "ขั้นที่ 2 จาก 4: รายการที่ขอ" แล้วเลื่อนด้วยปุ่มท้ายขั้น
- ขั้น 1 รายละเอียด (≤ 8 ช่อง): ชื่อคำขอ (จำเป็น) · บรรทัดงบ (เติมให้ตาม BR-FORM-02 เลือกได้เฉพาะงบของฝ่ายตนหรือที่ได้ grant) ·
  ฝ่ายที่ตั้งเบิกและศูนย์ต้นทุน (มาจากบรรทัดงบ) · "งบคงเหลือของบรรทัดนี้" ของบรรทัดที่เลือกเท่านั้น (ตัวเลขชิดขวา) ·
  คำถามของประเภทคำขอ (label/help เป็นข้อมูลภาษาไทยและอังกฤษจาก FieldDef แสดงหรือซ่อนทันทีตามคำตอบ) · ตัวเลือก ≤ 3 ข้อแสดงเป็นปุ่มวิทยุ
- ขั้น 2 รายการ: ติ๊ก "ราคาที่กรอกรวม VAT แล้ว" · แต่ละรายการเป็นกลุ่ม (fieldset + legend "รายการที่ n") สิ่งที่ขอ จำนวน หน่วย
  ราคาต่อหน่วย มี VAT วันสิ้นสุดบริการ (เมื่อเงื่อนไขของฟอร์มเป็นจริง ใต้ช่องบอกวันที่เลือกเป็น พ.ศ. เช่น 31 ต.ค. 2570 เพราะตัวเลือกวันที่
  ของเครื่องแสดง ค.ศ.) และจำนวนเงินของรายการชิดขวา · ปุ่ม "ลบรายการที่ n" เป็นปุ่มขอบแดง กดแล้วถามก่อนข้างรายการนั้น
  ("ลบรายการที่ n ออกจากคำขอ?" · คำขอที่ถูกตีกลับบอกงบที่รายการนั้นจองไว้และจะคืนเมื่อบันทึก) · ปุ่ม "เพิ่มรายการ" ·
  ยอดก่อน VAT / VAT 7% / ยอดรวม VAT ชิดขวา tabular-nums ทศนิยม 2 · งบประมาณ: คงเหลือ คำขอนี้ใช้ (ก่อน VAT) และผล
  "งบพอ" (ไอคอนถูก) หรือ "งบไม่พอ ขาด x บาท" (ไอคอนเตือน) เปลี่ยนทันทีเมื่อพิมพ์ (aria-live)
- ขั้น 3 เอกสาร: "เอกสารที่ต้องแนบตอนนี้" ตามยอดและคำตอบปัจจุบัน แต่ละกฎบอกรหัส (ATT-QUOTES) เหตุที่ใช้ (เช่น ยอดรวม VAT มากกว่า
  100,000.00 บาท) สิ่งที่ต้องมีและสถานะ (ไอคอน + ข้อความ) · ใบเสนอราคาเป็นข้อมูล: ผู้ขาย ยอด รวม VAT ไฟล์ เลือกใบที่ใช้ ·
  ยอดก่อน VAT ของแต่ละใบและป้าย "ต่ำสุดก่อน VAT" (ไอคอน + ข้อความ) เทียบทันที · เลือกใบที่ไม่ต่ำสุด → ช่องเหตุผลขึ้นมา ·
  ไฟล์แนบอื่น: เลือกชนิดก่อน (ชนิดที่กฎยังขาดขึ้นก่อน) แล้วปุ่มอัปโหลดที่บอกชนิด "แนบไฟล์: ข้อตกลงการประมวลผลข้อมูล (DPA)" ·
  รายการไฟล์: ลิงก์ "เปิดไฟล์ …" ชิดซ้าย และปุ่มขอบแดง "เอาไฟล์ … ออก" ชิดขวาสุด (ห่างกัน ไม่หน้าตาเหมือนกัน) กดแล้วถามก่อน ·
  "ลบใบเสนอราคาที่ n" เป็นปุ่มขอบแดงที่ถามก่อนเช่นกัน และบอกว่าไฟล์ของใบนั้นออกจากคำขอด้วย
- ขั้น 4 ตรวจและส่ง: สรุปคำขอ · งบ · "เส้นทางอนุมัติที่คาดไว้" (แต่ละขั้นมีชื่อ ตำแหน่งของแผนก แถบซ้ายสี primary + คำอธิบาย
  ภาษาไทยของ engine เช่น "DOA-DEMO ฉบับ 1 ข้อ PR-02: …") · เส้นทางหาไม่ได้ → Notice บอกเหตุและให้ติดต่อ "ผู้ดูแลระบบขององค์กร"
  (บอกตามบทบาท ไม่บอกชื่อบุคคล จนกว่าผู้ใช้ตัดสินเรื่องข้อมูลส่วนบุคคล) และบอกว่าระบบแจ้งผู้ดูแลแล้วเฉพาะเมื่อแจ้งได้จริง ·
  เอกสารที่ต้องแนบ · "ตรวจก่อนส่ง" รายการสิ่งที่ยังขาดแต่ละข้อมีลิงก์ "ไปแก้ที่ขั้น …" · ข้อความเหตุที่ส่งไม่ได้ (งบไม่พอพร้อมยอด
  คงเหลือและยอดที่ขาด) อยู่เหนือปุ่มและผูกกับปุ่มด้วย aria-describedby · ปุ่มหลัก "ส่งขออนุมัติ" (ถูกตีกลับ: "ส่งขออนุมัติอีกครั้ง"
  · ผู้ขายรายใหม่: "ส่งคำขอให้ฝ่ายจัดซื้อ") · ใต้ปุ่มบอกว่าหลังส่งจะเกิดอะไร · server ตอบปฏิเสธ → Notice ข้างปุ่ม (ไม่ใช่ toast)
  บอกเกิดอะไรและแก้อย่างไร พร้อมลิงก์ไปขั้นที่แก้ · ร่างถูกแก้จากที่อื่น (CONFLICT_VERSION) → ในข้อความนั้นมีปุ่ม "โหลดฉบับล่าสุด"
- ส่งแล้ว (§9.9 ข้อ 7 ข้อความยืนยันใช้คำเดียวกับปุ่ม): หน้าเดิมเปลี่ยนเป็นคำยืนยัน H1 ชื่อคำขอ · Notice สีเขียว (ไอคอน + ข้อความ)
  "ส่งขออนุมัติแล้ว รอ {ชื่อผู้อนุมัติ} พิจารณา" และ "เลขที่คำขอ PR-…" (ส่งซ้ำ: "ส่งขออนุมัติอีกครั้งแล้ว …" · ผู้ขายรายใหม่:
  "ส่งคำขอให้ฝ่ายจัดซื้อแล้ว") · ประโยคบอกขั้นต่อไป · ลิงก์ "ดูคำขอ PR-… และติดตามสถานะ" ไปหน้าคำขอ และ "ขอซื้อ / ขอจ้างรายการอื่น"
  · โฟกัสย้ายไปที่คำยืนยัน (แบบเดียวกับฟอร์มเสนอการเปลี่ยนโครงสร้างอำนาจของหน่วย c)
- ท้ายทุกขั้น: ปุ่มรอง "กลับไปขั้น …" และปุ่มหลัก "ไปขั้นถัดไป: …" (มือถือเรียงซ้อน ปุ่มหลักอยู่บน)
- การส่งคำขอย้อนได้ (ผู้ขอยกเลิกได้ตาม §6.4) และขั้น "ตรวจและส่ง" ทำหน้าที่ยืนยัน จึงไม่ต้องมีกล่องยืนยันซ้อน · การเอารายการ
  ใบเสนอราคา หรือไฟล์ออกถามยืนยันข้างสิ่งนั้น (ไม่ใช่ modal) คำถามมีปุ่ม "ลบ…" ขอบแดง และ "ไม่ลบ เก็บ…ไว้" แยกห่างกัน
- มือถือ: คอลัมน์เดียว ช่องเต็มความกว้าง fieldset มี `min-w-0` กันล้นแนวนอน ตัวอักษรเนื้อหา 16 px

## 2. ตรวจแผนกับ "สิ่งที่ห้ามใช้" ก่อนเขียนโค้ด

| ข้อห้าม (§9.9) | แผนนี้ |
| --- | --- |
| ไล่สี สีม่วงเป็นสีหลัก | ใช้ token `bg` `surface` `line` `ink` `ink-muted` `primary` `warn` `danger` `info` เท่านั้น |
| การ์ดมนเงาเดียวกันทุกใบ | การ์ดเฉพาะประเภทคำขอ ขอบเส้นไม่มีเงา ส่วนอื่นเป็นรายการคั่นเส้น |
| glassmorphism neumorphism เงาหนา ขอบเรืองแสง | ไม่มี |
| ป้ายตัวพิมพ์ใหญ่เหนือหัวข้อ ป้ายไม่จำเป็น | ไม่มี หัวข้อแยกด้วยขนาดและน้ำหนัก |
| เน้นคำเดียวในหัวข้อ | ไม่มี |
| เลข 01/02/03 กับสิ่งที่ไม่ใช่ขั้นตอน | เลขใช้กับขั้นของฟอร์ม (ขั้นตอนจริง) และ "รายการที่ n" "ใบเสนอราคาที่ n" (ลำดับจริงของข้อมูล) |
| ลูกศรท้ายปุ่มหรือลิงก์ · monospace | ไม่มีลูกศร ใช้คำ "ไปขั้นถัดไป: …" · ตัวเลขใช้ tabular-nums ฟอนต์เดิม |
| animation ตกแต่ง | มีเฉพาะ transition สีของปุ่มและการ์ด ≤ 150 ms |
| hero ภาพประกอบ emoji | ไม่มี ไอคอน lucide คู่ข้อความ |
| dashboard ตัวเลขใหญ่ | ไม่มี |
| สถานะด้วยสีอย่างเดียว | งบพอ/ไม่พอ กฎครบ/ไม่ครบ ต่ำสุด ขั้นปัจจุบัน มีไอคอนหรือข้อความหรือน้ำหนักคู่เสมอ |
| contrast < 4.5:1 · ตัวอักษร < 14/16 px | ข้อความรองใช้ `ink-muted` (ผ่าน 4.5:1) · มือถือ 16 px · คำอธิบายบนเว็บ 14 px |
| modal ซ้อน · ฟอร์ม > 8 ฟิลด์ไม่แบ่งขั้น · error ใน toast | ไม่มี modal · แบ่ง 4 ขั้น ขั้นละ ≤ 8 ช่อง (รายการและใบเสนอราคาเป็นกลุ่มซ้ำ) · error อยู่ข้างช่องหรือข้างปุ่ม |
| ปุ่มอนุมัติ/ไม่อนุมัติเหมือนกัน · การกระทำย้อนไม่ได้ไม่ยืนยัน | หน้านี้ไม่มีปุ่มตัดสิน · การส่งย้อนได้ (ยกเลิกคำขอ) และมีขั้นตรวจก่อนส่ง · การเอารายการ ใบเสนอราคา หรือไฟล์ออกถามก่อนเสมอ (คำขอที่ถูกตีกลับ: การเอารายการออกคืนงบส่วนของรายการนั้นทันทีที่บันทึก จึงบอกยอดในคำถาม) |
| ตารางเลื่อนแนวนอนบนมือถือ | ไม่มีตาราง รายการเป็นกลุ่มช่องซ้อนกัน |
| ไอคอนเปล่าสำหรับคำสั่งสำคัญ | ทุกปุ่มมีข้อความ |
| หน้าว่าง "ไม่มีข้อมูล" · ปุ่ม "ตกลง"/"ส่ง" | หน้าว่างบอกขั้นต่อไป · ปุ่มบอกผล "ส่งขออนุมัติ" "บันทึกร่างตอนนี้" "เพิ่มใบเสนอราคา" |

## 4. รอบแก้หลังรีวิว (2026-10-03)

ผลรีวิวของหน่วย a ที่เกี่ยวกับหน้าจอ และสิ่งที่แก้ (ข้อเงิน สิทธิ์ และ event อยู่ในสรุปของหน่วยถึง orchestrator):

1. หลังกด "ส่งขออนุมัติ" ไม่มีคำยืนยัน (§9.9 ข้อ 7) → หน้าเดิมเปลี่ยนเป็นคำยืนยันในคำเดียวกับปุ่ม "ส่งขออนุมัติแล้ว รอ {ผู้อนุมัติ} พิจารณา"
   พร้อมเลขที่คำขอ ประโยคบอกขั้นต่อไป และลิงก์ "ดูคำขอ PR-… และติดตามสถานะ" ไปหน้าคำขอ (แบบเดียวกับคำยืนยันของฟอร์มเสนอการเปลี่ยน
   โครงสร้างอำนาจ) · โฟกัสย้ายไปที่คำยืนยัน · e2e @demo ตรวจข้อความนี้และลิงก์
2. ปุ่มลบเป็นลิงก์ธรรมดาชิดกับ "เปิดไฟล์" และลบทันทีไม่ถาม → ปุ่มขอบแดง (variant danger) แยกห่างจาก "เปิดไฟล์" (ลิงก์ชิดซ้าย ปุ่มชิดขวาสุด)
   และถามก่อนข้างสิ่งนั้น (ไม่ใช่ modal): คำถาม + ผลที่ตามมา + "ลบ…" ขอบแดง และ "ไม่ลบ เก็บ…ไว้" แยกกัน · คำขอที่ถูกตีกลับบอกยอดงบที่
   รายการนั้นจองไว้และจะคืนเมื่อบันทึก · ใบเสนอราคาบอกว่าไฟล์ของใบนั้นออกด้วย · ไม่ลบ → โฟกัสกลับปุ่มเดิม
3. บรรทัดสถานะร่างบอก "ตรวจการเชื่อมต่ออินเทอร์เน็ต" กับทุกความผิดพลาด → บอกเหตุตามรหัสที่ได้ (หมดเวลาการเข้าระบบ ระบบกำลังทำรายการอื่น
   ร่างใหญ่เกิน บัญชีไม่มีฝ่าย ประเภทคำขอไม่มีฟอร์มแล้ว ข้อมูลบางช่องไม่ถูกต้อง) และใช้ข้อความเรื่องการเชื่อมต่อเฉพาะเมื่อไม่ได้คำตอบเลย ·
   มีไอคอนคู่ข้อความ
4. ส่งแล้วได้ CONFLICT_VERSION ข้อความบอกให้โหลดใหม่แต่ไม่มีปุ่ม → ในข้อความนั้นมีปุ่ม "โหลดฉบับล่าสุด"

   ("วันที่เลือก: …") ตาม FR-PLT-002 AC3
7. ผู้อนุมัติในเส้นทางที่คาดไว้เป็นชื่อไทยแม้ผู้อ่านใช้ภาษาอังกฤษ → ใช้ชื่ออังกฤษเมื่อองค์กรมี (ไม่มีก็ใช้ชื่อไทย)
