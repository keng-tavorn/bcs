# แบบฟอร์มข้อมูลจริงของ BCS (`BCS_inputs_real_template.xlsx`)

แบบฟอร์มนี้ใช้เก็บข้อมูลจริงของบริษัทลูกค้าเพื่อตั้งระบบ BCS ระยะ 1 (เส้นชัย B · spec §16.0) · ชีตและชื่อคอลัมน์เหมือนไฟล์ข้อมูลสังเคราะห์ระยะ 1 (`BCS_inputs_p1.xlsx`) ทุกชีตที่ขอจากลูกค้า ระบบจึงนำเข้าด้วยตัวอ่านเดิม · ในไฟล์มีชีต `README` ที่สรุปเรื่องเดียวกันแบบย่อ

- สร้างไฟล์ใหม่ (ทีม BCS): `node scripts/py.mjs scripts/inputs_p1/make.py --blank` · ห้ามแก้ไฟล์แม่แบบด้วยมือ แก้ที่ `scripts/inputs_p1/` (ข้อความของแบบฟอร์มอยู่ใน `p1_texts.py` ส่วน `README_BLANK` `BLANK_LABELS`) · ได้ไฟล์เดิมทุกไบต์เมื่อข้อมูลไม่เปลี่ยน
- เทสต์ `tests/unit/inputs-real-template.test.ts` ตรวจว่าแบบฟอร์มมีทุกชีตและทุกคอลัมน์ที่ต้องขอ และไม่มีข้อมูลสังเคราะห์หลงเหลือ
- `pnpm inputs:check` ไม่ตรวจไฟล์นี้ (ตารางว่างจึงไม่ผ่านกฎของไฟล์ระยะ 1) · ไฟล์ที่ลูกค้ากรอกแล้วตรวจด้วยตัวตรวจของเส้นชัย B

## 1. ก่อนกรอก

- **ยังห้ามนำข้อมูลจริงเข้าระบบ** จนกว่าบริษัทกับ BCS ตกลงเรื่องข้อมูลส่วนบุคคลครบ (DPO นโยบาย PDPA ที่ตั้งข้อมูล และข้อตกลงการประมวลผลข้อมูล · ชีต Inputs IN-20 IN-25 · OQ-19) · กรอกไว้ในไฟล์ได้
- **ไฟล์ที่กรอกแล้วมีข้อมูลส่วนบุคคล** (ชื่อ อีเมลพนักงาน เลขบัญชีผู้ขาย) ส่งกลับทางช่องทางที่ตกลงกับ BCS เท่านั้น ไม่ส่งในแชต ไม่แนบอีเมลธรรมดา และ**ห้าม commit ไฟล์ที่กรอกแล้วเข้า repo**
- **ไม่ต้องกรอกทุกชีตพร้อมกัน** ชีต `Inputs` บอกว่าแต่ละเรื่องขอจากใคร (`provider`) ต้องมีก่อนขั้นไหนของระบบ (`neededBefore` เช่น `S2` `S8` `go-live`) และกรอกที่ชีตไหน (`sheet`) · ส่งเป็นรอบตามลำดับนั้นได้
- **ชีต `Questions`** คือคำถามที่ต้องตัดสินในการประชุม (A ผู้บริหาร · B จัดซื้อ · C บัญชีการเงิน · D หน้างาน · E IT HR กฎหมาย · BCS ภายใน) · `demoDefault` คือค่าที่ระบบใช้อยู่ตอนนี้ · กรอกคำตอบที่ `answer` ระหว่างประชุม และเอกสารที่ต้องขอที่ `docsToRequest`

## 2. โครงของทุกตาราง

- แถว 1 = ชื่อคอลัมน์สำหรับโปรแกรม **ห้ามแก้ ห้ามสลับลำดับ** · แถว 2 = คำอธิบายภาษาไทย · ข้อมูลเริ่มแถว 3 · แถวว่างแถวแรกคือจุดจบของตาราง (ห้ามเว้นแถวกลางตาราง)
- สีหัวคอลัมน์: **น้ำเงินเข้ม** = ข้อมูลจริงที่ขอจากบริษัท (ตารางว่าง) · **เทา** = ค่าที่ BCS ตั้งตามค่าเริ่มต้นไว้แล้ว ตรวจแล้วแก้เฉพาะที่ต่าง (ช่องว่างในชีตเทาคือค่าที่ต้องเป็นของบริษัท เช่น `DOA_Policy` `code` `version` `effectiveFrom` และ `Settings` `ap.inboxAddress`)
- ชีตสีทองของไฟล์สังเคราะห์ (`Request_History` `DocSamples` `Scenarios` `Demo_Script_P1`) ไม่อยู่ในแบบฟอร์ม เพราะเป็นข้อมูลทดสอบของ BCS
- ชีตแบบ key / value (`Org` `DOA_Policy` `Settings`): กรอกหรือแก้เฉพาะคอลัมน์ `value` อย่าแก้คอลัมน์ `key`

## 4. ชีตที่ต้องกรอก (เรียงตามลำดับในไฟล์)

ขอจากใครและต้องมีก่อนขั้นไหน ดูจากชีต `Inputs` (แหล่งเดียว) · ตารางนี้บอกสิ่งที่ต้องระวังและกฎที่ตัวตรวจของ BCS ใช้

| ชีต | เรื่อง (Inputs) | สิ่งที่ต้องระวัง |
| --- | --- | --- |
| `Org` | ชื่อจดทะเบียน เลขผู้เสียภาษี สาขา ที่อยู่ ผู้ลงนาม ผู้ดูแลระบบ ขนาดงาน (IN-01 IN-05 IN-19) | `code` BCS ตั้งให้ · `orgAdmins` อย่างน้อย 2 คน คั่นด้วย `,` (รหัสผู้ใช้ในชีต `Users` ที่มีบทบาท `ORG_ADMIN`) · `logoFile` ว่าง = ใช้โลโก้ BCS (ส่งไฟล์โลโก้แยก) |
| `Departments` | ผังองค์กร (IN-02) | ผังต้องเป็นต้นไม้เดียว: แผนกรากได้แผนกเดียว (`parent` ว่าง) ไม่มีวนรอบ และ `parent` ต้องมีจริง · `kind` ตามคำอธิบายแถว 2 |
| `Positions` | ตำแหน่งที่มีอำนาจอนุมัติ (IN-03) | เฉพาะ "ตำแหน่งใน DOA" ไม่ใช่ตำแหน่งงานทุกตำแหน่ง (ตำแหน่งงานอยู่ที่ `Users` `jobTitleTh`) |
| `Users` | ผู้ใช้ (IN-04 IN-21) | อีเมลบริษัทจริงคนละอีเมล · ผู้ดำรงตำแหน่งที่ DOA และผู้ตรวจอ้างต้องมีครบ · `supervisor` อ้างรหัสผู้ใช้ในชีตเดียวกัน |
| `DOA` | ระเบียบอำนาจอนุมัติฉบับปัจจุบัน และวงเงินของเอกสารใหม่ของระยะ 1 (IN-06 IN-32) | ช่วงวงเงินของแต่ละประเภทเอกสารต้องต่อกันพอดี ไม่ซ้อนและไม่เว้น · ต้องมีข้อของ `DOA_CHANGE` และ `ORG_AUTHORITY_CHANGE` ที่มีผู้ดำรงตำแหน่ง · **BCS ไม่แก้ DOA ให้** ชีตนี้ใช้ตั้งร่างแรก แล้วผู้ดูแลของบริษัทเผยแพร่เองในระบบ (NG-12) |
| `DOA_Policy` (เทา) | กติกาประกอบ DOA | กรอก `code` `version` `effectiveFrom` ของระเบียบฉบับที่ใช้ · ค่าอื่นตรวจแล้วแก้เฉพาะที่ต่าง |
| `Workflow_Reviewers` | งานที่ต้องให้หลายฝ่ายตรวจ (IN-31) | `mode` ALL = ต้องครบทุกฝ่าย · ANY = ฝ่ายใดฝ่ายหนึ่ง · ใส่ผู้สำรองทุกแถว · เขียนเงื่อนไขเป็นภาษาไทยที่ `conditionTh` แล้วปล่อย `whenJson` ว่างได้ BCS เขียนให้ |
| `Budget` · `CostCenters` · `GL_Accounts` | งบปีนี้และปีหน้า ศูนย์ต้นทุน ผังบัญชีส่วนที่ใช้ (IN-07 IN-08 IN-26) | `planned` เป็นยอดก่อน VAT · `code` = `budgetKey` ตามด้วย `-` และปี พ.ศ. |
| `Suppliers` · `SupplierPayment` | ผู้ขายที่ใช้บ่อย บัญชีรับเงิน เครดิต ประเภทหัก ณ ที่จ่าย ผู้ออก e-Tax (IN-09 IN-24 IN-28) | ผู้ขายที่จะจ่ายเงินผ่านระบบต้องมีแถวใน `SupplierPayment` · `bankCode` อ้างชีต `Banks` · `whtIncomeType` อ้างชีต `WHT_Types` · `expressVendorCode` กรอกเมื่อมีรหัสเจ้าหนี้ใน Express |
| `Banks` (เทา) | รายชื่อธนาคาร | แก้เมื่อใช้ธนาคารที่ไม่มีในรายการ |
| `Items` | รายการที่ซื้อบ่อย ราคาล่าสุด ราคาที่ตกลง (IN-27) | `refUnitPrice` ก่อน VAT · ราคาที่ตกลงต้องระบุผู้ขายใน `agreementSupplier` |
| `Sites` | ไซต์งานและสถานที่ส่งของ (IN-10) | — |
| `RequestTypes` | แบบฟอร์มขอซื้อขอจ้างที่ใช้อยู่ (IN-11) | `code` ต้องเป็นประเภทที่ระบบมีฟอร์มแล้ว · แบบฟอร์มที่ไม่มีให้แนบตัวอย่างแยก แล้ว BCS เพิ่มให้ |
| `Holidays` | วันหยุดบริษัทปีนี้และปีหน้า (IN-13) | ใช้นับ SLA เป็นชั่วโมงทำการ |
| `Settings` · `WHT_Types` (เทา) | ค่าตั้งของระบบ ประเภทเงินได้และอัตราหัก ณ ที่จ่าย (IN-12 IN-14 IN-16 IN-17 IN-29) | `WHT_Types` รอผู้ทำบัญชีของบริษัทยืนยัน (BR-WHT-01) · `ap.inboxAddress` คืออีเมลรับใบแจ้งหนี้ของบริษัท · แก้เฉพาะค่าที่ต่าง |
| `CompanyBankAccounts` | บัญชีธนาคารของบริษัทที่ใช้จ่ายผู้ขาย (IN-22 IN-30) | เลขบัญชีจริงเป็นข้อมูลอ่อนไหว · รูปแบบไฟล์จ่ายเงินของธนาคารจริงยังไม่รองรับ (ระยะ 1 ใช้ไฟล์แม่แบบกลาง) |

**เรื่องที่ขอเป็นเอกสาร ไม่ใช่ชีต** (`sheet` = `-` ในชีต `Inputs`): รายงานที่ใช้อยู่ (IN-15) · ตัวเลข KPI ปัจจุบัน (IN-18) · DPO และนโยบาย PDPA (IN-20) · ตัวอย่างเอกสารจริงสำหรับ AI ที่ลบข้อมูลอ่อนไหวแล้ว (IN-23) · แม่แบบ DPA (IN-25) · บัญชีผู้พัฒนาแอปของบริษัท (IN-33)

## 5. หลังกรอก

1. ในชีต `Inputs` เปลี่ยน `status` ของเรื่องที่ส่งเป็น "ได้แล้ว"
2. ส่งไฟล์กลับทางช่องทางที่ตกลงกับ BCS (ไม่ส่งในแชต)
3. BCS ตรวจไฟล์ด้วยตัวตรวจของเส้นชัย B แล้วส่งรายการที่ต้องแก้กลับ (อ้างชีต แถว และคอลัมน์)
