# Traceability: แผนที่เจ้าของ AC

ไฟล์ `ac-map.yaml` ในโฟลเดอร์นี้บอกว่า **AC (เกณฑ์ยอมรับ) แต่ละข้อของ FR ชั้น 1 เป็นงานของข้อใดใน checklist §16** พอข้อนั้นถูกติ๊ก `[x]` ด่าน traceability ของ `pnpm verify` ต้องเจอเทสต์ที่ผ่านและชื่อมีแท็ก `[FR-xxx-nnn/ACn]` อย่างน้อย 1 ตัวต่อ AC ที่ข้อนั้นเป็นเจ้าของ ถ้าไม่เจอ ข้อนั้นติ๊กไม่ได้

spec.md เป็นแหล่งความจริง ถ้าไฟล์นี้ขัดกับ spec ให้ยึด spec แล้วแก้ไฟล์นี้ และบอกในสรุปตอนจบรอบ

## ทำไมต้องมีไฟล์นี้

- spec §15.7: ชื่อเทสต์ต้องมีแท็ก `[FR-xxx-nnn/ACn]` หรือ `[GC-…]` และก่อนปิดขั้นใด AC ทุกข้อของ FR ในขั้นนั้นต้องมีเทสต์อย่างน้อย 1 ตัว
- บรรทัด "เสร็จเมื่อ" ใน §16 บอกชื่อ FR แต่ไม่ได้บอกทุก AC บาง FR ไม่มีข้อใดระบุเลย และบาง AC ทดสอบไม่ได้จนกว่าข้อหลังจะสร้างของที่ต้องใช้ เช่น LINE งบ หรือ PO
- ไฟล์นี้จึงกำหนดเจ้าของ **ข้อเดียว** ต่อ AC ให้ verify ตรวจได้ตอนติ๊ก ไม่ต้องรอจบทั้งขั้น

## รูปแบบไฟล์

```yaml
frs:
  FR-PLT-003:
    title: "Event log และไทม์ไลน์"
    acs:
      AC3: { owner: S2-12, demo: true, basis: later, text: "…", note: "…" }
unowned: []
counts: { frs: 76, acs: 236, demo: 213, goLive: 23, unowned: 0 }
basisCounts: { named: 190, later: 30, builder: 16, none: 0 }
```

| ฟิลด์ | ความหมาย |
| --- | --- |
| `owner` | รหัสข้อใน §16 ที่ต้องมีเทสต์ของ AC นี้ก่อนติ๊ก · `null` = ยังไม่มีข้อใดทำได้ |
| `demo` | `true` ถ้าต้องเสร็จก่อนเส้นชัยของรอบเจ้าของ (A หรือ A2) · `false` ถ้าเป็นงาน go-live หรือ §16.10 ให้ข้ามใน demo |
| `basis` | ที่มาของเจ้าของ: `named` `later` `builder` `none` (ดูกฎด้านล่าง) |
| `text` | สรุป AC หนึ่งบรรทัด ข้อความเต็มอยู่ใน spec §8 |
| `note` | เหตุผลที่เลือกเจ้าของ ส่วนที่ทดสอบได้ก่อน หรือเรื่องที่ spec ไม่ได้ระบุ (ต้องมีเมื่อ `basis` เป็น `later` หรือ `builder`) |
| `counts` | `demo + goLive = acs` · `unowned` คือจำนวนใน list `unowned` |

## กฎเลือกเจ้าของ (ทำตามลำดับ)

1. **named** — ข้อที่บรรทัด "เสร็จเมื่อ" ระบุ FR นั้น (หรือระบุ ACn ของ FR นั้นตรง ๆ) เป็นเจ้าของ ถ้าข้อหนึ่งระบุบาง AC เช่น "FR-DOA-001 AC2–AC3" จะเป็นเจ้าของเฉพาะ AC นั้น ถ้าหลายข้อระบุ FR เดียวกันคนละ AC ให้แบ่งตามนั้น
   - ถ้าข้อหนึ่งระบุทั้ง FR และอีกข้อระบุ AC ตรง ๆ ข้อที่ระบุ AC ตรง ๆ เป็นเจ้าของ AC นั้น เช่น FR-PLT-007 AC3 เป็นของ S2-15 ไม่ใช่ S1-13 และ FR-PLT-001 AC2 เป็นของ NEW-12
   - ข้อที่ทดสอบเฉพาะกรณีย่อยของ AC (เสร็จเมื่อเขียนว่า "กรณี …" หรือรอผู้ใช้ยืนยันกติกาของกรณีนั้น เช่น NEW-10 กรณีสมาชิกหลายองค์กร และ NEW-11 กรณีปิด PO) ไม่เป็นเจ้าของ AC นั้น เจ้าของยังเป็นข้อที่ทดสอบ AC ทั้งข้อ
   - ถ้าสองข้อระบุทั้ง FR เหมือนกัน (FR-DOA-004 ใน S2-10 และ S2-12 · FR-INT-007 ใน S2-10 และ S3-05) เจ้าของคือข้อแรกที่ทดสอบ AC ได้ครบ
2. **later** — ถ้า AC ทดสอบได้ไม่ครบจนกว่าข้อหลังจะสร้างของที่ต้องใช้ (LINE และ LIFF จาก S5 · งบจาก S3 · PO GR และผู้ขายจาก S4 · ORG_AUTHORITY_CHANGE จาก S2-16 ฯลฯ) เจ้าของคือข้อ `[demo]` ข้อหลังที่สร้างชิ้นสุดท้ายที่ AC ต้องใช้ และต้องมี `note` บอกว่าส่วนไหนทดสอบได้ก่อน ตัวอย่าง: FR-AUTH-003 AC1 (LIFF idle 15 นาที) เป็นของ S5-03
   - ส่วนของ AC ที่ไม่ทำให้ย้ายเจ้าของมี 2 แบบเท่านั้น: (ก) ส่วนที่บอกวิธีตรวจเพิ่มจากเทสต์ของ AC เอง เช่น "ตรวจด้วยเทสต์และ KPI" ของ FR-INT-007 AC2 (เทสต์ทำได้ใน S3-05 ส่วน KPI G-4 อยู่ใน FR-VIS-003 AC1) (ข) ส่วนที่ไม่มีข้อ `[demo]` ใดสร้าง เช่น "รายงานประวัติ (FR-DOA-011)" ของ FR-DOA-007 AC3 ซึ่งสร้างใน S4-13 `[go-live]` และโมดูลเสริมของ FR-PLT-011 ซึ่งเริ่ม S7
   - ส่วนอื่นทำให้ย้ายเจ้าของตามข้อ 2 แม้เป็นเนื้อหาเดียวกับ AC อื่นหรืออ้าง "(FR-…)" เช่น LINE link ของ FR-AUTH-003 AC2 (เรื่องเดียวกับ FR-LINE-001 AC3) ไป S5-04 · "(FR-LINE-004)" ของ FR-INT-001 AC3 ไป S5-06 · บรรทัดงบตามสิทธิ์ของ FR-INT-003 AC2 (เรื่องเดียวกับ FR-BUD-004 AC2) ไป S3-07 · "LINE ส่งไม่ได้" ของ FR-NOTI-002 AC1 (เรื่องเดียวกับ FR-LINE-007 AC3) ไป S5-08 · วิธีเทสต์ที่เป็นเทสต์ของ AC เองก็ย้ายตามของที่เทสต์ต้องใช้ เช่น "เทสต์ query กับ seed" ของ FR-VIS-001 AC3 ไป D-01 เพราะ seed มี ApprovalTask ตั้งแต่ D-01
   - สิ่งนอกโค้ดที่ข้อ `[demo]` ของ agent สร้างไม่ได้ ได้แก่ บัญชีหรือ repo บน GitHub บัญชี hosting มือถือจริง แอป LINE จริง และโดเมนอีเมลจริง ไม่ทำให้ย้ายเจ้าของ (คนจัดหาเองในข้อ `[คน]` เช่น P0-05 ถึง P0-08 D-03 D-08 และ §16.9 หรือยังไม่มีข้อใดเลย เช่น GitHub repo) จึงเขียนไว้ใน `note` ว่าต้องตรวจที่ไหน
   - CI (GitHub Actions) และ URL ของ staging เป็นของที่ S1-14 `[demo]` สร้างด้วยโค้ด AC ที่ต้องใช้ CI หรือ URL ของ staging จึงเป็นของ S1-14 (FR-PLT-005 AC1 AC3 · FR-PLT-006 AC1–AC2) แม้ S1-14 อาจติดรอ GitHub repo และ P0-05 ถึง P0-08
3. **go-live** — ถ้าเจ้าของมีแท็ก `[go-live]` (S4-13 S4-14 S4-16 S4-18 S5-09 S5-10 S5-11 S5-14 S5-15 S5-16 NEW-08) ตั้ง `demo: false`
4. **demo** — ถ้าเจ้าของมีแท็ก `[demo]` ตั้ง `demo: true` · ข้อ D ของ §16.10 ที่ไม่มีแท็ก `[คน]` เป็นเจ้าของได้ ตอนนี้มี 1 AC คือ FR-VIS-001 AC3 ของ D-01
5. **builder / none** — ถ้าไม่มีข้อใดระบุ AC นั้น เจ้าของคือข้อที่สร้างสิ่งนั้น (`basis: builder`) เช่น S2-05 สร้าง resolveRoute ซึ่งคือ FR-DOA-003 AC1 · ถ้าไม่มีข้อใดสร้างเลย ตั้ง `owner: null` `basis: none` และใส่ใน `unowned` เพื่อเพิ่มเป็นข้อ NEW ใน §16.11

กติกาเสริมที่ใช้ตัดสิน (spec ไม่ได้ระบุ ไฟล์นี้จึงเลือกแบบที่ตรวจได้และปลอดภัย):

- **AC แบบครอบทุกส่วน** เช่น "ทุก command สร้าง Event" (FR-PLT-003 AC1) "การละเมิดทุกครั้ง" (FR-DOA-007 AC2) "event approval_task.decided ทุกตัว" (FR-DOA-005 AC1) เป็นของข้อที่สร้างกลไก ข้อหลังที่เพิ่ม service ใหม่ต้องเพิ่มเทสต์ที่มีแท็กเดียวกันด้วย (`note` บอกว่าข้อไหน)
- **AC ที่บอกว่า "แจ้ง …"** ตรวจได้เมื่อ command สร้าง `Notification` ให้ผู้รับในธุรกรรมเดียวกัน (§4.3 §4.7) ส่วนการแสดงในกระดิ่งอยู่ใน FR-NOTI-001 (S2-14) และการส่งทางอีเมลหรือ LINE อยู่ใน FR-NOTI-002 (S4-06 · AC1 ที่ S5-08) FR-LINE-002 (S5-05) FR-LINE-007 AC3 (S5-08) ยกเว้น AC ที่ระบุช่องทางเอง เช่น "แจ้งทางอีเมล"
- **FR-VIS-002 AC2 (รายงาน 7 ฉบับ)** เจ้าของคือ NEW-08 `[go-live]` จึงเป็น `demo: false` ตามกฎข้อ 3 ซึ่งตรงกับ §16.10 ที่ให้ข้าม "รายงานที่ยังไม่มีนิยาม" ใน demo · AC นี้ห้ามเดาจนกว่า OQ-09 ปิด

## verify ใช้ไฟล์นี้อย่างไร (ด่าน traceability)

ด่าน `trace` เป็นด่านสุดท้ายของ `pnpm verify` (กติกาอยู่ใน `scripts/lib/traceability.ts` · รันเองได้ด้วย `pnpm exec tsx scripts/check-traceability.ts`) อ่านผลเทสต์ของรอบเดียวกันเท่านั้น และทำตามนี้

- AC ที่มีแต่เทสต์ e2e (เช่น FR-PLT-002 AC2 ของ S1-09 · FR-PLT-004 AC3 ของ S1-10 · FR-PLT-005 AC1–AC3 ของ S1-11 และ S1-14) ใช้ผลจาก `test-results/e2e-results.json` เมื่อใหม่กว่าไฟล์เทสต์ทุกไฟล์เท่านั้น ถ้าไม่มีผลที่ใหม่พอ ด่านเป็น SKIP และ `--strict` เปลี่ยนเป็น FAIL → ก่อนติ๊กข้อเหล่านี้ให้รัน `pnpm verify --e2e`
- `--only=trace` รันด่าน unit golden property integration ให้ด้วย เพราะต้องใช้รายงานของรอบนั้น


1. **ตรวจไฟล์นี้กับ spec** — FR และ AC ตรงกับ §8 ครบและเรียงเหมือนกัน · ทุก `owner` เป็นข้อที่มีอยู่ใน §16 · `demo` ตรงกับแท็กของเจ้าของ · `basis: named` ต้องตรงกับบรรทัด "เสร็จเมื่อ" ของเจ้าของจริง · `unowned` และ `counts` ตรงกับที่นับได้ ถ้าไม่ตรง → FAIL
   - วิธีอ่าน "เสร็จเมื่อ" ว่าระบุ AC ใด: หา FR id ด้วย regex ที่มีขอบเขต `(?<![A-Za-z0-9])FR-[A-Z][A-Z0-9]*-\d{3}` เพราะ (1) บรรทัดของ S1-04 มี "NFR-SEC-09" ซึ่ง regex แบบ `FR-[A-Z]+-\d+` อ่านผิดเป็น FR ที่ไม่มีอยู่ "FR-SEC-09" และ (2) รหัสโมดูลมีตัวเลขได้ ถ้าใช้ `[A-Z]+` จะไม่เจอ FR-P2P-xxx เลย (บรรทัด "เสร็จเมื่อ" อ้าง FR-P2P 13 ครั้ง) · ถ้ามี AC ต่อท้ายทันที (`ACn` · `ACn ACm` · `ACn–ACm`) หรือมีรูป "ACn … ของ FR-…" อยู่หน้า ให้นับเฉพาะ AC เหล่านั้น ถ้าไม่มีให้นับทุก AC ของ FR นั้น
2. **อ่านผลเทสต์** — ชื่อเทสต์ที่ผ่านจาก Vitest JSON (`testResults[].assertionResults[].fullName` แบบที่ verify ใช้อยู่แล้ว) และจากผลของ Playwright แล้วดึงแท็กรูป `[FR-PLT-001/AC1]` (ตัวพิมพ์ใหญ่ ไม่มีช่องว่าง) เทสต์หนึ่งตัวมีได้หลายแท็ก
3. **ตรวจข้อที่ติ๊กแล้ว** — ทุกข้อใน §16 ที่เป็น `[x]` ทุก AC ที่ข้อนั้นเป็นเจ้าของต้องมีเทสต์ที่ผ่านและมีแท็กของ AC นั้นอย่างน้อย 1 ตัว ถ้าขาด → FAIL พร้อมบอกผลกระทบ (ข้อนั้นติ๊กโดยไม่มีหลักฐานว่า AC ทำงาน) และวิธีแก้ (เขียนเทสต์ชื่อ `[FR-…/ACn]` หรือเอาติ๊กออก)
4. **ข้อที่ยังไม่ติ๊ก** — รายงานความครอบคลุมอย่างเดียว ไม่ทำให้ FAIL เพราะเทสต์ของข้อนั้นอาจยังไม่ได้เขียน
5. **AC ที่ไม่มีเจ้าของ** — รายงานใน `unowned` ไม่ทำให้ FAIL จนกว่าจะเพิ่มเป็นข้อ NEW
6. **ข้อ `[คน]`** (ตอนนี้มี S4-14 เป็นเจ้าของ FR-P2P-009 AC3) ผู้ใช้ติ๊กเองหลังตรวจด้วยคน ไม่มีเทสต์อัตโนมัติ spec ไม่ได้ระบุว่า verify ต้องทำอย่างไร ข้อเสนอคือรายงานว่า "ตรวจโดยคน" แทนการหาเทสต์
7. **แท็ก GC** — เทสต์ golden มีชื่อขึ้นต้นด้วย `GC-…` (§15.2) spec ไม่ได้บอกว่าแท็ก GC นับแทนแท็ก AC ได้ ด่านนี้จึงนับเฉพาะแท็ก `[FR-xxx-nnn/ACn]` ตัวรัน golden เติมแท็ก AC ในชื่อเทสต์ได้โดยไม่แก้ไฟล์ YAML ของ golden

## เมื่อ spec หรือ checklist เปลี่ยน

- เพิ่ม ลบ หรือแก้ AC ใน §8 หรือแก้บรรทัด "เสร็จเมื่อ" ใน §16 → แก้ไฟล์นี้ให้ตรงในรอบเดียวกัน แล้วแก้ `generatedFrom` `counts` `basisCounts`
- เพิ่มข้อ NEW ให้ AC ใน `unowned` → ตั้ง `owner` เป็นข้อ NEW ตั้ง `demo` ตามแท็ก แล้วเอาออกจาก `unowned`

## ข้อจำกัด

- ด่านนี้รู้แค่ว่ามีเทสต์อย่างน้อย 1 ตัวต่อ AC ไม่ได้พิสูจน์ว่าเทสต์ครอบทุกส่วนของ AC ผู้ตรวจต้องอ่านเอง `note` บอกส่วนที่ต้องทดสอบตั้งแต่ข้อก่อนหน้า
